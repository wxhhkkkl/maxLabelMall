# 旧商城数据导入：字段映射与变更清单

**来源**：`u247521.yz168.cc`（旧微商城后台导出的 `data-collection(1).xlsx`，5 张表共 1478 行）
**目标**：当前系统 —— yudao，租户 **162（御旺宸发）**，即线上 152.136.105.223 与本地开发共用的那个库
**脚本**：`scripts/import_legacy_mall.py`　**测试**：`scripts/test_import_legacy_mall.py`（44 条）

> ⚠️ 本文件与脚本中出现的手机号一律不出现在仓库里 —— 含客户手机号与地址的
> `data-collection(1).xlsx` **不提交**（见文末「版本库卫生」）。

## 1. 数据事实（先核对过，测试与 dry-run 都以它们为基准）

| 事实 | 值 |
|---|---|
| 商品 | 282 行，**唯一编号只有 242 个**（32 个编号重复、涉及 72 行） |
| 分类 | 42 个 = 7 个一级 + 35 个二级（yudao 的硬限制正好是 2 层） |
| 会员 | 91 人，其中 **5 人无手机号**；**余额与积分全部为 0** |
| 订单 | 393 张、486 行明细；下单时间 2025-05-08 ~ 2026-09-24 |
| 流水 | 670 条 = 335 笔「充值」+ 335 笔「订单扣款」，成对，净额 0 |
| 会员表 vs 订单表 | 会员表里的「交易次数/成交金额」有 6/91 与订单表对不上（**以订单表为准**） |
| 订单实付 vs 流水扣款 | 非空的「实付」与流水扣款额**逐笔吻合**（如 190 对 -190）→ 实付即真实付款额 |
| 订单商品名 → 商品表 | 486 行中 367 行能匹配（75.5%），**119 行、63 个名称匹配不上** |
| 商品价格 | 282 条里 **16 条用 float×100 会错 1 分**（如 `37.66 → 3765.9999999999995`） |

### 为什么「商品编号」不能当规格分组依据

32 个重复编号里有 **26 个的重复行跨分类**。例如 `LGTD100300` 同时是
「理光 B110CR 全树脂 129.88」和「理光 B110A 混合基 82.8」——
编号只编码了「品牌 + 品类 + 宽×长」，**材质是另一个维度**。所以这 282 行是
**282 个独立商品**，不合并为多规格（已与项目所有者确认）。

## 2. 字段映射

### 2.1 分类 → `product_category`（42 个，走 admin-api）

| 目标字段 | 来源 / 取值 |
|---|---|
| `name` | `分类名称(Name)` |
| `parent_id` | 由 `上级分类(ParentName)` 解析成新 id；一级为 `0` |
| `sort` | `页面行序号(VisibleOrder)` |
| `pic_url` | `/assets/logo.png`（全站唯一图片资产，现有 14 个分类用的也是它） |
| `status` | `0`（开启。注意分类的 0/1 语义与商品的 0/1 **相反**） |

### 2.2 商品 → `product_spu` + `product_sku`（282 × 1，走 admin-api）

走接口而不是 SQL 的原因：SPU 的 `price`/`stock` 是 SKU 的聚合
（`ProductSpuServiceImpl.initSpuFromSkus`），分类必须挂在二级、品牌必须已存在 ——
这些由服务端裁决的规则不该在导入脚本里重抄一遍（宪法原则 III）。
先例：仓库里已有的 `storefront/scripts/seed-demo-tenant.py`。

| 目标字段 | 来源 / 取值 |
|---|---|
| `name` | `产品名称(Name)` |
| `category_id` | 解析后的二级分类（商品**必须**挂二级，否则服务端拒绝） |
| `price`（分） | `价格(Price)` × 100，**用 Decimal**（16 条会被 float 算错 1 分） |
| `stock` | `库存(TotalQuantity)`；哨兵值见 §3 |
| `keyword` | **旧商品编号**（本 build 的查询不搜 keyword，所以不占搜索位；保留编号便于按编号对账） |
| `introduction` / `description` | `[[…，原系统未导出，待补充]]`（宪法 FR-054：不得编造业务事实） |
| `pic_url` / `slider_pic_urls` | `/assets/logo.png`（旧系统未导出图片地址，老站也拒绝爬取） |
| `brand_id` | 复用租户 162 已有的品牌「御旺宸发」（id=4） |
| `spec_type` / `delivery_types` / `give_integral` | `false` / `[1]` 快递 / `0` |
| `sales_count`、`browse_count` | 建完后按创建返回的 id 回填 `销量(SalesCount)`、`点击数(Hits)`。**必须回填**：接口建单时会把这两个强制置 0（`ProductSpuServiceImpl:114-118`） |
| SKU `name`/`pic_url`/`weight` | 同 SPU；`market_price` 记 0（等于售价会让前台显示成两个一样的价格），`weight` 记 0（旧系统未导出） |

### 2.3 会员 → `member_user`（86 个，直连 SQL）

yudao 的 `/admin-api/member/user` **没有 create 接口**（已逐文件核实），只能直写库。

| 目标字段 | 来源 / 取值 |
|---|---|
| `mobile` | `电话(Mobile)`；有 `UNIQUE(mobile, tenant_id)`，导入前已核对与现有 7 个会员**无交集** |
| `nickname` | `会员名(sNickName)`，空则用旧编号 |
| `create_time` | `注册时间(CrTime)` —— yudao **没有 `register_time` 字段**，注册时间就落在 `create_time` |
| `mark` | `迁移自旧商城 u247521.yz168.cc，原会员编号 <旧编号>`（保留旧编号，可回溯 + 可回滚） |
| `point` / `experience` | `积分(Point)`（全为 0）/ `0` |
| `level_id` | 留空 —— 租户 162 没有会员等级，且前台完全不读等级（已 grep `storefront/src`） |
| `password` | 空串（C 端走「手机号 + 短信验证码」登录即注册） |
| `register_ip` | `0.0.0.0`（NOT NULL，但旧系统未导出注册 IP） |
| `status` / `deleted` / `tenant_id` | `0` 开启 / `0` / `162` |

### 2.4 订单 → `trade_order` + `trade_order_item`（393 + 486，直连 SQL）

`/admin-api/trade/order` 也没有 create 接口（只有发货/改价/改地址/自提）。

**状态码映射**（旧系统状态码由项目所有者 2026-09-29 提供）

| 旧 | 旧含义 | 单数 | → yudao `status` | → `refund_status` |
|---|---|---|---|---|
| 2 | 交易成功 | 381 | `30` 已完成 | `0` |
| 3 | 等待收货 | 1 | `20` 已发货 | `0` |
| 4 | 交易关闭 | 9 | `40` 已取消 | `0` 未退款 |
| 6 | 退款完成 | 1 | `40` 已取消 | **`20` 全部退款** |
| 8 | 货到付款，已发货 | 1 | `20` 已发货 | `0` |

| 目标字段 | 来源 / 取值 |
|---|---|
| `no` | **旧订单编号原样保留**（21 位数字，可搜索、可对账） |
| `user_id` | 按旧会员编号映射到新建的 member_user.id |
| `total_price` | `订单总额(Money)` × 100（**旧系统原值**） |
| `pay_price` | `金额(ModifiedMoney)` × 100；为空则取 `订单总额`（已用流水逐笔验证） |
| `discount_price` / `adjust_price` | 分摊差额，保证 `原价 − 优惠 + 运费 + 调价 = 应付`（与 yudao `TradePriceCalculatorHelper` 的算法一致） |
| `refund_price` | 退款完成那一单取**流水扣款额**（比订单字段可靠） |
| `pay_status` | 状态为 20/30 或已退款 → 1；交易关闭（未退款）→ 0 |
| `pay_time` | 流水的支付时间；没有流水的（线下付款）回落到下单时间 —— **推导值，见 §3** |
| `create_time` / `finish_time` | `下单时间(CrTime)` / `完成时间(ConfirmTime)` |
| `logistics_no` | `快递单号(InvoiceNo)`；111 张为空 → NULL |
| `receiver_name` / `receiver_mobile` | `收件人(Contact)` / `联系电话(Mobile)`（已核对：无空值、长度均 ≤20） |
| `terminal` | `0` 未知 —— 旧系统未导出终端来源，**不猜**是公众号还是小程序 |
| `brokerage_user_id` | NULL —— 推荐人字段只有 `0`/`-1`，没有真实推荐关系 |
| `delivery_type` | `1` 快递 |
| `product_count` | Σ 各明细数量 |
| `remark` | `迁移自旧商城 u247521.yz168.cc`（可回溯 + 可回滚） |
| 明细 `spu_name` | **订单里的历史名称原样保留**（即使该商品现已改名或下架） |
| 明细 `spu_id` / `sku_id` | 按归一化名称匹配到的商品；匹配不上记 **0** |
| 明细 `price` | 匹配到的**现行**商品价；匹配不上记 **0** |
| 明细 `properties` | `默认` 占位（单规格 SKU 的行为，与 `ProductSkuServiceImpl` 一致） |

**为什么不按「现行商品价 × 数量」重算订单金额**：`赋签 MaxLabel 软件授权费` 一类
商品改过价，只有 85.6% 的订单能用现行价对上 —— 订单金额一律取旧系统原值。
明细单价记的是现行目录价，与历史成交价在约 14% 的订单上不一致，属已知缺口。

### 2.5 流水 → **不入库**，导出留档

`scripts/legacy-mall-finance-archive.csv`（670 条，`utf-8-sig`，Excel 双击不乱码）。

理由：91 个会员的余额与积分**全部为 0**，没有任何资产需要迁移；yudao 也没有对应的
资金流水表（最接近的 `pay_wallet_transaction` 是钱包余额流水，硬塞会污染钱包账）。
但流水**有用**：它的支付时间与扣款额被用在了订单上（见 §2.4）。

## 3. 改动过 / 推导出的值（完整清单）

写进报告的都是这些，没有别的：

1. **库存 `2147417040` → `999999`**：仅 `DZ001 不干胶定制` 一条。原值是旧系统的
   「无限库存」哨兵（`int` 上限 − 15），前台会显示成 21 亿件。
2. **`pay_time` 回落到下单时间**：58 张订单没有流水（线下付款），拿不到真实支付时间。
3. **索引 `unclassified` 的人工判定**：`GDTB10070 高等铜版纸 100×70mm` 在旧系统里
   分类是「未分类」。按商品名归入 **卷筒标签 / 高等铜版**。
   —— 这是本次**唯一一处人工判断**，其余分类路径都是照搬。
4. **4 个「孤儿分类路径」中的 3 个不是判定而是修正**：`经济热敏`、`蜡基`、`宸发服务`
   在分类表里都真实存在，只是导出时漏写了父级名，直接补全为
   `卷筒标签/经济热敏`、`碳带/蜡基`、`软件服务/宸发服务`。
5. **退款完成那一单的 `refund_price`** 取自流水扣款额（订单表自身没有退款金额字段）。

**没有改动的**：金额、订单号、注册时间、商品名、收件人、快递单号、销量、点击数、旧编号 ——
一律原值。

## 4. 已知缺口（不是缺陷）

1. **282 个商品都没有主图**，统一用 `/assets/logo.png`。旧系统的图片地址没导出，
   老站根路径 404 且拦截 curl。
2. **商品简介与详情是 `[[ ]]` 占位符**（FR-054：不得编造业务事实）。替换时只改这一处。
3. **订单没有收货地址、发货/收货时间、物流公司**——旧系统未导出，字段留空。
4. **119 行订单明细（63 个名称）在商品表里找不到对应商品**，`spu_id`/`sku_id`/单价记 0；
   订单金额不受影响（取旧系统原值）。这 63 个要分两类看（报告里已分列）：
   - **50 个「可恢复」**：旧系统的「多规格」商品，订单行带规格后缀
     （`多规格哑银不干胶标签【100*70*500单排 】`），而商品表只导出了父商品名
     （`多规格哑银不干胶标签`）。**故意不做自动关联**：父商品的价不等于被下单那个
     规格的价（该父商品在商品表里有两条、价 50 与 30，而订单里的规格名有 6 种以上），
     硬联过去等于给历史订单编一个单价。原值与推算值的区别就在这儿。
   - **13 个「不可恢复」**：旧系统里确实已无对应商品（改名或下架）。
5. **5 个无手机号会员未导入**（旧编号 5667032/5667031/5665971/5661130/5658616，
   全是微信注册、0 交易 0 余额）；清单见导入报告，拿到真号码可随时补录。
6. **订单明细单价是现行目录价**，与历史成交价在约 14% 的订单上不一致（见 §2.4）。
7. **管理端订单汇总会出现「售后 1 单 / ¥400.00」，订单数 392 而不是 393** ——
   这是 yudao 的固有口径（`refund_status != 0` 计入售后而非订单，
   `TradeOrderQueryServiceImpl.getOrderSummary:137`），对应的就是旧系统那张
   「退款完成」的订单。它没有对应的售后申请单记录，售后管理页里不会有单据。

## 5. 怎么跑

```bash
# 离线：只解析 / 打印将写入的每一条（不连库、不连后端）
python scripts/import_legacy_mall.py parse
python scripts/import_legacy_mall.py dry-run

# 备份受影响表 → scripts/_backup/tenant162-before-<时间戳>.sql
python scripts/import_legacy_mall.py backup

# 真正写入（会先停：没有 --yes 不动；有历史 manifest 会拒绝，防重复建商品）
# 前置：本地后端已起（java -jar yudao-server/target/yudao-server.jar，约 70 秒）
python scripts/import_legacy_mall.py apply --yes

# 读回核验（公开 app-api + SQL）
python scripts/import_legacy_mall.py verify

# 回滚（按 manifest 的 id 精确删；示例数据是「取消逻辑删除」而非重新 INSERT）
python scripts/import_legacy_mall.py rollback --yes
```

**连接信息**从后端自己的 `application-my.yaml` 的 `datasource.master` 读，不新增任何凭据。
⚠️ 注意那个文件里**第一个 `password:` 是 Redis 的**，必须按 YAML 结构定位
（第一版脚本就栽在这儿，把 Redis 口令发给了 MySQL 而得到 1045）。

**回滚不是万能的**：回滚会把本次建的商品/会员/订单物理删除，并取消示例数据的逻辑删除。
但它**不会**恢复导入前那 7 个会员在导入后的任何变化（导入本身不改它们）。

## 6. 版本库卫生

- ❌ **不提交** `data-collection(1).xlsx`：含 91 个客户手机号、收件人姓名、联系电话。
- ❌ **暂不提交** `scripts/legacy-mall-finance-archive.csv`（670 条真实资金流水：
  会员编号/昵称、金额、支付时间）。它留在工作区里可用，但**进版本库等于把客户
  交易记录写进永久历史**，这件事该由项目所有者点头，不该默认做。
  要入库就 `git add` 它；要保持仓库干净就删掉它（脚本不读它，删了不影响任何流程）。
- ✅ 已提交：脚本、测试、本文件、导入报告、manifest（manifest 只含 id 与商品名）。

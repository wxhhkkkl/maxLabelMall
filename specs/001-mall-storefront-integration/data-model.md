# Data Model: 赋签门面站与 yudao 后台打通

**Feature**: `001-mall-storefront-integration`
**Source of truth**: [spec.md](./spec.md) 的 Key Entities + yudao 既有后端契约
**Date**: 2026-09-24

## 设计原则

**本特性不新建持久化实体。** 所有数据都由 yudao 既有模块承载，前端只做「读取 → 适配 → 展示」与「表单 → 请求」两个方向的转换。因此本文件描述三件事：

1. **后端实体到前端视图模型的映射**（字段级，含单位换算与命名差异）
2. **前端派生数据**（不落库、由真实数据算出，且必须可验证）
3. **状态流转与校验规则**

### 金额单位（关键约定）

后端所有金额字段均为 **`Integer`，单位「分」**（`ProductSpuDO.price`、`AppTradeOrderSettlementRespVO.Price.totalPrice` 等）。前端展示为「元、两位小数」，换算与格式化只在一处实现，禁止散落 `* 0.01`。

**风险点**：结算金额的核对（SC-007）依赖这一约定。任何跳过统一换算函数的临时计算都会引入分位误差。

## 1. 后端实体 → 前端视图模型

### 1.1 会员（Member）

| 后端来源 | 字段 | 前端用途 |
|---|---|---|
| `AppMemberUserController` `/member/user/get` | `id`、`nickname`、`mobile`、`avatar` | 顶栏展示昵称或脱敏手机号（FR-016） |

- **标识**：手机号为账号主体；由验证码登录隐式建号（FR-009）。
- **末位展示**：昵称为空时回落为脱敏手机号（`138****8000`）。

### 1.6 收货地址（Address）

### 1.7 订单（TradeOrder）

来源：`AppTradeOrderController` `/trade/order/{page,get-detail,create,cancel}`

| 视图字段 | 后端字段 |
|---|---|
| 订单号 | `id` / `no` |
| 状态 | `status`（见 1.7.1） |
| 商品项 | `items[]`（下单时的名称/规格/单价/数量**快照**） |
| 金额构成 | `Price` 对象（见 1.8） |
| 收货信息 | 地址快照 |
| 支付截止时间 | `payExpireTime`（后端已返回，前端直接展示，FR-041） |
| 支付时间 | 支付成功后记录（FR-039） |

#### 1.7.1 订单状态（必须与后端一一对应）

后端 `TradeOrderStatusEnum` 为 5 态，**前端不得归并或自定义命名**（FR-041a）：

| 后端值 | 后端文案 | 前端展示 | 终态？ |
|---|---|---|---|
| `0` | 待支付 | 待支付（可取消、可支付） | 否 |
| `10` | 待发货 | 待发货（即"已付款，等发货"） | 否 |
| `20` | 已发货 | 已发货 | 否 |
| `30` | 已完成 | 已完成（超时自动完成，接收货时限默认 14 天） | 是 |
| `40` | 已取消 | 已取消 | 是 |

**关键语义**：**支付成功后订单进入 `10 待发货`，不是「已支付」**（FR-039）。这是最容易被实现错的映射，必须覆盖测试（SC-017）。

**状态流转**：
```
待支付(0) --支付成功--> 待发货(10) --运营后台发货--> 已发货(20) --超时14天--> 已完成(30)
    |                                    
    +--用户取消 / 超时2小时未支付--> 已取消(40)
```

- 端只在「待支付」提供动作（支付、取消）；「待发货」及之后不提供用户侧动作（本期不做确认收货，FR-041b）。
- 发货动作由运营在既有后台完成，不在本特性范围。

### 1.8 金额构成（Price）

来源：`AppTradeOrderSettlementRespVO.Price`（结算页）与订单详情

| 视图字段 | 后端字段 | 展示要求 |
|---|---|---|
| 商品小计 | `totalPrice` | 明细行 |
| 促销优惠 | `discountPrice` | **独立明细行**（FR-026g） |
| 运费 | `deliveryPrice` | 明细行 |
| 优惠券抵扣 | `couponPrice` | **独立明细行**，与促销优惠分列（FR-026g） |
| 应付总额 | `payPrice` | 明细行，**必须等于以上各项之和**（SC-007） |

- 后端另返回 `pointPrice`（积分）与 `vipPrice`（会员价）。本期**不使用积分**（假设已声明），前端固定声明不使用积分，且明细中不出现积分行。
- **不变量**：`payPrice === totalPrice - couponPrice - pointPrice - discountPrice + deliveryPrice - vipPrice`（以分为单位核对，避免浮点误差）。
  **注意是六项**：`pointPrice` 本期恒为 0（`pointStatus` 固定 `false`），但 **`vipPrice`（会员折扣）不会被置零**，漏掉它会在运营配置会员折扣时失配。若只核对四个展示行之和，MUST 同时声明以服务端 `payPrice` 为准。
- **券的可用性由后端判定**：结算响应已返回可用与不可用两组券，并带 `match` 与 `mismatchReason`（FR-026b）。前端**不得自行判断券是否可用**。

### 1.9 优惠券（CouponTemplate / Coupon）

来源：`AppCouponTemplateController`（可领取的券模板）与 `AppCouponController`（我的券）

| 视图字段 | 说明 |
|---|---|
| 券模板 | 面额、使用门槛、有效期、适用范围（FR-026c 的领券中心） |
| 用户券 | 所属模板、领取时间、状态（未使用 / 已使用 / 已过期）（FR-026d） |
| 结算可用性 | 由结算响应的 `coupons[]` 提供，含不可用原因 |

**唯一性规则**（FR-026c）：同一会员对同一模板只持有一张券，重复领取须被拒绝而非产生重复凭证。
**占用规则**（FR-026e）：一张券只能抵扣一笔订单；订单取消后释放，可再次使用。

## 2. 前端派生数据（不落库）

这些数据**不在后台存储**，由前端按规则从真实数据算出，因此必须可验证（不得写死文案）。依据 FR-008a。

| 派生项 | 规则 | 边界 |
|---|---|---|
| 「热销」角标 | 当前列表内销量最高的前 3 个商品 | 销量全为 0 或商品数不足时不展示（FR-008c），不得铺满整页 |
| 「新品」角标 | 当前列表内商品编号最大的若干（`id` 单调递增，作为创建顺序的近似） | **这是启发式**：列表接口不返回上架时间。若需精确到天，须后端补字段（超出本期范围） |
| 「旗舰」「订阅」角标 | **不展示** | 无任何可推导依据（FR-008a） |

**冲突规则**（FR-008b）：同一商品不得同时挂两个角标，冲突时「热销」优先。

**作用域**：角标只作用于当前展示的那一页，不因翻页而改变同一商品在别处的判定（spec 的 Edge Cases）。

## 5. 与后端能力边界的对照（实现前必读）

本特性**不新增后端实体、字段与接口**。以下字段/能力**后端不存在**，前端不得假设其存在：

| 缺失项 | 影响的需求 | 已定的替代方案 |
|---|---|---|
| 分类的商品数量 | FR-002 | 移除侧栏计数（FR-002a） |
| 商品的价格区间 / 服务标签 | FR-004 | 移除该两组筛选（FR-004a） |
| 结构化的「规格参数」 | FR-005 | 改用 SKU 规格项 + 详情富文本（FR-005a） |
| 商品的角标标记 | FR-008a | 由前端派生，且只派生「热销」「新品」 |
| 商品上架时间 | FR-008a | 「新品」用商品编号近似 |
| 人工配置的推荐位 | FR-008 | 首页商品区按销量取前 N（FR-008） |
| 面向用户的促销活动查询 | FR-026h | 不做商品页促销标签；促销在结算页单列 |
| 注册接口 | FR-009 | 隐式注册（验证码登录即建号） |
| 后端记录协议同意 | FR-050 | 前端门禁，不落库 |

# 设计规范：新增页面的补充设计

**Feature**: `001-mall-storefront-integration`
**Date**: 2026-09-24（**2026-09-27 修订**）
**性质**：交付需要 **23** 条路由；最初其中 6 条来自 `www/` 的设计稿、其余 **17 条**由本文件提供可执行的设计规格。**设计稿已于 2026-09-27 删除**，如今本文件是全站（含原 6 页）**唯一的设计规格来源**。
**依据**：所有令牌与类名均取自原 `www/css/style.css`（1005 行）与 `www/*.html` 的实测清点，**不是新造的设计系统** —— 这份"实测清点"的历史价值在于：它证明了下表每一个色值/类名都**真的来自设计稿**，而不是实现者凭喜好编的。

> **约束（2026-09-27 修订后）**：本规范仍是**新增页面**的视觉归口 —— 新增样式写在 `storefront/src/styles/store.css`，`design.css` 是本项目**可演进**的样式基线（不再要求与设计稿逐字一致）。
>
> ⚠️ 原「设计稿基线」约束（FR-046 要求逐页还原、偏离仅限六处；`design.css` 必须是设计稿的逐字拷贝）**已放开**：允许为可用性与美观做合理改进，无需逐处声明。因此**本文件里凡是"与设计稿保持一致"性质的要求，都不再具有约束力** —— 保留它们是因为这套语言本身是好的、一致的，而不是因为不能改。
> 🚫 **仍然有效**：§1.1 色表与 §1.2 断点的**收口**（对新增页面而言）、§2 的 C1–C8 组件契约、§3.x 的逐页结构、§5 判定口径里不依赖设计稿的那几条 —— 它们已由 `storefront/src/styles/design-consistency.spec.ts` 变成**可执行断言**。

#### C6 变体 ←→ 订单状态映射（MUST 一一对应，不得增删）

设计稿与早期版本在此处**不可实现**：曾出现 `.is-paid`（后端五个状态里没有"已支付"），且 `.is-pending` 与 `.is-paid` 配色逐字节相同 → 五个变体有三个肉眼不可分，正好废掉 FR-041c。

| 后端 `status` | 状态 | 变体 | 底色 | 文字色 |
|---|---|---|---|---|
| `0` | 待支付 | `.is-pending` | `#FF5C22` | `#FFFFFF` |
| `10` | 待发货 | `.is-awaiting-shipment` | `#EAF1FF` | `#2E7CD6` |
| `20` | 已发货 | `.is-shipped` | `#0A1A38` | `#FFFFFF` |
| `30` | 已完成 | `.is-done` | `#F0F4FB` | `#5B6C8F` |
| `40` | 已取消 | `.is-cancelled` | `#F0F4FB` | `#8A97B5` |

**五个变体的底色两两不同**（`#FF5C22` / `#EAF1FF` / `#0A1A38` / `#F0F4FB` / `#F0F4FB`）——
其中已完成与已取消同底但文字色不同（`#5B6C8F` vs `#8A97B5`），二者均为终态、语义差异小，可接受；
**未支付 / 待发货 / 已发货三者必须一眼可分**，这正是 FR-041c 的要求。

该映射 MUST 实现在 `storefront/src/utils/orderStatus.ts`（T092），由 `orderStatus.spec.ts`（T091）
**断言五个变体互不相同**（而不只是断言状态文案不同）。

## 3. 页面规格（17 条路由）

每条给出：用途 / 结构 / 复用的既有类 / 新组件 / 关键状态。

> **个人中心一组页面的共用布局（2026-09-27 修订）**
>
> `/account`、`/order`、`/order/:id`、`/account/address`、`/coupon`、`/coupon/mine` 这 6 条
> **共用同一个两列布局**：左侧 `AccountSidebar`（个人中心 / 我的订单 / 领券中心 / 收货地址 / 我的券，
> 当前项高亮）+ 右侧内容区（`.account-main`）。布局样式在 `store.css` 的 `.account-wrap`。
>
> **原因**：所有者 2026-09-27 反馈「点选后不要没有菜单，这样用户体验很差」——
> 原先只有 `/account` 自带侧栏，点进其余任一页菜单就消失，用户只能靠浏览器后退。
>
> ⚠️ 两个实现要点（都踩过）：
> ① 设计稿的 `.sidebar` 写着 `width: 250px`，会把 200px 的栅格列**撑破**、顶到右侧内容上，
>    所以 `.account-sidebar` 必须覆盖 `width: 100%`；
> ② 有子路由的项（`/account`、`/coupon`）必须**精确匹配**才高亮，否则 `/coupon/mine`
>    会同时点亮「领券中心」与「我的券」。
>
> 因此下面的 **§3.3–§3.8 只描述右侧内容区的构成**，侧栏不再逐节重复。

### 3.1 `/cart` 购物车

- **结构**：`.crumbs` → 页标题（`26px`）→ 有效条目区（`.dl-table` 行式布局：主图 72×72 + 名称/规格 + 单价 + `.qty-box` + 小计 + 移除）→ 失效条目区（同表结构，整行降透明度 .6 且**复选框禁用**）→ 右下固定结算条（已选 N 件 / 合计 `.ml-amount-row.is-total` / `.btn-buy` 去结算）
- **复用**：`.crumbs`、`.dl-table`/`.dl-row`、`.qty-box`、`.btn-buy`、`.empty-state`
- **新组件**：C3（勾选）、C8（合计）
- **状态**：加载中 C5；空车 `.empty-state`（文案 + `.btn-cyan` 去商城）；部分失效时两区并存；结算条在 0 勾选时按钮置灰

### 3.2 `/checkout` 结算

- **结构**：`.crumbs` → `.ml-steps`（当前「填写信息」）→ 左栏：收货地址卡（选中态描边 `#2E7CD6` + 新增地址入口）→ 商品清单（同购物车行式，但**只读**，不可改量）→ 券选择行（点击展开 C1 弹层列出可用/不可用券）→ 右栏（桌面）：金额明细卡（商品小计 / 促销优惠 / 运费 / 优惠券抵扣 / **应付总额**）+ `.btn-buy` 提交
- **复用**：`.crumbs`、`.dl-table`、`.btn-buy`、`.btn-cart`
- **新组件**：C1（券选择弹层）、C7（步骤条）、C8（金额明细）
- **关键约束**：促销优惠与优惠券抵扣是**两行**（FR-026g）；**无积分行**；明细总额 MUST 等于各行之和（SC-007，按**六项**核对）；移动端每件商品在该页以紧凑卡片呈现，为优惠券与运费腾出首屏空间
- **状态**：无地址 → 地址卡换成引导 + `.btn-cyan`「新增收货地址」（**就地弹层，MUST NOT 跳转** —— 复用 `AddressFormDialog`，与地址管理页同一个组件；跳走会丢掉本页已选的券/地址/备注。保存后自动选上新地址并**重算运费**，FR-028）；提交中按钮禁用；库存/价格变动 → C1 弹层要求确认（FR-030）

### 3.3 `/order` 我的订单

- **结构**：`.crumbs` → 状态筛选 `.cat-pills`（全部 / 待支付 / 待发货 / 已发货 / 已完成 / 已取消）→ 订单卡列表：卡头（订单号 + 下单时间 + 右侧 C6 状态标签）+ 商品缩略行 + 卡脚（应付金额 + 操作按钮：待支付 → 取消订单 / 立即支付；其余 → 查看详情）
- **复用**：`.crumbs`、`.cat-pills`/`.tab`、`.p-card`、`.pager`、`.empty-state`、`.dl-table`（卡内商品行）
- **新组件**：C6（状态标签）、C2（操作反馈）
- **状态**：各筛选下为空 → `.empty-state` + `.btn-cyan`「去商城逛逛」

### 3.4 `/order/:id` 订单详情

- **结构**：`.crumbs` → 状态区（大号状态文案 + 该状态下的一句话说明；**待支付时**显示支付截止时间与倒计时 + `.btn-buy`「立即支付」）→ 收货信息卡 → 商品明细表（`.dl-table`，含下单时的名称/规格/单价/数量快照）→ 金额构成卡（C8，**含所用券与抵扣金额**，FR-026f）→ 订单信息（订单号/下单时间/支付时间/支付方式，`.dl-table` 只读）
- **复用**：`.crumbs`、`.dl-table`、`.btn-buy`、`.btn-cart`
- **新组件**：C6、C8、C2
- **关键约束**：**不存在**用户侧「确认收货」控件（FR-041b）；已付款订单**不展示**支付入口（FR-040）；状态 MUST 来自后端，不自判（FR-039）
- **状态**：待支付（支付 + 取消）/ 待发货 / 已发货 / 已完成 / 已取消 —— 五种共用同一结构，仅状态区与操作区不同

### 3.5 `/account` 个人中心

- **结构**：`.crumbs` → 左侧导航（`.sidebar` 复用，项目：个人中心 / 我的订单 / 领券中心 / 收货地址 / 我的券 / 设置密码）→ 右侧内容区：昵称（或脱敏手机号）+ 头像占位（`.ph` 风格圆形）→ 快捷入口三卡（订单/地址/券，`.entry-card`）→ 设置密码表单（C4）+ `.btn-primary`
- **复用**：`.crumbs`、`.sidebar`、`.entry-card`、`.btn-primary`、`.btn-cart`
- **新组件**：C4（表单）、C2（保存反馈）
- **设置密码表单字段**：新密码 / 确认新密码 / **手机验证码（必填）** + 内联「获取验证码」按钮（60 秒倒计时，复用 `LoginDialog` 的同一机制；短信场景取 **3 = 修改密码**，与登录场景 1 不是同一个码，两者不可互换）
- **关键约束**：后端 `PUT /member/user/update-password` 的 `code` 是**必填**（`AppMemberUserUpdatePasswordReqVO` 上标着 `@NotEmpty(message = "手机验证码不能为空")`），且服务端会 `useSmsCode(scene=3)` 实际核销 —— **只传 `password` 必然 400**。故本表单 MUST 一并收集验证码，不得省略
- **状态**：未设密码 → 提示卡「尚未设置密码，仅可使用验证码登录」；设置成功后 C2 提示

### 3.6 `/account/address` 收货地址

- **结构**：`.crumbs` → 地址卡列表（`.p-card` 变体）：收件人 + 手机号 + 完整地址 + 「默认」标记（`.ml-pill`）；卡脚操作（编辑 / 删除 / 设为默认）→ `.btn-cyan` 新增地址 → C1 弹层表单：收件人 / 手机号 / **地区三级联动** / 详细地址 / 是否默认（C3）
- **复用**：`.crumbs`、`.p-card`、`.btn-cyan`、`.btn-cart`
- **新组件**：C1、C3、C4、C6（默认标记）
- **关键约束**：行政区划**必须来自后台** `/system/area/tree`，不得前端内置（宪法原则 III）；五个字段全必填（FR-027）
- **状态**：无地址 → `.empty-state` + 新增引导；删除前 C1 二次确认

### 3.7 `/coupon` 领券中心

- **结构**：`.crumbs` → 券卡网格（桌面 3 列 / 平板 2 列 / 移动 1 列）：左侧面额区（`#EAF1FF` 底 + `#2E7CD6` 大字面额或折扣）+ 右侧信息（名称 / 使用门槛 / 有效期）+ `.btn-primary`「立即领取」或灰色「已领取」
- **复用**：`.crumbs`、`.grid-3`、`.btn-primary`
- **新组件**：C2（领取反馈）、C6（券状态）
- **关键约束**：重复领取**不得展示成两张**（FR-026c）
- **状态**：可领 / 已领 / 已抢光 / 未登录（点了先弹登录）

### 3.8 `/coupon/mine` 我的券

- **结构**：`.crumbs` → `.cat-pills`（未使用 / 已使用 / 已过期）→ 券卡列表（结构同上，操作区改为「去使用」`.btn-cyan` 跳可用商品，或灰态无操作）
- **复用**：`.crumbs`、`.cat-pills`、`.grid-3`、`.btn-cyan`
- **新组件**：C6
- **状态**：各分组为空 → `.empty-state` + 「去领券中心」

### 3.9 `/agreement/user` 与 3.10 `/agreement/privacy` 协议页

- **结构**：`.crumbs` → 单栏阅读版式（最大宽 760px 居中）→ `.agr-title`（26px）+ `.agr-meta`（生效日期，13px `#8A97B5`）+ 正文（`h2` 18px `#16233F`、段落 14px/行高 1.75 `#5B6C8F`、列表缩进）
- **复用**：`.crumbs`
- **新组件**：无（纯排版，新增 `.agr-*` 少数几条）
- **关键约束**：**纯静态，不依赖任何接口** —— 后端不可用时仍可打开（SC-016）

## 4. 内容依赖（MUST 由业务方提供，实现者不得编造）

**这是一条硬约束，不是建议。** 以下内容涉及真实业务事实，编造等于在正式站点上发布虚假信息：

| 页面 | 需要业务方提供 |
|---|---|
| `/about` 公司介绍 | 公司全称与简介、成立年份、真实数据（服务企业数/模板数/专利数）、发展历程节点 |
| `/news` 新闻动态 | 真实文章条目（**至少 3 条**，否则该页不应发布） |
| `/contact` 联系我们 | 客服热线、合作电话、售后邮箱、公司地址、工作时间 |
| `/jobs` 加入我们 | 岗位清单、各岗位职责与要求、投递邮箱 |
| `/changelog` 更新日志 | 真实版本条目与日期 |
| `/enterprise` 企业采购 | 权益文案、热线号码、企业微信二维码图片 |
| `/templates` 模板中心 | 真实模板数量与条目（**不得沿用设计稿的"2,000+"除非业务方确认**） |
| `/agreement/*` 协议 | 两份条款正文（法务提供） |
| 全站页脚 | 备案号（设计稿为 `京ICP备 XXXXXXXX 号` 占位）、真实客服热线 |

**实现策略**：先按本规范把页面结构与样式做出来，内容用**明显可辨的占位符**并在页面上标记 `data-content-pending`，**MUST NOT** 用编造的看似真实的文案（如虚构的电话号码、地址、数据）填充。上线前由业务方替换，并经一次巡检确认无残留占位符。

**种子数据**：已在 `storefront/src/data/placeholders.ts` 生成全部占位内容 —— 每处业务文案都包在 `[[ ]]` 里，字符串长度按真实文案量级给足（布局可直接渲染），并导出 `hasPendingContent()` 供上线前门禁使用。**替换时只改该文件的字符串并去掉 `[[ ]]` 即可。**

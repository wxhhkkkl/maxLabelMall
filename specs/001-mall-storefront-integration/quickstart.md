## 1. 前置条件

| 项 | 要求 | 依据 |
|---|---|---|
| Node | ≥ 20.19（本地实测 `v24.14.1`） | `yudao-ui-admin-vue3/package.json` 的 `engines` |
| 包管理器 | pnpm | 同上 |
| 后端 | `yudao-server` 在 **48080** 运行 | [research.md](./research.md) R2 |
| 数据库 | `ruoyi-vue-pro.sql` 之外，还需导入模块 SQL：`mall-2026-04-18.sql`、`member-2026-05-30.sql`、`pay-2026-04-18.sql` | 仓库自带的 `ruoyi-vue-pro.sql` 只含基础表；模块 SQL 在同目录 |
| 中间件 | Redis 与 MySQL 可达（凭据见 `.env` / `application-my.yaml`） | 项目既有约定 |

### 启动后端（2026-09-24 实测确认）

```bash
cd yudao-cloud
mvn -B -DskipTests package          # 代码有改动时必须重新打包，见下方警告
java -jar yudao-server/target/yudao-server.jar
```

- ✅ **能启动**。实测：Tomcat 绑定 48080，约 70 秒完成启动，成功响应真实接口。
- ⛔ **绝不能加 `--spring.profiles.active=local`**。`yudao-server` 的 `application.yaml` 里 `spring.profiles.active` 已是 `local,my`，命令行传 `local` 会**覆盖**这个列表、丢掉 `my` 这个 profile，于是回落到 `jdbc:mysql://127.0.0.1:3306` 并以 `Connection refused` 启动失败。**这正是"只能从 IDE 启动、java -jar 跑不起来"这个错误结论的来源。**
- ⚠️ **jar 不会自动反映源码改动**：jar 里的模块代码来自构建时的模块产物。改了代码必须重新 `mvn package`。
- ⚠️ `application-my.yaml` 被 gitignore，但会在构建时打进 jar（`BOOT-INF/classes`）。从干净 clone 构建出的 jar 不含它，会回落到 tracked 的 `application-local.yaml` 默认值，需用 `--spring.config.additional-location=.` 之类外部提供。
- ⚠️ 远程 Redis 与 CynosDB 是**启动期硬依赖**（Druid 与 Redisson 在启动时就连），连不上会启动失败；云安全组只放行开发机当前出口 IP，家庭宽带 IP 变动后需重新加白。
- ⚠️ `flowable.database-schema-update: true` —— 首次以 jar 启动会在远程 CynosDB 上建/改 Flowable 表，**所以裸跑一次并非只读操作**。

**两个必查的一次性前置**（缺任一项会以难懂的方式失败）：

1. **`pay_channel` 必须有 `code='mock'` 且 `app_id=1` 的行**，且 `status=0`（启用）。缺行会导致提交支付因渠道不可用而失败。
2. **运营侧必须关闭自提开关**（`deliveryPickUpEnabled`）。本期前台不做自提（FR-027a），开关未关可能出现"前台按快递下单、后台按自提校验"的错配。

## 2. 启动前端

```bash
cd storefront
pnpm install          # 网络受限时追加 --registry=https://registry.npmmirror.com
pnpm dev
```

默认 `http://localhost:5173`。

**环境变量**（`storefront/.env.local`）：

```
VITE_BASE_URL=http://localhost:48080
VITE_API_URL=/app-api
VITE_TENANT_ID=1
VITE_PORT=5173
VITE_TITLE=赋签 MaxLabel
```

**不需要配置开发代理** —— 后端 CORS 已放开所有来源（`allowedOriginPattern("*")`），浏览器直连 48080 即可。详见 [research.md](./research.md) R4。

## 3. 联调利器（本地专用）

### 3.1 短信验证码恒为 `9999`

`yudao-server` 的 `yudao.sms-code.begin-code: 9999` / `end-code: 9999`，生成区间只有一个值，所以**任何手机号的验证码都是 `9999`**。发送验证码时传 `scene: 1`。

验证码会先落库再发送，即使渠道发不出（种子里是钉钉调试渠道且 token 是占位符）也能用：

```sql
select code from system_sms_code where mobile = '13800000000' order by id desc limit 1;
```

### 3.2 跳过登录：mock 令牌

本地开了 `yudao.security.mock-enable: true`，带 `Authorization: Bearer test1` 即冒充 `userId=1` 的会员。适合快速验证购物车/下单，**但不要用它验收登录流程本身**。

### 3.3 模拟支付"提交即成功"

```
POST /app-api/trade/order/create        → { id: 交易订单号, payOrderId: 支付单号 }
POST /app-api/pay/order/submit          body: { id: payOrderId, channelCode: "mock" }
   → 立即返回成功 → 异步回调 /app-api/trade/order/update-paid → 订单进入待发货(10)
```

**前端不要自己把订单标记为已支付**（FR-039：状态权威在后端）。提交后拉一次订单详情确认状态，必要时带 `sync=true`。

## 5. 未纳入本清单的验证

**每一项都写明了理由与归属。** 这张表存在的意义是：不验证的部分必须显式可见，而不是看起来"已覆盖"。

| 项 | 归属 | 不验证的原因 |
|---|---|---|
| **SC-006（100 并发不超卖）** | 后端 | 需要压测工具与隔离环境，规划阶段不安排。本特性不引入并发逻辑，库存扣减正确性由后端下单事务保证 |
| **FR-033 的「超时释放库存」半段** | 后端 | 由 `TradeOrderAutoCancelJob` 驱动，见下方 SC-018。**注意：FR-033 的另外半段是被验证的**——「下单扣减库存」由 §4.4 的下单核对体现，「取消后释放」由 §4.4 验证。不要把它整条说成不验证 |
| **SC-018 的「超时后 10 分钟内自动取消」半段** | 后端 + 调度器 | 依赖 XXL-Job 调度器。本地未启用调度器时不会自动触发。**「直接调取消接口」不能算验证这一条**——那走的是用户取消路径，且不含 10 分钟时限。若要验证，须启用调度器并把实测结果记回此处 |
| **SC-013 的「同一张券只能抵扣一笔订单（含并发）」半段** | 后端 | 由后端的券占用机制保证，前端不含相关逻辑。SC-013 前半段（抵扣金额正确）由 `money.spec.ts` 与 `CheckoutView.spec.ts` 验证 |
| **SC-002 / SC-003 的上限判定** | 前端 + 人工 | e2e 会**记录**墙钟时间但不硬断言上限（避免在慢机器上假失败），实测值需人工核对 |

**已从本表移除的一项**：「端到端自动化不做」——该结论的依据（后端无法无头启动）已于 2026-09-24 被实测推翻，`java -jar` 可正常启动，因此 e2e **在做**（见 [tasks.md](./tasks.md) 的 T060 / T075 / T088 / T114 与 §7 的执行记录）。

> **2026-09-27 复核**：本表五项**依然成立**，无一项转为可验证。特别是
> **SC-018 的「超时自动取消」半段仍未验证** —— 本地未启用 XXL-Job 调度器。
> 重申口径：**调 `/trade/order/cancel` 不算验证这一条**（那是用户主动取消，
> 不含 10 分钟时限）。SC-006 的并发压测同样未做，归属后端。

## 6. 常见故障排查

| 现象 | 很可能的原因 |
|---|---|
| **页面加载成功但商品列表为空、控制台无报错** | `tenant-id` 漏传。注意错误是 `HTTP 200 + body.code=400`，只看 HTTP 状态会漏判 |
| 所有请求返回 `code: 400`「请求的租户标识未传递」 | 同上 |
| 登录后依然请求不带令牌，或刷新后掉登录态 | 令牌存储 key 不一致（`ACCESS_TOKEN` 与 `token` 混用）。本项目固定用 `ACCESS_TOKEN` / `REFRESH_TOKEN` |
| 刷新令牌接口报参数错 | `refreshToken` 是 **query 参数**，写成 body 会失败 |
| 结算接口报 `items` 绑定失败 | `items[]` 需手工拼 query（`items[0].skuId=..&items[0].count=..`） |
| 结算接口报「是否使用积分不能为空」 | 漏传 `pointStatus`（后端标了 `@NotNull`），本期固定传 `false` |
| 提交支付报渠道不可用 | `pay_channel` 缺 `code='mock'` 且 `app_id=1` 的行 |
| 支付成功但订单仍显示待支付 | 支付回调未到达。回调地址是种子数据里写死的 `http://127.0.0.1:48080/app-api/trade/order/update-paid`，确认后端确实在 48080 |
| 改价后前台不变 | 前端缓存或后台未真正保存；也确认没有把商品列表缓存进本地存储 |
| 金额差 100 倍 | 分/元混淆。后端所有金额是**分**，换算只允许走 `utils/money.ts` |
| 埠 48080 被占用且后端起不来 | `yudao-gateway` 与 `yudao-server` **都监听 48080**，两者本地互斥，不要同时启动 |

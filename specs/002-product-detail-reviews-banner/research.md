# Research: 商品详情、评价（展示与撰写）与商城页 banner

Phase 0 产出。每条记「决定 / 理由 / 被否决的方案」。所有事实均来自代码核查（含文件位置），
不是推测。

## R1 —— 详情"有没有内容"怎么判定

**决定**：在 `src/utils/sanitize.ts` 里新增纯函数 `hasVisibleContent(html): boolean`，
用 DOM 解析判断：**存在 `<img>`，或存在非空文本节点**，即算"有内容"。

**理由**：
- 现在的判定是 `clean.replace(/<[^>]*>/g, '').trim()` —— 剥掉所有标签后看还剩不剩**文字**。
  纯图片详情必然剥成空串，于是整块被隐藏。这正是本缺陷的根。
- 用 DOM 解析而不是正则，是因为正则判"有没有可见内容"本来就不可靠（自闭合标签、属性里的 `>`、
  注释都能骗过它）。浏览器与 jsdom 都有 `document.createElement`，测试环境一致。
- 判据选「`<img>` **或** 非空文本」，覆盖了电商详情的两种常态：长图型、图文型。
  `<p></p>`、`<div></div>`、`<br>` 这类**空壳不算有内容** —— 它们的可见面积是零，
  放它们通过会让"详情区块渲染出来但什么也看不见"，那正是 FR-066 要防的空白块。

**被否决的方案**：
- **正则改宽松**（例如同时检测 `<img`）：能修好图片型，但判据仍是字符串匹配，
  跟着会漏掉 `<table>` 内的图片、注释里的假 `<img>`。修一次埋在里面的第二个坑不划算。
- **去掉判定，只要有内容就渲染**：会让"详情是空串 / 只剩空壳"的商品渲染出空白区块 —— 直接违反 FR-066，
  而当前的那层判定当初就是为这个加的。
- **放在 `ProductView.vue` 里就地改**：判定逻辑会散在视图里、难以穷举测试；
  `sanitize.ts` 是本仓库富文本处理的唯一实现处，判据属于它。

## R2 —— 详情判定的消费方式

**决定**：`ProductView.vue` 的 `safeDescription` 改为 `sanitizeRichText` 之后调用 `hasVisibleContent`，
命中才返回 `clean`。

**理由**：`safeDescription` 是 `sanitizeRichText` 在全仓库的**唯一生产调用点**（已 grep 确认），
改动面就一处。保持"清洗 → 判空 → 渲染"的顺序不变，只换判空的口径。

**被否决的方案**：把判定合并进 `sanitizeRichText`（让它顺带返回是否为空）。那会改变一个
**安全相关函数**的返回值语义，且它的既有 11 条测试全都断言"返回 HTML 字符串"，改动面反而更大。

## R3 —— 商城页 banner 的位置：新增而不是复用「首页」

**决定**：给 `BannerPositionEnum` 加 `MALL_POSITION(6, "商城页")`，并往字典
`promotion_banner_position` 插一行同值数据。

**理由**：
- 后端对 banner 位置做 `@InEnum` **强校验**（`BannerBaseVO.position`），提交枚举外的值会被 400 拒绝 ——
  **只加字典行没有用**，两处必须同时改。
- 管理端「位置」是**字典驱动**的单选（`getIntDictOptions(DICT_TYPE.PROMOTION_BANNER_POSITION)`），
  加完字典后端**零改动**就会出现新选项。这是本次服务端改动能压到"一项枚举 + 一行数据"的原因。
- 当前枚举只有「首页 / 秒杀 / 砍价 / 限时折扣 / 满减送」，**没有任何一个语义贴近商品列表页**。

**被否决的方案**：
- **复用「首页」位置**：零服务端改动。且因为**首页现在是写死的静态首屏、根本不读这个接口**，
  眼下的确不会串位。但这是**埋雷** —— 首页哪天接上同一接口，两处就会被迫共用同一批内容。
  用一个未来的耦合去省"一项枚举 + 一行数据"，不划算。
- **前端写死 banner 内容**：与"内容由后台下发"的既有做法相反，运营改不了，且直接违反 FR-080。
- **不加枚举，前端把值硬编码为 6**：提交到后端一样被 `@InEnum` 拒绝。

## R4 —— 评价列表的排序：**已证实「无排序」**

**决定**：**不假设任何顺序**。契约不承诺"返回最近评价"，详情页文案用中性的「用户评价」。
**当前不为此改服务端**；若将来要"真正的最新在前"，那是**另一轮**的事（见下）。

**已证实的依据（2026-10-10 查代码，非推测）**：
- `AppCommentPageReqVO extends PageParam` —— **不是** `SortablePageParam`，请求体里根本没有排序字段；
- `PageParam` 不带默认排序；
- `BaseMapperX.selectPage` 的 ORDER BY 完全来自 `sortingFields`，为空则 **SQL 里没有 ORDER BY**。

→ 返回顺序**不确定**；MySQL 实际多半按主键升序，**也就是最早的在前**。
若按最直观的用法（取第一页展示），用户看到的会是**最老的**评价 —— 比空着还糟。

**为什么现在不修**：
- 线上当前**没有评价数据**（决策 Q6），顺序暂时无从体现；
- 要"真正的最新在前"必须**再动一处服务端**（让该请求 VO 继承 `SortablePageParam`，
  或在 mapper 加 `orderByDesc`），超出本次 plan / contracts 的边界 —— **须先改设计再动手**，
  不能顺手做。
- 前端能做的只是"不在文案里承诺顺序"，这一条已经落进
  [contracts/app-api.md](./contracts/app-api.md) §2.1 与 [tasks.md](./tasks.md) T243。

**被否决的方案**：
- **假定它是倒序**（本项目多数返工的成因 —— 对既有后端行为做未经核实的假设）。
- **前端拿到结果后自行按时间倒序**：第一页本就是最早的 N 条，倒序后仍是"最早那批里最新的"，
  属于**看起来修好了、实际更误导**。要真修就修服务端。

## R5 —— 评价图片上传：新写一个多图组件，不改 `AvatarUploader`

**决定**：新增 `src/components/MultiImageUploader.vue`（props: `modelValue: string[]`、`max`），
内部复用已有的 `uploadFile()`（`src/api/upload.ts`）。

**理由**：
- `AvatarUploader` **只支持单张**：它硬读 `input.files?.[0]`，input 上没有 `multiple`，
  `modelValue` 是单个字符串。评价要最多 9 张，语义对不上。
- `uploadFile(file): Promise<string>` 是通用的（接受任意 `File`、无尺寸/格式假设、返回 URL 字符串），
  **可以直接复用**，不需要新接口封装。
- 后端限制是从配置来的（`spring.servlet.multipart.max-file-size: 16MB`），且**没有格式白名单** ——
  所以前端不做格式判断，超限时把后端文案透出来即可（沿用个人中心头像上传的口径）。

**被否决的方案**：
- **把 `AvatarUploader` 改成支持多张**：会改到一个已在用的组件（个人中心），
  违反最小改动；而且头像"圆形单张"与评价"九宫格多张"的展示形态完全不同，硬合会写出满是分叉的组件。
- **不引入组件，在 `CommentCreateDialog` 里内联写**：弹层已经要管星级与文字校验，
  再塞一套上传状态机会让它难测；上传的"失败不丢已填内容"是可独立测试的行为，值得单独成件。

## R6 —— 商城页 banner 的样式复用边界

**决定**：**只复用外层 `.mall-banner`**（容器尺寸、圆角、阴影、以及已有的移动端媒体查询），
并给 `BaseCarousel` 传 `class="mall-banner"`；slide 自己写图片型的最小样式。
**不套** `.mbn-tag / .mbn-title / .mbn-desc / .mbn-btn / .mbn-1..3`。

**理由**：
- `design.css` 里这套样式**早就写好了，但没有任何页面在用**（grep 确认：`.mall-banner`/`.mbn-*`
  只出现在样式表里）。轮播组件 `BaseCarousel` 同样只被它自己的测试引用 —— 也就是说**版式是现成的、缺的只是接线**，
  这正是本次成本很低的原因。
- 但 `.mbn-*` 是**文字型**横幅（渐变底 + 标题 + 描述 + 按钮），而后端 `promotion_banner` 只提供
  `picUrl` + `url` + `title` —— **没有描述、没有"标签"字段**。硬套等于要为不存在的字段编内容（违反宪法
  "业务事实不得编造"）。
- `.mall-banner` 与 `BaseCarousel` 的类名是**对得上的**：样式表里的后代选择器写作
  `.mall-banner .car-dots` / `.mall-banner .car-arrow`，而 `BaseCarousel` 的根节点正是 `class="carousel"`，
  Vue 的 class 透传会把 `mall-banner` 合并上去，选择器自然命中。
- **一个必须记住的细节**：`BaseCarousel` **不会**给插槽内容加 `car-slide`，而
  `flex: 0 0 100%` 只在 `.car-slide` 上 —— 所以 slide 的 class 必须是 `"car-slide"`（或与自己的类并列写）。

**被否决的方案**：
- **连 `.mbn-*` 一起用**：需要给后端加"描述/标签"字段，是把一个纯展示需求扩张成数据结构变更。
- **不用 `BaseCarousel`，自己写轮播**：已有的那个已经覆盖自动播放、圆点、箭头、悬停暂停、
  触摸滑动，并且有 9 条测试。重写是纯粹的重复实现（违反原则 III）。
- **单条 banner 时也走轮播组件**：会渲染出无意义的圆点与箭头。FR-081 要求单条时**不出现**轮播控件，
  所以要么条件渲染组件，要么在组件内按 `count<=1` 隐藏控件。

## R7 —— 评价的可见性：保持"先审后显"，不改服务端

**决定**：维持既有行为 —— 会员提交的评价**默认不可见**，须运营在后台点"显示"才出现在前台。
前端**不改**这一点，只在提交成功的提示里**明说**（FR-078）。

**理由**：
- 事实核查：会员路径的转换器（`ProductCommentConvert.convert(createReqDTO, ...)`）
  **没有调用 `setVisible(...)`**，而 `ProductCommentCreateReqDTO` 里也没有这个字段 →
  落库时取数据库默认值（**隐藏**）。而 C 端读取接口只返回 `visible = true` 的行。
  （对照：管理端的转换器是显式 `.setVisible(true)` 的。）
- 所有者已决策保持（Q8）：内容可控、零服务端改动。代价由文案承担。
- 这条**必须写进契约与手工清单** —— 否则它会被当成"评价功能坏了"，
  用户重复提交后还会撞上"订单已评价"的拒绝，体验更差。

**被否决的方案**：
- **改为提交后即可见**：要动服务端逻辑（给可见标记一个默认值），超出本期"只消费既有接口"的边界，
  且等于放弃内容审核。所有者已明确不选。
- **前端提交后自行"本地插入"一条假评价**：那是编造内容，且刷新即消失，比不做更糟。

## R8 —— 评价入口放哪

**决定**：
- **订单详情页**：对**订单项**给入口（"评价"按钮），放在既有的 `.od-sale-actions` 那一块
  （即"申请退款/撤销申请"所在的容器），沿用 `:data-item="it.id"` + `openXxx(it)` 的既有模式。
- **订单列表页**：对**订单**给入口（"去评价"，跳详情），与既有的"立即支付"同处 `.oc-foot`。

**理由**：
- 后端**按订单项**提交评价（`orderItemId` 必填），所以订单详情那颗按钮的粒度是订单项。
- 但后端的**前置条件是订单级**的：`order.status === COMPLETED` 且 `order.commentStatus === false`。
  订单项自己的 `commentStatus` **后端不校验**（重复提交由 product 层的 `COMMENT_ORDER_EXISTS` 挡）。
  → 所以前端的可见性判定要**同时**看订单状态与**该项**的 `commentStatus`，否则会出现
  "点了必然被拒"的按钮（违反 FR-073）。
- 订单列表页给**订单级**入口是因为列表页拿不到可靠的"哪一项待评价"上下文（拿得到，
  但列表页放逐项按钮会让卡片过长）；跳详情再选具体项，与上游 uniapp 的做法一致。
- **放置位置有讲究**：订单详情里 `.od-item` 是四列 grid，既有注释明确警告**不要往 grid 里加直接子元素**
  会撑坏布局 —— 所以评价按钮要跟在 `.od-sale-actions` 里面（那里已经是安全位置）。

**被否决的方案**：
- **订单列表页逐项给按钮**：卡片会变很长，且列表页的 items 未必带全字段。
- **只做一个独立的"待评价"页**：要额外做一个列表页与分页，而订单页已经有全部上下文。
- **入口只放订单详情**：用户在列表页看不到"还有东西没评"，会漏掉。

## R9 —— 校验归属：前端补齐，同时写进契约

**决定**：前端实现评分范围（1~5）、内容非空且 ≤1024、图片 ≤9 张的**提交前校验**；
并把这三条**写进 [contracts/app-api.md](./contracts/app-api.md)**，标注为"前端承担、后端当前不校验"。

**理由**：
- 事实核查：后端创建评价的请求 VO 里，两个评分字段**没有 `@Min/@Max`**，内容字段**没有 `@Size`**
  （"1-5"只写在文档注释里）。真正兜底的是数据库列宽（`content varchar(1024)`）。
- 也就是说：**不补前端校验，就会出现"前端放行、后端落库报错"** —— 用户看到的是数据库层的错误，
  而不是"评分请选 1-5 星"。这直接违反 FR-075 / SC-028。
- 契约里必须写明**是前端承担的**，不能写成"后端会校验" —— 那是对既有后端行为的错误承诺，
  正是宪法原则 II 点名的那类返工成因。

**被否决的方案**：
- **给后端请求 VO 加校验注解**：这是更"正确"的修法，但它是改服务端、且改动会作用于
  **所有客户**（含 uniapp），超出本期范围。已记录为**将来可做**，本期不做。
- **不写进契约**：下一个改这块的人会以为后端已经挡住了。

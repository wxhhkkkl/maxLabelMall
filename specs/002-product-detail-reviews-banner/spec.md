# Feature Specification: 商品详情、评价（展示与撰写）与商城页 banner

**Feature Branch**: `002-product-detail-reviews-banner`
**Created**: 2026-10-10
**Status**: Draft
**Input**: User description: "现在产品详情页，没有产品详情展示；没有用户的评价展示； 商城页的banner也没显示"

> **编号延续 001**：本仓库的 FR / SC / US / Q 是**全仓唯一**的命名空间（代码注释里直接引
> `FR-005c`、`SC-020`），所以本规格从 **FR-063 / SC-025 / US9 / Q5** 接着往下排。

## 背景与现状

所有者报告三处"看不到内容"。核查后，**三件事的性质完全不同** —— 这决定了它们各自该怎么做：

**① 商品详情展示** —— 链路是通的，**被前端自己吞掉了**。
`product_spu.description`（商品详情富文本）从数据库列、后端实体、到详情接口的返回体、前端类型、
渲染块，**一路都在**，后端也确实返回了存量内容。断点在详情区块的显示判断上：它把清洗后的富文本
**剥掉标签取纯文本**，纯文本为空就整块隐藏。于是**只有图片、没有文字的详情（电商里是常态）
被判成"没有详情"**。存量数据里已有多件商品正是纯图片详情，另有若干件详情为 NULL。

**② 用户评价展示与撰写** —— 后端**能力完整、前端零接入**。
`product_comment` 表、C 端只读接口 `/app-api/product/comment/page`（无需登录即可读）都现成。
**撰写链路也在**：`POST /app-api/trade/order/item/create-comment`（需登录），要求订单属于本人、
订单已完成、且该订单尚未整体评价过；另有"超期未评价则自动评"的定时任务。图片上传能力在个人中心
那一轮已经做出来了，是通用的，可直接复用。但 `storefront/` 里**没有任何一处**提到评价。

**③ 商城页 banner** —— 三样东西都缺：**页面没画、数据没有、位置也没有**。
- 商城页（商品列表页）模板里根本没有 banner 元素，也没有任何 banner 接口调用；
- 后端 `GET /app-api/promotion/banner/list` 有、且无需登录，但要求**必传"位置"**；
- 位置是**字典驱动**的（`promotion_banner_position`），现有取值只有
  「首页 / 秒杀 / 砍价 / 限时折扣 / 满减送」—— **没有"商城页"**；
- 库里该表只有 1 条种子数据，既不属于线上租户、位置也对不上。
- **但版式是现成的**：样式表里 `.mall-banner` / `.mbn-*` 那一套（含轮播圆点与箭头）已经写好，
  只是没有任何页面用它；轮播组件也只有它自己的测试在引用。**缺的只是接线。**

## Clarifications

### Session 2026-10-10

- **Q5 评价范围 → 含撰写。** 本期不只展示，还包含"订单完成后去评价"的完整入口与表单。
- **Q6 评价数据 → 接受空态。** 线上暂无评价；**不导入、不伪造**。前端做完后详情页显示
  "暂无评价"——这是**正确**的表现，不是缺陷。
- **Q7 商城页 banner 的来源 → 复用后台既有的 Banner 管理页。**
  该页面对应的正是这个接口读的那张表，**不需要新的后台页面**。但它「位置」是单选且由字典驱动，
  现有选项里没有"商城页"，故需新增一个位置取值（详见 FR-080 与 Q7 说明）。
- **Q8 评价的可见性 → 保持"先审后显"，但提交后必须明说。** 会员提交的评价默认不可见
  （数据库默认隐藏，C 端接口只返回可见的），**维持这个既有行为不改服务端**；代价是用户写完
  自己看不到，所以**提交成功的提示里必须讲清楚"审核通过后展示"**，不能让用户以为没提交上。

## User Scenarios & Testing *(mandatory)*

### User Story 9 - 商品详情真的能看到详情 (Priority: P1)

消费者打开某件商品的详情页，想看清楚这东西到底是什么样 —— 详情是商家放的长图、参数表或图文说明。
现在他往下滚，什么都没有，只能看到一个空页面，于是他退出去问客服。

**Why this priority**: 这是三件里**唯一一个"内容本来就在、只是没显示出来"**的问题 —— 修好它不需要
新增任何数据，存量商品的详情立刻可见。而且详情是成交前最关键的决策依据，缺了它商品页只剩价格。

**Independent Test**: 挑一件后台已录详情、且详情**只有图片**的商品，打开详情页应能看到那部分内容；
再挑一件确实没录详情的，应**不出现**任何空白区块或占位文案。

**Acceptance Scenarios**:

1. **Given** 一件商品录入了**纯图片**的详情，**When** 消费者打开它的详情页，
   **Then** 详情内容正常展示，且不出现"暂无详情"之类的占位文案。
2. **Given** 一件商品**没有录入**详情（空值），**When** 打开详情页，**Then** 详情区块整体不渲染，
   **不出现空白块、不出现占位文案**，页面其余部分布局不受影响。
3. **Given** 详情里含有被安全清洗规则移除的内容，**When** 清洗后仍有可见内容（文字**或图片**），
   **Then** 详情依然展示；**只有**清洗后确实什么都不剩时才不展示。
4. **Given** 详情里含有图片、表格等非文字内容，**When** 打开详情页，
   **Then** 这些内容与文字同等对待 —— **不得因为没有文字就判定为"无详情"**。

### User Story 10 - 买之前能看别人怎么说 (Priority: P2)

消费者在犹豫要不要下单，想看看买过的人怎么评价 —— 评分高低、有没有实物图、商家有没有回复。
现在详情页完全没有评价区，他只能自己猜。

**Why this priority**: 评价是转化率的第二支撑（仅次于详情）。后端读取能力已完备，
属于**纯展示层接入**，不动服务端。

**Independent Test**: 打开一件**有可见评价**的商品，详情页应能看到评价（含昵称/评分/内容/时间，
有图的能看到图）；打开一件**没有评价**的商品，应看到明确的空态说明而不是一片空白。

**Acceptance Scenarios**:

1. **Given** 某商品有若干条可见评价，**When** 打开详情页，**Then** 能看到最近的若干条评价，
   每条含：评价人昵称、评分、评价内容、评价时间；有评价图片的显示图片；有商家回复的显示回复。
2. **Given** 某商品没有任何评价，**When** 打开详情页，**Then** 显示明确的"暂无评价"说明，
   **不得**显示空白区域，**不得**编造评价内容。
3. **Given** 某商品的评价数超过详情页展示的条数，**When** 消费者想看全部，
   **Then** 有明确入口能查看该商品的全部评价。
4. **Given** 某条评价被后端判定为不可见（被隐藏），**When** 打开详情页，
   **Then** 该条评价**不出现**在页面上。
5. **Given** 评价是匿名提交的，**When** 展示该条评价，
   **Then** 昵称按后端给出的值原样展示（前端不自行改写、也不反向还原真实身份）。

### User Story 11 - 买完能说两句 (Priority: P3)

消费者收到货、订单完成，想给个评价 —— 打分、写两句、愿意的话传几张实物图。
现在他在订单页找不到任何评价入口，只能不了了之。

**Why this priority**: 它是评价数据的**唯一来源** —— 没有它，US10 永远只有空态。
但它依赖订单状态流转，且**提交后能否立刻看见还存在一个待定的前置问题**（见 Q8），
所以排在展示之后。

**Independent Test**: 对一笔**已完成**且**未评价过**的订单，订单页应有评价入口；
填完提交应成功，并且该订单不再显示待评价。订单**未完成**时**不得**出现该入口。

**Acceptance Scenarios**:

1. **Given** 一笔已完成且未评价的订单，**When** 消费者打开订单页，
   **Then** 有明确的评价入口，并能看出订单里有商品待评价。
2. **Given** 某订单**尚未完成**（未发货/已发货未完成），**When** 打开订单页，
   **Then** **没有**评价入口（后端会拒绝，前端不该先给一个必然失败的按钮）。
3. **Given** 消费者进入评价表单，**When** 提交，
   **Then** 可填写：商品质量评分、服务态度评分、评价内容、评价图片（选填）、匿名与否；
   必填项为空或未打分时**不得提交**，并给出明确提示。
4. **Given** 消费者提交成功，**When** 回到订单页，**Then** 该订单不再显示待评价。
5. **Given** 提交失败（例如后端判定该订单已评价过、或订单状态不满足），
   **When** 提交，**Then** 把后端的原话透给用户，**不得**静默失败。
6. **Given** 消费者选了"匿名"，**When** 该评价被展示，**Then** 不暴露其真实昵称与头像。

### User Story 12 - 商城页有 banner (Priority: P4)

消费者点进"商城"（商品列表页），希望顶部有个能点进去的活动入口或主推位。
现在打开就直接是分类树和商品网格，顶部一片空白。

**Why this priority**: 三件里唯一需要**先定下"这个位置叫什么"**、并且**运营还得去后台录内容**
才看得见效果的一件，外部依赖最多，所以排最后。

**Independent Test**: 打开商城页顶部应能看到运营配置的 banner，点击能按配置跳转；
该位置没配任何 banner 时，页面**不应**出现空白占位，商品列表照常从顶部开始。

**Acceptance Scenarios**:

1. **Given** 运营在该位置配置了 banner，**When** 打开商城页，**Then** 顶部展示这些 banner，
   按运营设定的顺序呈现。
2. **Given** 配置了**多条**，**When** 打开商城页，**Then** 可以轮播；
   **Given** 只有**一条**，**Then** 展示但不出现轮播控件。
3. **Given** 该位置**没有**配置，**When** 打开商城页，
   **Then** 不渲染 banner 区域，**不出现空白占位**，商品列表布局不上移塌陷。
4. **Given** 某条 banner 配了跳转链接，**When** 点击，**Then** 跳到该链接；**Given** 没配链接，
   **Then** 点击不产生跳转（也不报错）。
5. **Given** 在窄屏下浏览，**When** 打开商城页，**Then** banner 不变形、不遮挡分类树与商品网格。

---

### Edge Cases

- **详情内容为空白字符串 / 全空白字符**：视同"没有详情"，不渲染区块。
- **详情内容只有不可见的空标签**（如一连串空 `<div>`）：清洗后若无任何可见内容则不渲染。
- **详情内容被清洗规则整体移除**（如只含被禁用的标签）：不渲染区块，**不得**渲染出空白框。
- **评价只有评分没有文字内容**：仍然展示该条（评分本身是有效信息）。
- **评价内容很长**：详情页上的摘要不得把页面撑爆 —— 需有截断或折叠策略，且查看全部时能看到完整内容。
- **评价图片加载失败 / 链接失效**：不得整块评价区崩掉。
- **同一商品的评价全部不可见**：等同"没有评价"，走空态。
- **撰写评价时图片上传失败**：不得丢掉已填写的评分与文字；要能重试。
- **撰写评价时上传超过 9 张图**：前端应拦在提交前并说明原因，不是提交后被后端拒。
- **两个标签页同时对同一订单项提交评价**：后端会拒其中一个，前端要把原因说清楚（不是崩溃）。
- **刚提交的评价立刻去看却看不到**：这是**设计如此**（Q8）。所以提交成功的那一刻就必须说清楚
  "审核通过后展示"，否则用户会以为提交失败或功能坏了，然后再提交一次。
- **商城页 banner 图片加载失败**：不得把商品列表挤下去或留下空白大块。
- **banner 与首页现有 banner 同时存在**：两者互不覆盖、互不串位。
- **"三无"叠加**（无详情、无评价、无 banner 同时出现在一个页面）：页面不得出现任何空白块或
  占位文案，也不得布局错位。

## Requirements *(mandatory)*

### Functional Requirements

**商品详情（US9）**

- **FR-063**: 商品详情页 MUST 展示商品详情的富文本内容，包括其中的图片、表格等非文字内容。
- **FR-064**: 详情内容 MUST 经既有安全清洗后再展示；**判定"有没有详情"时，非文字内容（图片、表格）
  MUST 与文字同等计为"有内容"** —— 不得因为一段详情里没有纯文字就不展示它。
- **FR-065**: 仅当详情**未录入**、或清洗后**确实没有任何可见内容**时，MUST 不渲染详情区块。
- **FR-066**: 详情区块不渲染时，页面 MUST NOT 出现空白占位、边框、占位文案或布局错位。

**评价展示（US10）**

- **FR-067**: 商品详情页 MUST 展示该商品的用户评价列表。
- **FR-068**: 每条评价 MUST 展示：评价人昵称、评分、评价内容、评价时间；有图片的展示图片；
  有商家回复的，该回复 MUST **显示在同一条评价之内**并带回复时间，
  MUST NOT 渲染成与用户评价并列的另一条。
- **FR-069**: 商品**没有评价**时，MUST 展示明确的空态说明；MUST NOT 展示空白区域，
  MUST NOT 编造或占位任何评价内容。
- **FR-070**: 展示的评价 MUST 只包含被判定为可见的评价；不可见的 MUST NOT 出现在页面上。
- **FR-071**: 评价数多于详情页展示条数时，MUST 提供查看全部评价的入口。
- **FR-072**: 详情页上的评价内容超过 **120 个字符**时 MUST 折叠（默认收起、可展开）；
  「全部评价」页 MUST 展示完整内容、不折叠。
  **该阈值是展示口径，与输入上限 1024 无关。**

**评价撰写（US11）**

- **FR-073**: 订单**已完成**且**尚未评价**时，订单相关页面 MUST 提供评价入口，并能看出哪些商品待评价；
  订单不满足条件时 MUST NOT 提供该入口。
- **FR-074**: 评价表单 MUST 支持：商品质量评分、服务态度评分、评价内容、评价图片（选填）、
  匿名与否。两个评分均必填，且 MUST 是 **1~5** 的整数（默认 5）；内容必填、去空白后非空、
  且 MUST 不超过 **1024** 个字符（与数据库列宽一致）。
  ⚠️ 这两条**后端当前不校验**、由前端承担 —— 见 [research.md](./research.md) R9
  与 [contracts/app-api.md](./contracts/app-api.md) §3.2。
- **FR-075**: FR-074 / FR-076 的约束 MUST **在发出请求之前**校验；不通过时 MUST NOT 发请求，
  并**指出是哪一个字段**不合格。
- **FR-076**: 图片上传 MUST 复用既有的通用上传能力；单次最多 9 张。上传失败 MUST NOT 丢掉
  已填写的评分与文字，且 MUST 可重试。
- **FR-077**: 提交失败时 MUST 把**后端返回的原因原样**展示（例如"创建交易订单项的评价失败，
  订单不是【已完成】状态"），MUST NOT 静默失败、MUST NOT 吞错、
  MUST NOT 用前端自造的通用文案（如"提交失败，请重试"）替换掉它。
- **FR-078**: 提交成功后，订单页 MUST 不再显示该订单的待评价入口；
  **并且 MUST 在成功提示里明确告知评价需要审核通过后才展示** ——
  评价默认不可见是既有行为（Q8），不明说会让用户以为没提交上而重复提交。
- **FR-079**: 选择匿名时，展示出去的评价 MUST NOT 暴露真实昵称与头像。

**商城页 banner（US12）**

- **FR-080**: 商城页（商品列表页）MUST 在商品列表上方展示运营配置的 banner。banner 的**内容来源
  MUST 是后台既有的 Banner 管理页**（对应 `promotion_banner` 表），
  **MUST NOT 采用前端写死内容**。因为该页面的「位置」选项由字典驱动、且后端对位置做强校验，
  本项 MUST 新增一个**独立的「商城页」位置取值**，MUST NOT 复用「首页」位置
  （复用会让两处被迫共用同一批内容，且未来首页若接入同一接口就会串位）。
- **FR-081**: 配置了多条 banner 时 MUST 支持轮播；只有一条时 MUST NOT 出现轮播控件。
- **FR-082**: 该位置没有配置 banner 时，MUST NOT 渲染 banner 区域，MUST NOT 出现空白占位，
  商品列表 MUST NOT 因此错位。
- **FR-083**: banner 配了跳转链接时点击 MUST 跳转；未配链接时点击 MUST NOT 跳转、MUST NOT 报错。
- **FR-084**: 商城页 banner MUST NOT 影响首页现有 banner，两者互不覆盖。

**共性**

- **FR-085**: 上述改动 MUST 只消费既有的 C 端接口，**不得**为展示而新增或改造服务端接口 ——
  唯一例外是 FR-080 新增 banner 位置取值（仅限位置定义本身）。
- **FR-086**: 三处新增的展示区域 MUST 通过既有的视觉一致性可执行断言（色板与三个断点）。
- **FR-087**: 页面 MUST NOT 出现"空白块 / 占位文案 / 编造内容"这三类静默缺陷中的任何一种 ——
  凡是"没有内容"，一律要么不渲染、要么明说"暂无"。

### Key Entities

- **商品详情内容**：商品上的一段可录入的富文本，可含文字、图片、表格；未录入时为空。
  本次只**展示**既有内容，不新增录入能力。
- **商品评价**：一条由购买过的用户提交（或系统超期自动生成）的评价，含评价人昵称、匿名标记、
  评分（两个维度）、内容、图片、商家回复、时间，以及一个"是否可见"的标记。
  与商品、订单项相关联。本次**既读取展示、也新增撰写**。
- **待评价的订单项**：订单项上有一个"是否已评价"的标记，订单层面还有一个汇总标记。
  这两个标记决定了评价入口出不出现。
- **商城 banner**：一条运营配置的推广位，含标题、图片、跳转链接、排序、启用状态、
  以及它所属的**展示位置**。位置由字典维护、并由后端强校验取值。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-025**: 对线上**已录入详情**的商品抽样核查，详情内容可见率 **100%** ——
  含"详情只有图片、没有文字"的商品（这是当前失败的整类）。
- **SC-026**: 对线上**已有可见评价**的商品，详情页能看到评价；对**没有评价**的商品，
  显示明确的空态。两类商品的页面上都**不出现空白区块**。
- **SC-027**: 对一笔**已完成且未评价**的订单，用户可以从订单页走到评价表单并提交成功；
  提交后该订单**不再**显示待评价。对**未完成**的订单，**不出现**评价入口。
- **SC-028**: 撰写评价的各项校验（必填、评分范围、图片张数上限）在**提交前**生效，
  不产生注定被后端拒绝的请求；后端拒绝时用户能看到**后端原话**。
- **SC-029**: 商城页在**有 banner** 与**无 banner** 两种数据下均正常：有则顶部可见 banner
  且可轮播/可跳转，无则商品列表从顶部正常开始、无空白占位。
- **SC-030**: 全站**没有一件**商品、**没有一个**页面会出现"空白块 / 占位文案 / 编造内容"这三类缺陷 ——
  抽查 10 件商品（含无详情、无评价、仅有图片详情三类）与商城页有/无 banner 两种状态，均符合。
- **SC-031**: 三处改动在 **1100 / 768 / 480** 三个断点下均不破坏既有布局
  （由既有视觉一致性断言自动覆盖）。

## Assumptions

- **评价本期不包含"商家回复"的撰写**。回复仍由运营在既有后台完成，C 端只展示。
- **评价内容长度上限**以后端数据库约束为准（当前为 1024 字符）；**后端不校验长度这一点需要在前端
  补上并写进契约**，否则会出现"前端放行、后端落库报错"。
- **评价图片上限 9 张**，与后端既有约束一致；不额外收紧。
- **评价采用"先审后显"**（Q8）：用户提交后，需运营在既有后台的「商品评价」页点"显示"，
  才会出现在前台。这是既有行为，**本次不改服务端**；前端负责把这件事**说清楚**（FR-078），
  否则用户会以为没提交上。运营侧不需要新功能 —— 后台那个列表本来就能看到并操作可见性。
- **不为展示效果造数据**。不导入、不伪造评价（Q6）。线上暂无评价时，空态是**正确**的表现。
- **首页现有 banner 维持现状**（它是一个写死的静态首屏，不读接口）。本次只做商城页，不动首页。
- **不新增商品详情的录入能力**。运营在既有后台录详情，本次只保证录了什么就能看到什么。
- **banner 位置新增「商城页」需要一次生产库的字典数据插入**，属运营/发布动作，不由前端代码完成。
- **遵守项目宪法**：不引入 UI 组件库；C 端只走 `/app-api`；测试先行不可协商。
- 详情富文本的既有安全清洗规则**保持不变** —— 本次只改"判定有没有内容"的口径，
  不放松清洗（那是安全边界，不为显示效果让步）。

## 落地决策

| Q | 决策点 | 结论 | 影响与理由 |
|---|--------|------|-----------|
| Q5 | 评价的**范围** | **含撰写**（所有者 2026-10-10 定） | 后端读取与撰写接口都已具备，所以这是范围选择而非能力有无。写评价是评价数据的**唯一来源** —— 没有它，展示侧永远只有空态 |
| Q6 | 评价**数据从哪来** | **接受空态，不造数据**（所有者 2026-10-10 定） | 不导入、不伪造评价。前端做完后详情页显示"暂无评价"，这是正确表现。数据将随 Q5 的撰写功能自然长出来 |
| Q7 | 商城页 banner 的**位置** | **新增一个独立的「商城页」位置**（按建议采用；若要改回"复用首页位置"，改这一行即可） | 所有者问"能否复用后台那个 Banner 管理页"——**能，而且就该用它**：它就是 `promotion_banner` 表的维护入口，正是这个接口的数据源，**不需要任何新的后台页面**。但它的「位置」是**字典驱动的单选**（`promotion_banner_position`），现有取值只有「首页 / 秒杀 / 砍价 / 限时折扣 / 满减送」，**没有"商城页"**；且后端对位置做**强校验**，塞一个字典里没有的值会被直接拒绝。所以要么给这个位置新增一个取值（改动很小：后端枚举加一项 + 插一行字典 + 生产库执行一次；**管理端前端零改动**，因为它完全靠字典渲染），要么把商城页的 banner 挂在「首页」位置上。**选新增而不是复用首页位置**的理由：复用会让两处被迫共用同一批内容；虽然首页目前是写死的静态首屏、**不读这个接口**（所以眼下不会真串位），但那是**埋雷** —— 哪天首页接上接口就会一起变。新增取值的成本明显低于这个隐患 |
| Q8 | 刚写的评价**能不能立刻看见** | **保持"先审后显"，不改服务端；但提交成功时必须明说**（所有者 2026-10-10 定） | ⚠️ **核查中发现的事实**：会员提交的评价，其"是否可见"标记**没有被设置**，数据库默认值是**隐藏**；而 C 端读取接口**只返回可见的评价**。也就是说 —— **用户刚写完的评价，自己去商品详情页看是看不到的**，必须在后台被点过"显示"才会出现。这不是本次引入的，是上游既有行为。所有者选择**保持这个行为**（内容可控、零服务端改动），代价由文案承担：FR-078 要求提交成功的提示里说明"审核通过后展示"。**若将来改成"提交后即可见"，那要动服务端，需重新决策** |

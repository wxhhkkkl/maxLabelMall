# app-api 契约（003）

C 端（`storefront/`）本期消费与改动的接口。所有路径以 `/app-api` 为前缀，**只走 `/app-api`**。

> 本文只记本次真正会调用/改动的部分，不重复 001 / 002 已覆盖的接口。

---

## 1. 商品分页 —— **改动：新增一个可选参数**

`GET /product/spu/page`

| 参数 | 必填 | 本期 | 说明 |
|---|---|---|---|
| `pageNo` / `pageSize` | ❌ | 既有 | |
| `categoryId` | ❌ | 既有 | 后端**已**展开为该分类及其子分类（既有行为，不改） |
| `keyword` | ❌ | 既有 | 只匹配商品名 |
| `sortField` / `sortAsc` | ❌ | 既有 | 白名单仍是 `price` / `salesCount`（**不改**） |
| **`filterValueIds`** | ❌ | **新增** | **值 id 的扁平数组**，逗号分隔：`3,7,11` |

- **不传 = 既有行为，逐字不变。** 这是本接口唯一的兼容性承诺，MUST 由测试钉住。
- 传了 → 服务端按值的 `dimension_id` **自行归组**；**每个维度至多一个值**（Q9=B 单选），
  服务端为每个值追加一条**等值** `EXISTS`，**跨维度是 AND**（FR-101）。
  前端 MUST NOT 按维度拆参数名（R9）。
- **同一维度传入多个值是非法请求** —— 服务端 MUST 以明确的业务异常拒绝，
  MUST NOT 静默取其中一个（否则前端的单选 bug 会表现为「筛选结果莫名其妙」，无从排查）。
- 空数组等价于不传。
- 无需登录（`@PermitAll`，与既有三个 app 商品接口一致）。

⚠️ **前端序列化的具体形态**（本项目吃过"单测只断言 UI、不断言请求体"的亏，这条要测）：
既有 `toPageParams()` 对数组用的是 `.join(',')`（见 `api/product.ts` 的 `categoryIds`），
`filterValueIds` **沿用同一形态**，MUST 有单测钉住。

## 2. 筛选维度列表 —— **新增**

`GET /product/filter/dimension-list`

| 参数 | 必填 | 说明 |
|---|---|---|
| `categoryId` | ✅ | 当前浏览的分类；服务端取 `scopeOf(categoryId)` 上的维度 |

**只有一个参数** —— 这是 Q11=A 的直接结果：选项集合只由配置决定，
**不需要也不接受** `keyword` / `filterValueIds`（R6 / R7）。

**返回**

```jsonc
{
  "code": 0,
  "data": [
    {
      "dimensionId": 12,
      "dimensionName": "宽度",
      "sort": 1,
      "values": [
        { "valueId": 3, "name": "40", "sort": 1 },
        { "valueId": 4, "name": "50", "sort": 2 }
      ]
    }
  ]
}
```

**契约承诺**

1. **没有任何计数字段。** 选项集合**不随关键词、已选值、实际商品数变化**（FR-111 / Q11=A）。
   某个值当前一件商品都没有，**照样在这里返回**，点选后由前端走空态。
2. `values` **为空数组的维度不出现在返回里**（FR-090）——**不是**返回一个空 `values`。
3. 整个列表为空数组时，前端整块不渲染筛选条（FR-104）。
4. **`sort` 是展示顺序的唯一依据**（FR-112）。接口**不承诺返回数组的顺序**，
   前端 MUST 按 `sort` 自行排序。
5. **该接口只依赖 `categoryId`**，因此前端在同一个分类内**只需请求一次**（切换分类才重取）——
   这是 Q11=A 带来的简化，若将来加了计数就不成立了（R7）。

**失败语义（FR-106）**：该接口失败 **MUST NOT** 影响商品列表 ——
前端应让筛选条**整块不渲染**并允许重试，商品列表照常显示（沿用 002 R1 对评价区的处理方式）。

## 3. 前台不消费、但服务端必须保证的行为

以下不是接口，是**服务端行为**，但它们直接决定前台看到什么，故写进契约：

| # | 行为 | 依据 |
|---|---|---|
| 1 | 值被删除后，`filterValueIds` 里若仍带着它 → **忽略该 id**，不报错、不返回空 | 顾客可能停在旧页面上（FR-105 的边界） |
| 2 | 值改名后，**按 id 匹配仍然成立** —— 已选条件不被打断 | SC-038 |
| 3 | 维度/值被删除或改名，**不需要发版**，前台立即反映 | SC-032 |

---

## 4. 显式不在本期契约内

- ❌ **不新增** `/product/spu/page` 之外的任何**筛选结果**接口（结果仍走既有分页）。
- ❌ **不做聚合计数**：不返回"每个可选值下有多少商品"，也不按当前条件收敛选项（Q11=A / R6）。
  将来若要加，先看 [research.md](../research.md) R6 记的那个陷阱。
- ❌ **不返回**商品身上挂了哪些筛选值（详情页不展示维度，见 spec 的 Assumptions）。
- ❌ **不做**按维度的独立商品列表页（如 `/product/filter/:valueId`）。
- ❌ **不改**既有排序白名单、关键词匹配范围、分类展开逻辑。

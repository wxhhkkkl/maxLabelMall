| # | 事项 | 漏了的后果 |

## 1. 运营侧：从零把「碳带」配出来（US13 / US14）

**这是本特性最重要的一条人肉走查，因为它同时验证了"能不能配"和"配起来有多累"。**

1. 后台 → 商品分类 → 找到「碳带」→ 点「筛选维度」
2. 新建维度「宽度」，在其下建 40 / 50 / 60 / 70 / 80 / 90 / 100 / 110 八个值
3. 新建维度「长度」，建 300m / 70m
4. 新建维度「轴心」，建运营认为该有的档位
   ⚠️ **档位由运营定，不得照抄参考图的「1英寸 / 半英寸」** —— 现有数据里根本没有这两种写法
   （现在是「110mm轴」「小轴」，见 spec 背景②）。这是**业务事实，不得编造**。
5. 切到子分类「蜡基」→ 点「筛选维度」
   ✅ **应看到步骤 2~4 的三组维度，标注为继承自「碳带」，且不需要重配**（Q10=B / FR-110）
6. 打开一件碳带商品 → 在筛选标签子表单里勾选若干值 → 保存 → 重新打开
   ✅ 勾选状态保持

### 1.1 顺带记录**实际耗时**

碳带 54 件商品 × 3 个维度 ≈ **162 次勾选**。走查时**记下真实耗时**：
- 若在可接受范围内 → R12 的"不预填"决策成立；
- 若运营明确表示无法承受 → 触发 R12 里记的备选方案（预填脚本 + 运营逐条复核），**单独立项**。

## 2. 前台：筛选条（US15）

在**已按 §1 配好**的「蜡基」分类页上：

| # | 操作 | 期望 |
|---|---|---|
| 1 | 进入「蜡基」 | 商品列表上方出现「宽度」「长度」「轴心」三行，行首「全部」 |
| 2 | 点「宽度 = 110」 | 列表只剩挂了 110 的商品；「全部」可恢复 |
| 3 | **已选「宽度 = 110」，再点「宽度 = 100」** | **「110」高亮消失、「100」高亮（单选替换，Q9=B）**，结果是 100 的商品 —— **不需要先点「全部」取消** |
| 4 | 再点「长度 = 300m」 | 结果收窄为「宽度 ∈ {110,100} **且** 长度 = 300m」 |
| 5 | 输入一个能搜到结果的关键词 | 关键词与维度条件**同时**生效 |
| 6 | 输入一个搜不到的关键词 | 空态（明说没有商品）；**筛选条整块仍在**，刚选的「110」仍可点，逐行点「全部」可依次取消；**页面上没有**「清除筛选」按钮（FR-105 / FR-113 / FR-114） |
| 7 | 翻到第 2 页 | 仍是筛选后的商品（**不是**先筛当前页）—— FR-100 |
| 8 | 从「蜡基」切到「混合基」 | 若两者都继承同一维度 → **选择保留**；切到「打印机」→ 选择**重置**（FR-103） |
| 9 | 进入一个**没配任何维度**的分类（含其祖先也没配） | **不出现**筛选条区域，**不留空白块**，列表从上方正常开始（FR-104） |
| 10 | 找**一个挂得很少的值**（例如只有 1 件商品的「轴心」档位），点它 | 有结果；再看一个**没有任何商品挂的值** —— 它**照样在筛选条上**，点它得到空态（操作同上）而不是选项消失（Q11=A） |

### 2.1 关键的一条验证：选项集合必须**纹丝不动**

Q11=A 之下，**同一个分类页上的选项集合是稳定的**。这是全特性最容易"实现着实现着就跑偏"的一条
（很容易顺手做成"没结果就不显示"）。

做法：进入「蜡基」后**把筛选条上所有选项抄下来**（或截图），然后：

1. 点「宽度 = 110」→ 再看筛选条 —— **逐字相同**
2. 再叠加一个搜不到的关键词（结果归零）→ 再看筛选条 —— **仍然逐字相同**

任何一次出现"某个选项不见了"，就是违反 FR-111 / Q11=A。

## 3. 三个断点

在 **1100 / 768 / 480** 三档宽度下走一遍 §2 的 1、3、6 三步：
筛选条不撑破版式、不把商品列表挤出首屏、长值名（如「1英寸（25.4毫米）」）不换行错位。
（色板与断点的自动化断言由 `design-consistency.spec.ts` 覆盖，这里看的是**观感**。）

**再验一次失败路径**（Q14 / FR-115）：在开发工具里把商品列表接口改成返回 500（或直接断网），
点一个值 —— 高亮 MUST **退回**到点击前，同时出现可重试的提示；
**不得**停在「新值高亮着、列表还是旧的」。

**480 下额外确认两条**（Q13）：
1. **页面本身不出现横向滚动条** —— 该滑的是「宽度」那一行**内部**的值区，不是整个页面。
2. 把「宽度」的 8 个值用上（它是现有数据里最长的一行）：筛选条仍是 **4 行**，
   没有因为值多而折行变高。行首的「全部」始终在，不会被滑走。

## 4. 后台的破坏性操作（FR-092 / FR-097）

| # | 操作 | 期望 |
|---|---|---|
| 1 | 删一个**已被商品引用**的值 | 弹窗显示被多少商品使用；确认后删除，那些商品上的该标签**一并消失**，且**前台不再出现该选项** |
| 2 | 把一件碳带商品**改到另一个分类** | 保存后重开该商品：原有的碳带标签**已被移除**（R11）；后台有"已移除 N 个"之类的可见反馈 |
| 3 | 在「蜡基」下新建一个与「碳带」**同名**的维度 | **被拒绝**，且错误信息指明"与分类「碳带」下的「宽度」重名"（FR-091） |
| 4 | 改一个值的**名称** | 前台立即显示新名；**已选中该值的顾客的筛选条件不被打断**（按 id 匹配）—— SC-038 |

## 5. 显式不验证的项（宪法原则 V 要求写明）

| 项 | 为什么不验证 |
|---|---|
| **并发**（两个运营同时改同一分类的维度、同一商品被同时改分类） | 沿用既有后台行为，本次不做并发控制（spec 的 Edge Cases 已写明）。不写自动化也不手工构造 |
| **聚合计数 / 选项收敛** | Q11=A 已改成"选项照常展示"，服务端**不做计数**（R6）—— 没有这个功能可验 |
| **筛选查询的性能** | 全站 282 件商品、碳带 54 件，任何写法都够快。**不在本期建立性能基线**；等商品量上千再谈 |
| **小程序 / App 端（`yudao-ui-mall-uniapp`）** | 本期范围外（spec 的 Assumptions）。该端不同步改造 |
| **维度/值的启用停用** | 本期只有"存在/删除"两态，没有这个功能可验 |
| **商品详情页显示筛选标签** | 本期不做（spec 的 Assumptions） |
| **筛选条件的 URL 同步 / 分享 / 刷新后保持** | **本期不做**。切分类与刷新都会重置维度选择。若将来要做，是一个独立的增量 |
| **管理端的视觉与交互观感** | 管理端在本特性里**首次接入了 Vitest**（T246/T247），但只覆盖**新增的纯函数与一个子表单**（T261/T274/T282）。抽屉与子表单的**观感、间距、与既有 element-plus 表单的一致性**仍靠 §1/§4 人工核对 —— 自动化只保证"逻辑对不对"，不保证"好不好看" |

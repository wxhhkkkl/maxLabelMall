# 技术决策与研究（003）

Phase 0 产出。每条记：**决策 / 依据（查过代码，不是推测）/ 被否决的方案**。

## R1 —— 能不能复用既有的「商品属性」？**不能，必须新建**

**决策**：**否决复用 `product_property` / `product_property_value`，新建 3 张表**（见 [data-model.md](./data-model.md)）。

**依据**（2026-10-11 查代码）：

| 事实 | 出处 |
|---|---|
| `ProductPropertyDO` 只有 `id / name / remark` —— **没有 `categoryId`**，属性是**全局**的 | `dal/dataobject/property/ProductPropertyDO.java` |
| `ProductPropertyValueDO` 只有 `propertyId / name / remark`，同样无分类 | 同上（value DO） |
| 属性值只挂在 **SKU** 上：`ProductSkuDO.properties` 是内嵌 JSON 的 `List<Property>` | `dal/dataobject/sku/ProductSkuDO.java` |
| **全仓没有 SPU 级属性关联**：`grep -rn "spu_property\|property_value_id"` → 0 结果；建表 SQL 里也**没有**这张表 | `sql/mysql/mall-2026-04-18.sql` 的 product 表清单只有 `brand / browse_history / category / comment / favorite / property / property_value / sku / spu / statistics` |
| 既有属性机制在**线上实际是空的**：54 件碳带商品全是"单规格 + `默认` 占位属性" | `scripts/import_legacy_mall.py:428` |

**为什么不能"给它加个 categoryId 就行"**：这套属性服务的语义是**多规格商品的 SKU 规格**，
`ProductSkuServiceImpl` 的一整套校验（规格数一致、属性值必须属于同一属性项）都挂在它上面。
往同一张表塞"分类级筛选维度"，会让两个语义互相拖拽 —— 删一个筛选维度要担心有没有 SKU 在用，
加一个筛选值要过 SKU 的校验。**这是把两个真相塞进一张表，不是复用。**

**被否决的方案**：
- ❌ 复用 `product_property` + 加 `category_id` 列 —— 见上，语义冲突。
- ❌ 复用 SKU 的 `properties` JSON，从 SKU 反推筛选 —— ① 每个 SPU 只有 1 个 SKU 时它恒为 `默认`；
  ② 没有任何按 JSON 内容检索的既有路径；③ 商品改规格会连带改掉筛选行为，耦合方向反了。

## R2 —— 数据模型：3 张新表

**决策**：
- `product_filter_dimension`(id, category_id, name, sort, tenant_id, …) —— 维度
- `product_filter_value`(id, dimension_id, name, sort, tenant_id, …) —— 可选值
- `product_spu_filter_value`(spu_id, filter_value_id) —— **多对多关联**

**依据**：规格要求「一个商品可挂多个值（含同一维度内多个）、一个值下可有多个商品」，
这正是多对多的标准形态；且筛选要按 `filter_value_id` 做 `JOIN` 与 `GROUP BY`，
**必须是关系表**而不是 JSON 列。

**被否决的方案**：
- ❌ 维度上用一个 `values` JSON 列存全部可选值 —— 关联表要按值 JOIN，JSON 列做不到（或要靠 MySQL
  的函数索引，得不偿失）。
- ❌ 关联表直接存 `(spu_id, dimension_id, value_id)` 三元组 —— 冗余，`dimension_id` 可由 `value_id` 推出，
  冗余列在改挂/迁移时会失真。

## R3 —— 关联挂在 SPU 还是 SKU？

**决策**：**SPU**。

**依据**：前台筛选与分页的粒度都是商品（`/product/spu/page` 返回的是 SPU），
展示用的 `ProductCard` 也是 SPU 级。碳带那 54 件商品**每件就是一个 SPU**（单规格）。
挂 SKU 会让"单规格商品"这一大类需要额外兜底逻辑，而它恰恰是现状的全部。

**被否决的方案**：❌ 挂 SKU —— 只有当"同一商品的不同规格要能分别被筛出来"时才需要，
而规格差异（110mm 宽 vs 100mm 宽）在线上**本来就是不同的商品**。

## R4 —— Q10=B（向下继承）怎么落库与查询？

**决策**：**维度只存一个 `category_id`（单一归属），辖域在查询时按分类祖先链实时求。**

- 浏览分类 X 时显示的维度 = `dimension.category_id ∈ {X} ∪ ancestors(X)`
- 商品属于分类 P 时可挂的维度值 = `dimension.category_id ∈ {P} ∪ ancestors(P)`

**依据**：分类树只有 **3 层、42 个分类**（线上实测）。祖先链就是沿 `parent_id` 向上走 ≤2 步，
**不需要任何新基础设施**。`ProductCategoryDO` 有 `id / parentId`，一次全量加载（42 行）后在内存里
走链即可。

**被否决的方案**：
- ❌ 物化一张"分类 × 维度"展开表 —— 分类树一改就要重建，且会引入"展开表与源数据不同步"这一新故障面。
- ❌ 只在**叶子**分类上允许配维度（把"配在父分类"变成编辑期展开） —— 那就回到了 Q10=A 的
  "配三遍"，正是所有者改口要避免的。

**⚠️ 一条随之而来的约束**：因为维度的归属分类**不在商品的祖先链上就无效**，
所以后台在子分类页必须把"继承自哪个父分类"显示出来（FR-110），否则运营改了父分类的维度值，
子分类页会静默变化，无从解释。

## R5 —— 按维度筛选商品怎么做？

**决策**：在既有 `ProductSpuMapper.selectPage(AppProductSpuPageReqVO, Set<Long> categoryIds)`
上**追加可选条件**，不动既有调用方：

```
每个已选维度 —— 一条 EXISTS（等值）：
  query.exists("SELECT 1 FROM product_spu_filter_value pfv WHERE pfv.spu_id = product_spu.id
                AND pfv.filter_value_id = {0}", selectedValueIdOfDimension)
```

- **每个已选维度 → 一条 `EXISTS`，条件是该维度选中的那个值**（Q9=B 单选，所以是**等值**不是 `IN`；
  这也正是 Q9 从多选改单选换来的简化）；**跨维度 → 多条 `EXISTS`（AND）** —— 对应 FR-101。
- 参数为空时**一条都不追加**，既有行为逐字不变。

**依据**：既有的分页查询用的是 `LambdaQueryWrapperX`，而排序里有一段**自定义 SQL**
（`query.last(" ORDER BY (sales_count + virtual_sales_count) …, sort DESC, id DESC")`，
见 `ProductSpuMapper`）。**重写成 XML 会踩到这段排序片段**；用 `.exists()` 追加条件则完全绕开它。

**被否决的方案**：
- ❌ 把分页查询整体重写成 XML —— 会连带重写排序片段（销量排序用的是表达式，不是列），
  改动面和回归面都远大于本特性的需要。
- ❌ 前端拉全量再过滤 —— 违反 FR-100（必须服务端），且关键词搜索本来就是服务端的。

## R6 —— 要不要做 facet 聚合计数？**不做**（Q11=A）

**决策**：服务端**不聚合商品数**。筛选条上的选项集合 = 该分类及其祖先分类上配置的全部维度与
可选值，**与当前关键词、已选条件、实际商品数完全无关**。

**依据（Q11=A）**：选项只由配置决定 → 选项集合是**静态**的 → 不需要任何聚合。
服务端因此少一整块能力（含一个 Mapper 聚合方法、一个带条件的接口）。

**被否决的方案 —— Q11=B「按当前条件动态收敛」**，以及它必然带出的陷阱：

若要让选项随条件收敛，计数口径**必须排除本维度自身已选的值**：

```
count(D,v) = |{ s : s 在分类范围内 ∧ 命中关键词 ∧ 上架 ∧ 挂着 v
                 ∧ 对每个其它已选维度 D'，s 至少挂着一个 D' 的已选值 }|
```

否则顾客一选中「宽度=110」，同一行其它宽度的计数**全部归零** →
被隐藏 → **顾客既加不了第二个（多选时），也点不到「100」去切换（单选时）**。而且它**不报错**，
只表现为"选了一个就选不了第二个"，极易被当成设计如此放过。

**这段留在这里是有意的**：将来若真要做"选项上显示商品数量"，上面那条陷阱会原样回来 ——
先在这里记下口径与理由，免得重新踩一遍。

## R7 —— 前台是一个接口还是两个？

**决策**：**两个**。

1. 既有 `GET /product/spu/page` **增加可选参数** `filterValueIds`（可选 → 向后兼容，既有调用方零改动）
2. **新增** `GET /product/filter/dimension-list?categoryId=X`，返回该分类的维度与可选值

**依据**：两者的**失效条件不同** —— 维度列表失败时正确做法是"筛选条降级、商品列表照常"，
而不是整页报错（沿用 002 R1 的做法）。塞进同一个响应会让两种错误耦合。

**Q11=A 带来的额外简化**：维度列表**只依赖 `categoryId`**，不依赖关键词与已选值
（那是 Q11=B 才需要的），所以它是**纯配置读**，可以在同一个分类内**只请求一次并复用**
（切换分类才重新请求）。若将来要加计数，这个前提会消失 —— 那时它就得随每次条件变化重取。

**被否决的方案**：
- ❌ 把维度列表塞进分页响应 —— 会给一个**被别处共用**的分页接口加一个只有商城页用的字段。
- ❌ 把维度列表合并进分类接口（`/product/category/list`）—— 分类是全站共用的导航数据，
  往里面塞某个分类的筛选配置会让两者耦合，且它已经是"取全部"的接口。

## R8 —— 管理端挂在哪？

**决策**：
- **维度与值** → **复用既有「商品分类」页**：在操作列加一个「筛选维度」按钮，点开抽屉。
  抽屉内分两段：**本分类自有**（可增删改、可排序）+ **继承自父分类**（只读，标注来源）。
- **商品挂标签** → 在既有**商品编辑页**新增一个子表单 `FilterTagForm.vue`，
  与既有的 `ProductAttributes.vue` 同层（该目录已经是这种"一个子表单一个文件"的结构）。

**依据**：维度数据本身就是**分类私有**的（`category_id` 是它的一等字段），放在分类页最顺；
新建一级菜单要多一套菜单/权限配置，而它并不会被独立访问。商品编辑页的
`views/mall/product/spu/form/` 下已经有 `InfoForm / SkuForm / DeliveryForm / DescriptionForm /
OtherForm / ProductAttributes` 六个子表单，加第七个是既有的扩展方式。

**被否决的方案**：
- ❌ 新建一级菜单「商品筛选维度」 —— 多一套菜单与权限，且运营的心智是"我给这个分类配筛选"，
  不是"我管理一堆维度"。

## R9 —— 维度值怎么传给后端？

**决策**：`filterValueIds` 传**值 id 的扁平数组**（`1,2,5,7`）。
**服务端按 `value.dimension_id` 自行归组**；Q9=B 之下**每个维度至多一个值**，
同组传入多个即为非法请求（见 contracts/app-api.md §1），跨维度是 AND。

**依据**：宪法原则 III —— "前端 MUST NOT 自行实现本应由服务端裁决的业务规则"。
让前端按维度拼参数名（`width=110,100&length=300`）等于把"哪个值属于哪个维度"这条规则搬到前端，
维度一改（运营挪个值）前端就错。

**被否决的方案**：❌ `filter=d1:1,2|d2:5` 这种字符串协议 —— 解析脆弱，且没有带来任何好处。

## R10 —— 空结果时筛选条怎么处理？（FR-105 / FR-113）

**决策**：**空结果时筛选条整块保留**，已选条件仍可取消；商品区给出空态，**明说"当前条件下没有
商品"**。**不另设「清除筛选」按钮**（Q12 / FR-114）—— 清除由各条件自带的控件承担：
维度行首的「全部」清该行（FR-099），关键词由搜索框自带的清空按钮清。

**依据**：Q11=A 之下选项集合本来就与商品数无关，所以"筛选条保留"是**自然结果**，
不需要额外的补全逻辑。但它仍然是一条必须写下来的要求，因为"没有结果就把整块区域收掉"
是很常见的偷懒做法，一旦这么做，顾客就被困在自己造出来的空结果里（连取消都做不到）。

**这是 Q11 从 B 改回 A 之后唯一还留下的、与"空结果"相关的注意点。**
初版规格在 Q11=B 下曾需要"前端把服务端漏掉的已选值补进来渲染"，**那条现在整块不需要了** ——
选项集合本来就不会变，也就无所谓补全。

**被否决的方案**：
- ❌ 空结果时把筛选条一起收掉 —— 顾客无法取消条件，只能刷新页面。
- ❌ 空态里再放一个全局「清除筛选」按钮（Q12）—— 行首的「全部」与搜索框的清空已经覆盖了
  每个条件的清除，再加一个是重复的；而且它会暗示"点一下什么都好了"，实际上关键词与维度
  是否都该清掉是两回事。**本特性不提供这个按钮**（FR-114）。

## R11 —— 商品改分类时，失效标签怎么处理（FR-097）？

**决策**：服务端在保存商品时**校验并剔除**：凡 `filter_value.dimension.category_id`
**不在** `{商品分类} ∪ ancestors(商品分类)` 里的关联，**保存时自动移除**，
并在返回给后台的提示里说明"已移除 N 个不再适用的筛选标签"。

**依据**：改分类是运营的常规操作。若改成"报错拒绝保存"，运营会被一个必然失败的保存卡住，
而错误原因（某个标签不再适用）与他此刻的意图（改分类）无关。**剔除 + 明说**既让操作顺畅，
又不静默吞掉数据变化（宪法：不得静默）。

**被否决的方案**：❌ 保留失效标签不动 —— 它们既不会在前台出现（分类不在范围内），
又会在后台商品页显示成"已选但不可见"，是典型的无法解释状态。

## R12 —— 初始数据从哪来？

**决策**：**不导入、不预填。** 维度、可选值、商品标签**全部由运营在后台录入**。

**依据**：沿用 002 的 Q6 口径 —— 不造数据。上线初期碳带页没有筛选条，这是**正确**表现。

**⚠️ 同时记下这个代价**：碳带有 54 件商品 × 3 个维度 ≈ **162 次勾选**的录入量。

**被否决的方案**：
- ❌ 写脚本从商品名正则抽取（`宸发110mm宽 300m长 蜡基碳带`）自动预填 ——
  这正是 [spec.md](./spec.md) 背景③里说的"写法不统一"（`宸发 红色 混合基碳带，110mm*300M`）；
  自动抽取会产生**不可控的选项集合**，且一旦商品改名，抽取结果与后台配置就分叉了。
  **本期不做**；若运营实际反馈录入量无法承受，再单独立项讨论"预填脚本 + 运营逐条复核"。
- ❌ 移植老站的筛选配置（「1英寸 / 半英寸」）—— 老站那套选项在**现有数据里根本不存在**
  （现在的写法是「110mm轴」「小轴」），照搬等于编造业务事实。

## R13 —— 测试策略

**决策**：三层 + 手工清单，**测试先行**（宪法原则 I）。

① **服务端单测（JUnit + H2，本模块已有 `src/test/resources/sql/create_tables.sql` 的先例）**
- 分页条件的组装：**每个已选维度一条等值 `EXISTS`、跨维度取交集**（FR-101）；
  并覆盖「同一维度传了多个值」这一非法请求的处理
- 分类祖先链：3 层链、根分类、孤立分类
- 挂标签时的辖域校验与**改分类后的剔除**（FR-095 / FR-097 / R11）
- 同名维度拒绝，**且必须覆盖"跨祖先链重名"**（FR-091，不是只查同一 `category_id`）
- **不传 `filterValueIds` 时，生成的查询与改动前逐字一致**（对既有共享接口的兼容性承诺）
- 维度列表接口：**只按 `categoryId` 取**，同一分类下的返回**不受关键词/已选值影响**（FR-111）

② **前端 Vitest 单测**
- `api/product.ts`：`filterValueIds` 的**序列化形态**（逗号分隔、空数组不传）
- 筛选状态的纯函数：切换分类时**保留仍适用的选择**、重置其余（FR-103）

③ **前端 Vitest 组件**
- 筛选条渲染：有维度 / 无维度整块不渲染 / 某行无可选值整行不出现（FR-090 / FR-098 / FR-104）
- **选项集合稳定**：改变关键词或选中值后，渲染出的选项列表**逐字不变**（FR-111 / SC-041）
- 空结果时**筛选条整块保留**、已选值仍可点；出现空态但**不出现全局清除按钮**（FR-105 / FR-113 / FR-114）

④ **手工清单**（[quickstart.md](./quickstart.md)）—— 自动化测不到的部分：真实数据的观感、
三个断点下的版式、运营完整录一遍的耗时。

## R14 —— 迁移与发布

**决策**：新增一个 SQL 迁移脚本（3 张建表），**生产库执行一次**。
**不需要插任何字典/枚举数据**（与 002 不同 —— 那里要加一个 banner 位置取值，
这里没有任何枚举或字典参与）。

**依据**：本特性的所有取值（维度名、可选值名）都是**运营数据**，不是系统枚举。
所以后端**没有** `@InEnum` 之类的强校验需要同步。

**⚠️ 与 002 的 R5 同类风险**：脚本漏执行 → 后台保存维度直接报错（表不存在）。
写进 [quickstart.md](./quickstart.md) 的前置核对清单。

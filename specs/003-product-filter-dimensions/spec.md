# Feature Specification: 商品分类筛选维度（后台配置 + 前台商城筛选）

**Feature Branch**: `003-product-filter-dimensions`
**Created**: 2026-10-11
**Status**: Draft
**Input**: User description: "需要对现在的商品分类下增加商品维度标签，每个分类下都可以进行设置，每个商品可能存在于多个维度标签，每个维度标签下也拥有多个商品，这个维度用于前台商城页面商品的筛选"

> **编号延续 001 / 002**：本仓库的 FR / SC / US / Q 是**全仓唯一**的命名空间（代码注释里直接引
> `FR-005c`、`SC-020`），所以本规格从 **FR-088 / SC-032 / US13 / Q9** 接着往下排。
>
> 本文中引用到的 **FR-004a / FR-045 / FR-077 / FR-086 / FR-087 / SC-001 / SC-008 均属 001 与 002**，
> 不是本规格漏定义 —— 引用它们是为了让"沿用既有口径"这句话可回溯。

## 背景与现状

所有者要的是一个「分类 → 维度 → 可选值 → 商品」的筛选体系，前台商城页据此出筛选条。
核查后，**这件事最难的部分不是 UI，而是"筛选所依据的数据根本不存在"**：

**① 前台一行筛选都没有。** [MallView.vue](../../storefront/src/views/MallView.vue) 里只有
左侧分类树、分类胶囊、关键词搜索、排序四种控件；侧栏的「价格区间 / 服务」筛选在 001 时被
**移除**了（FR-004a），原因是后端不支持。目前商城页**没有任何维度筛选**。

**② 后端不具备按规格筛选的能力。** C 端商品分页
（[AppProductSpuPageReqVO.java](../../yudao-cloud/yudao-module-mall/yudao-module-product-server/src/main/java/cn/iocoder/yudao/module/product/controller/app/spu/vo/AppProductSpuPageReqVO.java)）
只接受 `keyword / categoryId(s) / sortField / sortAsc` 四个条件；其中 `keyword`
在 [ProductSpuMapper.java](../../yudao-cloud/yudao-module-mall/yudao-module-product-server/src/main/java/cn/iocoder/yudao/module/product/dal/mysql/spu/ProductSpuMapper.java)
里**只对商品名做 LIKE**。没有任何"按属性/标签取商品"的查询路径。

**③ 规格信息目前只存在于商品名的文本里，且写法不统一。** 线上「碳带」类目共 **54** 件商品，
宽度、长度、轴心、基材全部写在名字里：

```
宸发110mm宽 300m长 蜡基碳带（单卷）
宸发110mm宽 70m长 110mm轴腊基（单卷）
宸发 红色 混合基碳带，110mm*300M      ← 同一类信息，换了一种写法
理光B110CR 60mm宽 70m长 110mm轴 全树脂碳带（单卷）
```

**④ 既有的结构化规格是空的。** 导入历史数据时
（[import_legacy_mall.py:428](../../scripts/import_legacy_mall.py#L428)），每个商品都被写成
**单规格 + 名为`默认`的占位属性**，等于零信息。而 yudao 的商品属性值**挂在 SKU 上**
（[ProductSkuDO.java](../../yudao-cloud/yudao-module-mall/yudao-module-product-server/src/main/java/cn/iocoder/yudao/module/product/dal/dataobject/sku/ProductSkuDO.java)
的 `properties`），**没有 SPU 级的属性表** —— 所以"直接复用既有商品属性做分类级筛选"是否成立，
需要计划阶段核实（见 Assumptions）。

**⑤ 分类树本身已经够用。** 现有分类已是三级，碳带（113）下就是
**蜡基（114）/ 混合基（115）/ 全树脂（116）** —— 这正是所有者给的参考图里「分类」那一行。
故「分类」行**不需要本特性新增**，它是既有的分类导航。

**结论**：这是一次**数据模型 + 后台配置 + 前台消费**的完整链路建设，
不是给商城页加一个组件。核心取舍在于**筛选所依据的"维度/标签"从哪来、由谁维护**。
服务端要新增的核心能力只有**一块：按维度值筛选商品**（Q11=A 之下不需要做聚合计数）。

## Clarifications

### Session 2026-10-11

- **Q9 前台筛选语义 → 同维度内单选，跨维度 AND。**
  每一行**同时只能有一个值被选中**：点一个新值即**替换**该行原有的选择；点行首的「全部」
  清除该行。不同行之间是「且」—— 商品 MUST 在**每一行**命中该行选中的那个值
  （没有选中的行不施加条件）。
  ⚠️ **这条与 Q11=A 一起，构成一个「点一下就换」的轻量模型**：全程最多 3 次点击就能把三个维度
  各选一个，且每一步都能立刻看到结果。
- **Q10 维度配置的作用范围 → 本分类及其全部子分类生效（向下继承）。**
  维度挂在分类 X 上后：浏览 X **及其任意后代分类**时都会出现这些维度；相应地，商品可挂的维度值
  是**其所属分类自身、以及它所有祖先分类**上配置的那些。于是「宽度」在「碳带」上配**一次**，
  蜡基 / 混合基 / 全树脂三个子分类页就都能用。**这正是所有者最初要的效果** ——
  参考图里「分类」行与「宽度」行同框，本身就说明筛选条是出现在**有下挂分类的那一页**上的。
- **Q11 没有商品的可选值 → 照常展示。**
  筛选条上的选项 = 后台配置的全部可选值，**不随当前条件下的商品数增减**。
  顾客点到没有结果的组合时，看到的是明确的空态（FR-105），而不是一个消失的选项。
  **这也意味着服务端不需要做聚合计数** —— 选项的集合只由配置决定，
  是「静态」的，因此这条决策同时也**消除了 Q9 与 Q11 之间的耦合**（详见下方）。
- **Q12 清除条件的手段 → 各条件自带，不另设全局按钮。**
  价值段本打算给空态配一个「清除筛选」按钮。所有者指出：**每个维度行首本来就有「全部」**
  （点它清空该行，FR-099），搜索框也已有自带的清空按钮 —— **再给一个全局按钮是重复的**。
  故本特性**不提供**「清除筛选」按钮（FR-114）；空态只负责把「当前条件下没有商品」说明白。
  这也顺带把本特性新增的控件压到了最少。
- **Q13 窄屏下的形态 → 每个维度一行，值区横向可滑。**
  一行的值放不下时（窄屏、或某个维度值很多），MUST **横向滚动**该行的值区，
  **MUST NOT 折行**把筛选条撑高。行首的「全部」固定不动，不随值区滚出视野。
  理由：行数（=高度）因此可预测，不会把商品网格整个挤到屏幕外；而单选 + 点即生效的轻量模型
  也不该在窄屏被打断（折叠成按钮/抽屉都要多一次点击）。与 001 的 **SC-008** 不冲突 ——
  那条禁止的是**页面**级横向滚动，行内滑动不算。
- **Q14 点选后的更新顺序 → 乐观更新，失败回退。**
  点一个值 MUST **立刻**改变该行高亮并发请求；请求失败时 MUST 把高亮**退回点击前的状态**
  并说明原因。**界面里不允许存在「选中态与列表不一致」的状态** —— 这是「点即生效」
  最容易漏掉的一面：高亮先动了、列表没跟上，页面上会出现「明明选了 110、看到的却是全部商品」，
  而且**不报错**。

#### Q11=A 顺带消掉的一个陷阱（值得记一笔）

初版规格曾在 Q11=B 下要求「计数必须排除本维度自身已选的值"。**改回 Q11=A 之后这条陷阱不再存在**
—— 选项不由商品数决定，筛选条上的选项永远是完整、稳定的。

（顺带记一笔这条陷阱为什么危险：计数若把本维度也算进去，顾客一选中「110」，同一行其它宽度
就会全部归零消失 —— **既加不了第二个，也切换不到「100」**，只能先点「全部」取消再重选。
在单选（Q9=B）下它比多选时更隐蔽，因为"选中后其它选项消失"看起来还挺像设计好的。）

代价换成另一处：顾客可能点进一个**没有结果**的组合。这由 FR-105 的空态兜住，
且**空态里必须保留筛选条**（否则顾客连取消都做不到）—— 怎么取消见 **Q12**。

#### Q10=B 带来的一条规则（必须实现）

**「分类」那一行与维度行必须不打架。** 参考图第 1 行的「分类：蜡基 / 混合基 / 全树脂」
正是「碳带」的子分类，它是既有的分类导航，**本特性不改它、也不把它变成普通维度**
（见 Assumptions）。但两套东西会**同页共存**，所以同名的分类与维度不得在同一页出现两次
（FR-110）。

## User Scenarios & Testing *(mandatory)*

### User Story 13 - 运营为分类配置筛选维度 (Priority: P1)

运营发现「碳带」这类商品顾客要按宽度、轴心、长度来挑，但商城页只能按分类和关键词找。
他需要在后台给「碳带」这个分类配上「宽度」「轴心」「长度」三组筛选维度，
并在每组下把可选值（40 / 50 / … / 110；1英寸 / 半英寸；300m / 70m）维护进去。

**Why this priority**: 这是**一切的地基** —— 前台筛选条上的每一行、每一个可点的值，
都来自这里。没有它，后面的商品挂标签无值可挂、前台无维度可渲染。
它也是三者中**唯一能完全独立验收**的一块（后台增删改查，不依赖任何其他部分）。

**Independent Test**: 在后台给某个分类新建两个维度、每个维度下建三个可选值，
改名、调序、删掉其中一个；每一步刷新页面后结果都应保持，且重复名称会被拒绝。

**Acceptance Scenarios**:

1. **Given** 运营打开了某个商品分类的维度配置，**When** 新增一个名为「宽度」的维度，
   **Then** 该维度出现在该分类下，且可继续在其下添加可选值。
2. **Given** 「宽度」下已有 40/50/…/110 等可选值，**When** 调整它们的顺序并保存，
   **Then** 重新进入时顺序与保存的一致。
3. **Given** 「宽度」已存在于「碳带」上，**When** 运营在子分类「蜡基」下再新增一个同名的「宽度」，
   **Then** 被拒绝并说明原因 —— 同一分类树的一条祖先链上 MUST NOT 出现两个同名维度
   （否则子分类页会出现两行「宽度」，顾客无从选择）。
4. **Given** 某个可选值已被商品引用，**When** 运营删除它，
   **Then** 系统明确告知它被哪些商品使用，并在确认后**一并清理**这些商品上的该关联，
   **不得**留下指向已删除项的关联。
5. **Given** 一个维度下**一个可选值都没有**，**When** 前台渲染该分类，
   **Then** 该维度**不出现**（前台不得出现只有标题、没有可点项的空行）。
6. **Given** 运营在**父分类**「碳带」下配好了「宽度」「轴心」「长度」，
   **When** 他切到子分类「蜡基」的维度配置，
   **Then** 能看到这三组维度**已继承生效**（说明它们来自父分类「碳带」），
   **不需要在蜡基下再配一遍**（Q10=B）。

### User Story 14 - 运营给商品挂维度标签 (Priority: P2)

运营把每个碳带商品挂到它对应的维度值上：某卷 110mm 宽、300m 长、1 英寸轴心的蜡基碳带，
就同时挂上「宽度=110」「长度=300m」「轴心=1英寸」三个标签。

**Why this priority**: 它是「维度」与「商品」之间的**唯一连接** —— 没有它，
前台即便渲染出筛选条，点任何一个值都是空结果。它依赖 US13 先把维度建出来，
所以排在 US13 之后。

**Independent Test**: 打开一个商品，勾选若干维度值并保存；重新打开该商品，
勾选状态应与保存的一致；取消勾选再保存，关联应真正消失。
勾选一个**不属于该商品所属分类、也不属于其任何祖先分类**的维度值时，应不可选或被拒绝。

**Acceptance Scenarios**:

1. **Given** 某商品所属分类及其父分类上共配置了三个维度，**When** 运营打开该商品的编辑页，
   **Then** 能按这三个维度分别勾选可选值，且**每个维度都可以勾多个**。
2. **Given** 运营勾选了若干值并保存，**When** 重新打开该商品，**Then** 已勾选的值仍然选中。
3. **Given** 运营取消勾选某个值并保存，**When** 前台按该值筛选，**Then** 该商品**不再**出现。
4. **Given** 某商品被修改到了另一个分类，**When** 保存，
   **Then** 它身上**不属于新分类、也不属于新分类任何祖先分类**的标签被清理掉，
   **不得**留下无法解释的标签。
5. **Given** 一个商品在同一个维度下勾了多个值（例如「宽度」同时勾了 110 与 100）
   —— **商品侧的勾选仍是多选**（FR-094），与前台的**单选**是两回事，
   **When** 前台按其中任一个值筛选，**Then** 该商品都会出现。
6. **Given** 商品属于「蜡基」，而「宽度」配在它的父分类「碳带」上，
   **When** 运营打开该商品，**Then** 「宽度」**出现在可勾选的维度里** ——
   继承来的维度与配在本分类上的同等可用（Q10=B）。

### User Story 15 - 顾客在商城页按维度挑商品 (Priority: P3)

顾客进入「碳带」分类，想找 110mm 宽、300m 长的蜡基碳带。他在筛选条上点「宽度=110」、
「长度=300m」，商品列表立刻收窄到符合条件的几件；他还可以叠加关键词搜索和排序。

**Why this priority**: 这是本特性的**价值终点** —— 所有者要的就是这个筛选条。
但它排最后，理由与 002 的取舍同源：**它独立验收必然依赖 US13 与 US14 配置出来的数据**，
在数据存在之前，这一块无法独立演示。

**Independent Test**: 在一个其分类树上有维度配置、且商品已挂好标签的分类页上：
点选任一维度值，列表只留下符合条件的商品；叠加关键词与排序后结果依然正确；
切到该分类树之外、没有任何维度配置的分类，筛选条整块不出现。

**Acceptance Scenarios**:

1. **Given** 父分类「碳带」配置了三个维度，**When** 顾客进入子分类「蜡基」页，
   **Then** 在商品列表上方看到三行筛选条（维度继承自父分类），
   每行第一项为「全部」，其后是该维度的可选值，顺序与运营设定的一致。
2. **Given** 顾客点了「宽度」行的「110」，**When** 列表刷新，
   **Then** 只展示挂了「宽度=110」的商品；点「全部」恢复为该维度不施加条件。
3. **Given** 「宽度」行已选中「110」，**When** 顾客再点「100」（Q9=B 单选），
   **Then** 「110」被**替换**为「100」—— 该行**同时只有一个**值高亮；
   列表随之改为只展示「宽度=100」的商品。顾客**不需要**先取消再重选。
4. **Given** 「宽度」已选「110」，「长度」已选「300m」，**When** 列表刷新，
   **Then** 只出现**同时**满足这两个维度的商品（跨行是「且」）。
5. **Given** 顾客已选中若干维度值，**When** 再输入关键词并搜索、或切换排序，
   **Then** 三种条件**同时生效**（互不覆盖），结果正确。
6. **Given** 筛选后的结果超过一页，**When** 顾客翻到第 2 页，
   **Then** 第 2 页仍是筛选后的商品，**不出现**不满足条件的商品。
7. **Given** 顾客选中的条件筛不出任何商品，**When** 列表刷新，
   **Then** 展示明确的空态（明说"当前条件下没有商品"）；**不得**白屏、**不得**残留上一批商品。
   **筛选条整块保留**，顾客逐行点「全部」即可依次取消条件（Q12）。
8. **Given** 顾客在「蜡基」下选了「宽度=110」，**When** 他切换到同样继承「宽度」的「混合基」，
   **Then** 该选择**保留**（Q10=B：同一维度在兄弟分类间是同一个，切换后仍然适用）；
   **When** 他改切到维度链之外的分类，**Then** 该选择被重置，**不得**带着失效条件去查询。
9. **Given** 某分类**及其所有祖先分类**都没有配置任何维度，**When** 顾客进入该分类页，
   **Then** **不出现**筛选条区域，也**不出现**空白块，商品列表照常从上方开始。
10. **Given** 维度配在父分类「碳带」上，**When** 顾客先在「碳带」页、再到「蜡基」页浏览，
    **Then** 两页**都**出现同一套筛选条（Q10=B：向下继承）。
11. **Given** 某个可选值在当前筛选条件下**一件商品都对应不上**，**When** 顾客进入该分类页，
    **Then** 该值**照常出现在筛选条上**（Q11=A）；点选它只会得到空态（场景 7），选项本身不消失。
12. **Given** 顾客已在「宽度」行选中「110」，**When** 列表刷新，
    **Then** 「宽度」行里的**其它可选值照常展示、照常可点** —— 顾客可以随时换一个
    （Q9=B 单向替换）。选项集合完全由后台配置决定，**不随已选条件变化**（Q11=A）。
13. **Given** 顾客选中了某个可选值之后又叠加关键词把结果筛空，**When** 列表刷新，
    **Then** **筛选条整块保留**、该值仍显示为已选中且可点击 —— 顾客必须能取消它，
    **不得**被自己造出来的空结果困住。

### Edge Cases

- **维度下没有可选值**：该维度前台整行不渲染（不是渲染一个空行）。这是**唯一的**整行不渲染情形。
- **可选值在当前条件下没有商品**：**照常展示**（Q11=A），点选后走空态。顾客可能点进死路 ——
  由 FR-105 的空态兜住，取消手段是行内的「全部」（Q12）。
- **顾客选中一个值后，结果被关键词筛空**：筛选条 MUST 整块保留，已选值仍可取消；
  **不得**因为"没有结果"就把筛选条一起收掉，那会把顾客困住。
- **维度配在父分类**：筛选条在父分类页与它的每个子分类页都出现；
  各页上的**选项集合完全相同**（选项只由配置决定，不按页面收敛）。
- **运营改了可选值的名称**：前台应立即显示新名称，且**已选中的筛选条件仍然有效**
  （按标识而非名称匹配，否则改名会把顾客的筛选条件打断）。
- **运营删除了正在被选中的可选值**：顾客侧该条件失效，结果集回到该维度未施加条件的状态，
  不得报错或永久卡住。
- **顾客想在同一行换一个值**：直接点新值即可**替换**（Q9=B）—— MUST NOT 要求他先点「全部」
  取消再选。选中「110」之后，同行其它值 MUST 仍然可点（Q11=A）。
- **点了一个值、查询却失败了**：高亮 MUST **退回点击前的状态**（并说明原因，FR-115）。
  页面上 MUST NOT 停在「选中的是新值、列表却是旧结果」的状态。
- **顾客快速连点同一行里的几个值**：以**最后一次**点击为准；先发出的请求即使后返回，
  MUST NOT 覆盖更晚的那次选择（否则高亮与列表会错位）。
- **商品被从 A 分类移到 B 分类**：其分类树变化后，不再落在新分类祖先链上的标签被清理（US14-4）。
- **一个分类下维度很多**（例如 6 行以上）：筛选条的高度 = **维度行数 × 固定行高**，行数只由
  运营配置的维度个数决定，**不随任何运行时数据变化**（FR-108 / FR-112）；MUST NOT 折叠成
  按钮或抽屉。**本期不设维度数量上限** —— 这是显式的范围声明，由运营自律（见 Assumptions）。
- **某个维度的值很多、或屏幕很窄**：该行的值区**横向滚动**，「全部」固定在行首；
  **不得折行**把这一行撑成多行（否则行数会随数据变，高度不可预测）—— Q13 / FR-108。
- **一个可选值的名称很长**（例如「1英寸（25.4毫米）」）：不得把该行撑破或换行错位。
- **后台服务不可用**：筛选条与列表都要给出可重试的错误态，不得白屏。
- **未登录顾客**：筛选行为 MUST NOT 要求登录（与既有商品浏览一致）。
- **两个运营同时改同一分类的维度**：以最后保存的为准（沿用既有后台行为，本次不做并发控制）。

## Requirements *(mandatory)*

### Functional Requirements

**后台：分类维度配置（US13）**

- **FR-088**: 运营 MUST 能在**指定的商品分类**下新增、重命名、删除、排序「筛选维度」。
- **FR-089**: 运营 MUST 能在某个维度下新增、重命名、删除、排序「维度可选值」。
- **FR-090**: 一个维度**没有任何可选值**时，该维度 MUST NOT 出现在前台
  （不得渲染只有标题、没有可点项的空行）。**这是整行不渲染的唯一情形**。
- **FR-091**: **同一条分类祖先链上**的维度名称 MUST NOT 重复（含分类自身与它的全部祖先）；
  同一维度下的可选值名称 MUST NOT 重复。违反时 MUST 拒绝保存并说明是哪一个名称重复了。
- **FR-092**: 删除维度或可选值、且它们已被商品引用时，MUST 先明确告知影响范围，
  并在确认后**一并清理**商品上的对应关联；MUST NOT 留下指向已删除项的关联。
- **FR-093**: 上述配置 MUST 持久保存，重新进入后台 MUST 仍可见、可改。

**后台：商品挂维度标签（US14）**

- **FR-094**: 商品编辑 MUST 支持把商品关联到**多个**维度可选值；**同一维度内 MAY 选多个**，
  跨维度 MAY 各选若干个。
- **FR-095**: 商品可选的维度值范围 MUST 限定为**该商品所属分类自身、以及它全部祖先分类**上
  配置的维度值（Q10=B）—— MUST NOT 允许挂上子分类或其它分支的维度值。
- **FR-096**: 保存后重新打开商品 MUST 保留已选关联；取消勾选并保存 MUST 真正解绑。
- **FR-097**: 商品所属分类发生变化时，MUST 清理掉**不再落在新分类祖先链上**的关联，
  MUST NOT 留下无法解释的标签。
- **FR-110**: 子分类 MUST 能看见并说明「这些维度继承自哪个祖先分类」；
  同一页 MUST NOT 出现两个同名维度行（含「分类」导航行与维度行重名的情况）——
  **冲突时以既有的分类导航行优先，同名的维度行不渲染**，并在后台提示运营。

**前台：商城页筛选（US15）**

- **FR-098**: 商城页在选中了某个分类、且**该分类自身或其任一祖先分类**配置了维度时，
  MUST 渲染筛选条：每个维度一行，行首为「全部」，其后按运营设定的顺序列出可选值。
  维度沿分类树**向下继承**（Q10=B）：配在「碳带」上的维度，在蜡基 / 混合基 / 全树脂页都出现；
  但 MUST NOT 上浮（子分类配的维度不出现在父分类页）。
  筛选条 MUST 位于商品列表之上，且 MUST NOT 与既有分类导航、关键词搜索、排序控件冲突。
- **FR-099**: 点选某个可选值 MUST 立即按其筛选商品列表（无需额外的「确定」动作）；
  **同一维度内同时只能有一个值被选中** —— 点一个新值 MUST **替换**该行原有的选择，
  MUST NOT 要求顾客先取消。点行首的「全部」MUST 清除该维度的条件。
- **FR-100**: 筛选 MUST 与分类、关键词、排序**共同生效**，且 MUST 在**服务端**执行 ——
  结果超过一页时，翻页后仍是筛选后的商品。筛选作用的商品范围 MUST 与既有的分类浏览口径一致
  （浏览某分类时，结果含其子分类下的商品）。
- **FR-101**: **同一维度内**是**单选**（Q9=B）：每一行最多一个选中值；
  **不同维度之间** MUST 是「且」—— 商品 MUST 在每一行里命中该行选中的那个值，
  未选中任何值的行 MUST NOT 施加条件。
- **FR-102**: 筛选条件发生变化时 MUST 回到第 1 页（沿用既有 `onSearch` / `onPickCategory` 口径）。
- **FR-103**: 切换分类时，MUST 重置**在新分类下不再适用**的维度选择；
  **在新分类下仍然适用的**（同一维度在兄弟分类间共有，Q10=B）MUST 保留。
  MUST NOT 用已失效的条件去查询。
- **FR-104**: 分类**及其全部祖先分类**都没有配置维度时，MUST NOT 渲染筛选条区域，
  MUST NOT 出现空白块，商品列表 MUST NOT 因此错位。
  **同一条也适用于"配了维度、但每个维度都没有可选值"的情形** —— 此时 FR-090 会让每一行都不渲染，
  整个筛选条 MUST 一并消失，MUST NOT 留下一块空条（这正是 FR-107 要禁的「空白块」）。
- **FR-105**: 筛选结果为空时 MUST 展示明确的空态（明说「当前条件下没有商品」）；
  MUST NOT 白屏，MUST NOT 残留上一次的结果。
  （**空态下筛选条本身怎么办，由 FR-113 单独规定** —— 两条分工，不重复。）
- **FR-114**: 清除条件 MUST 由**各个条件自带的控件**承担，MUST NOT 另设一个全局的
  「清除筛选」按钮：维度行由行首的「全部」清除（FR-099），关键词由搜索框自带的清空按钮清除。
  空态**只需要把"没有商品"这件事说明白**，不需要再给一个按钮（Q12）。
- **FR-115**: 点选一个可选值 MUST **立刻**改变该行高亮（乐观更新）并发起查询；
  查询失败时 MUST **把高亮退回点击前**的状态，并按 FR-077 的口径展示**后端返回的原因**。
  页面 MUST NOT 停留在「选中态与列表不一致」的状态（Q14）。
  同一行的**快速连点**以最后一次为准：先发出的请求即使后返回，MUST NOT 覆盖更晚的选择。
- **FR-106**: 请求失败时 MUST 展示**可重试**的错误态（沿用 FR-045 口径）。
- **FR-107**: 页面 MUST NOT 出现「空白块 / 占位文案 / 编造内容」三类静默缺陷（沿用 FR-087）——
  无维度配置、无可选值、无结果三种"没有内容"的情形，一律要么不渲染、要么明说。
- **FR-108**: 新增的筛选条 MUST 通过既有的视觉一致性可执行断言
  （色板与 **1100 / 768 / 480** 三个断点，沿用 FR-086 口径）。
  ⚠️ 该断言（`storefront/src/styles/design-consistency.spec.ts`）**目前只扫描显式登记的
  「视图文件」**，而筛选条是一个**组件**（不在 `views/` 下）。因此本项 MUST **同时**把该组件
  登记进断言的核对范围（组件只适用「色板」与「断点」两条，第三条「不得自带顶栏页脚」是页面级的，
  不适用于组件）—— **不登记 = FR-108 的 MUST 零覆盖**。
  形制上 MUST 保持**每个维度一行**：行首的「全部」固定，值区在放不下时**横向可滑**、
  MUST NOT 折行把筛选条撑高；MUST NOT 造成**页面**级横向滚动（Q13，与 001 SC-008 一致）。
- **FR-109**: C 端 MUST 只消费 `/app-api`；管理端 MUST 只走 `/admin-api`（宪法约束，不得跨用）。

**前台：选项的稳定性（Q11=A）**

- **FR-111**: 筛选条上的选项集合 MUST 只由**该分类及其祖先分类上配置的维度与可选值**决定，
  MUST NOT 随当前的关键词或已选维度值增减 —— 同一个分类页上的选项集合是**稳定**的。
  某个值当前没有商品，它**照样出现**；顾客点选后走空态（FR-105）。
- **FR-112**: 选项的**排列顺序** MUST 是运营设定的顺序（`sort`），
  MUST NOT 按商品数或任何运行时数据重排。
- **FR-113**: 顾客选中某个可选值后，无论结果集是否为空，**筛选条 MUST 整块保留**，
  已选中的值 MUST 仍可取消 —— **不得**因为「没有结果」就把筛选条一起收掉。

### Key Entities *(include if feature involves data)*

- **筛选维度**：挂在**某个商品分类**下的一组筛选条件，有名称与展示顺序。
  例如「碳带」下的「宽度」。它沿分类树**向下继承**（Q10=B）——
  挂在「碳带」上的维度，在蜡基 / 混合基 / 全树脂页都生效；子分类自己配的维度**不上浮**。
  同一条祖先链上不允许同名（FR-091）。
- **维度可选值**：属于某个维度，有名称与展示顺序。例如「宽度」下的「110」。
  前台可点的就是它。**当前没有商品对应时照常出现**（Q11=A）—— 选项集合只由配置决定，
  不随运行时的商品数变化。
- **商品与维度可选值的关联**：**多对多** —— 一个商品可挂多个可选值（含同一维度内的多个），
  一个可选值下可有多个商品。它是前台筛选的**唯一依据**，
  且只能挂**商品所属分类自身及其全部祖先分类**上的维度值（Q10=B）。
  ⚠️ **这里商品侧的多选与前台的选法是两件事**：商品可以同时挂着「宽度=110」和「宽度=100」
  （因为运营要表达的正是"这件货有这两个规格"），而顾客在前台每一行**只能选一个**（Q9=B）。
- **（前台）筛选状态**：顾客当前所处的分类 + **每个维度至多一个**选中值 + 关键词 + 排序。
  条件变化即触发一次服务端查询；切换分类时只重置**在新分类下不再适用**的维度选择。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-032**: 运营在后台给某分类配好维度与可选值后，**无需发版** ——
  顾客**下一次加载该分类页**（进入、切分类、或刷新）时即出现这些维度。
  ⚠️ **不承诺"自动出现"**：前台没有轮询也没有实时推送，已经打开的页面不会自己更新。
  （原稿写的"配置到前台可见的延迟不超过 1 分钟"是不可达也无需达的口径，已改。）
- **SC-033**: 对任一已挂标签的商品，点选它所属的任一个维度值，该商品 **100%** 出现在结果中；
  未挂该值的商品 **100%** 不出现。抽查 **10** 个可选值逐一核对。
- **SC-034**: 筛选与关键词、分类、排序三者叠加时，结果正确率 **100%** ——
  抽查 **5** 组组合条件，结果集应恰为各条件的交集（不得互相覆盖、不得只取其一）。
- **SC-035**: 筛选在**服务端**执行 —— 当筛选结果超过一页时，翻到第 **2** 页仍是筛选后的结果，
  页面上不出现任何不满足条件的商品。
- **SC-036**: 分类**及其全部祖先分类**都未配置维度的页面，**100%** 不出现筛选条或空白块；
  商品列表从上方正常开始。反之，维度配在父分类时，**100%** 在该父分类页及其每个子分类页上都出现。
- **SC-037**: 空结果时 **100%** 出现明确空态，不出现白屏或残留上一批结果；
  且**筛选条整块仍在**，已选条件可用行内「全部」逐个取消。页面上**不出现**全局的
  「清除筛选」按钮（FR-114）。
- **SC-038**: 后台闭环可跑通：**在父分类「碳带」上建维度 → 建可选值 → 子分类页立刻可见（无需发版）
  → 给商品挂标签 → 前台可见 → 改可选值名称 → 前台同步更新且已选条件不被打断
  → 删可选值 → 前台不再出现该项且商品关联被清理**。
- **SC-039**: 筛选条在 **1100 / 768 / 480** 三个断点下均不破坏既有布局
  （由既有视觉一致性断言自动覆盖）；且在 **480** 下确认：**页面**不出现横向滚动条、
  筛选条的行数不随某个维度的值变多而增长（值区自己横向滑动，Q13）。
- **SC-040**: 组合语义正确率 **100%** —— **跨维度取交集**：抽查 **5** 组两三个维度同时选中的
  条件，结果集恰为各条件的交集；且每一行**至多一个**值处于选中态（Q9=B）。
- **SC-041**: 选项集合**稳定**（Q11=A）—— 在同一个分类页上，无论关键词怎么变、
  选中了哪些值，筛选条上的选项集合**逐字不变**（对比 5 组条件下的选项列表）。
  其中至少有一组条件会筛出 0 件商品，此时筛选条与已选条件**仍然完整保留**。

## Assumptions

- **维度是两级结构（维度名 + 多个可选值），不是一层扁平标签。** 依据是所有者给的参考图 ——
  筛选条必须能渲染出「宽度：40 110 100 90 …」这种"一组标题下挂多个可点值"的形态，
  扁平标签列表渲染不出来。
- **参考图里的「分类」行就是既有的子分类导航**（蜡基 / 混合基 / 全树脂 = 现有三级分类
  114 / 115 / 116），**不属于本特性新增**。本特性只新增图中第 2~4 行那种维度。
- **维度沿分类树向下继承（Q10=B）**：「宽度」在「碳带」上配**一次**，蜡基 / 混合基 / 全树脂
  三个子分类页就都能用；商品挂在叶子上，挂的正是从父分类继承下来的那套维度值。
  代价是同一条祖先链上不能出现同名维度（FR-091），否则子分类页会有两行「宽度」。
- **选项不做任何计数。** Q11=A 之下服务端**不聚合商品数**，选项上也不显示数字
  （参考图上也没有）。将来若要显示"每个值有多少件商品"，需要新增一块 facet 聚合能力，
  并处理"计数要不要排除本维度自身已选的值"这个陷阱（Q11=B 曾引入过，见 Clarifications）——
  **那是一个独立增量，本期不做**。
- **未选中任何值时 = 不施加该维度的条件**，与点「全部」等价。
- **不设"一个分类下最多几个维度 / 一个维度下最多几个值"的上限。** 前台的高度只随**维度行数**
  线性增长（不折行，FR-108），因此不存在"布局被撑破"的风险；至于"运营配了 20 个维度导致
  商品列表被挤到很下面"，那是运营自己的取舍，**本期不用代码去管它**。若将来要管，
  应当先有真实的运营反馈，而不是现在预防性地加一道限制。
- **筛选条点即生效，没有「确定」按钮** —— 依据是参考图里没有确认动作。
- **维度与标签由运营在后台录入，不导入、不伪造数据。** 上线初期可以为空；
  此时前台不出现筛选条，这是**正确**表现而非缺陷（与 002 的 Q6 同一口径）。
- **本期只做 Web 前台商城页**；小程序 / App 端（`yudao-ui-mall-uniapp`）不在本期范围 ——
  与 001 / 002 的范围一致。
- **维度不在商品详情页展示，也不参与站内搜索与 SEO**。本期只服务"筛选"这一个用途。
- **不含价格区间、服务等其它筛选维度**。001 的 FR-004a 已排除它们，理由（后端不支持）不变；
  本特性只解决"按分类自定义维度筛选"这一件事。
- **后台的配置入口具体挂在哪个菜单下（既有商品分类页 / 商品属性页 / 新菜单）由计划阶段决定**，
  本规格只要求"运营可配置、可维护"。
- **实现 MUST 优先复用服务端既有的商品属性/维度能力**（宪法原则 III）。
  但需注意背景④所述事实：yudao 的属性值挂在 SKU 上、没有 SPU 级属性表，
  且现有 54 件碳带商品都是"单规格 + 占位属性"。
  **计划阶段 MUST 先核实既有能力能否直接承载"分类级筛选维度"，不能则新建，
  并在 `research.md` 记录否决既有方案的理由。**
- **遵守项目宪法**：不引入 UI 组件库；C 端只走 `/app-api`、管理端只走 `/admin-api`；
  测试先行不可协商；改动尽量收敛在少量文件。

## 落地决策

| Q9 | 前台的**筛选语义** | **B：同维度内单选，跨维度 AND**（所有者 2026-10-11 定；初选 A，同日改 B） | 一行一个值、点新的即替换 —— 全程最多 3 次点击就能把三个维度各定一个，且每一步立刻看到结果。Q12（不设全局清除按钮）在单选下更成立：行首「全部」就是唯一的取消手段，不需要别的。代价是"80 和 90 都想看看"要分两次看。服务端因此更简单：每个已选值一条**等值** `EXISTS`，不再需要"同组 OR"。落地为 FR-099 / FR-101 / SC-040 |
| Q10 | 维度配置的**作用范围** | **B：本分类及其全部子分类生效**（所有者 2026-10-11 改定；初选 A 后改） | 「宽度」在「碳带」上配**一次**，三个子分类页就都能用；商品挂在叶子上，挂的正是继承来的那套值。**代价**：同一条祖先链上不能重名（FR-091），且切换分类时"仍适用的选择"要保留而不是一律清空（FR-103）。落地为 FR-095 / FR-097 / FR-098 / FR-103 / FR-110 |
| Q11 | **没有商品**的可选值 | **A：照常展示**（所有者 2026-10-11 定；曾短暂改 B，同日改回 A） | 选项集合只由后台配置决定，顾客看到的筛选条是**稳定**的，不会因为选了一个值、或换了个关键词就变样。**同时省掉了服务端的聚合计数**，也就顺带消掉了 Q11=B 必然带出的那个陷阱（计数若忘了排除本维度自身的已选值，顾客选中一个值后同行其它值会全部消失，连切换都做不到）。代价是顾客可能点进没有结果的组合 —— 由 FR-105 的空态兜住，取消手段见 Q12，且空态下**筛选条必须留着**（FR-113） |

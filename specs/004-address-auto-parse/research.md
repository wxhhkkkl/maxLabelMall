# 技术决策与被否决方案

本文件记录 Phase 0 的调研结论。编号 **R1~R13** 接着 003 的 R14 之后另起（两篇独立）。

---

## R1 —— 解析放客户端还是服务端？**客户端**

**决策**：**在 `storefront` 客户端做，不新增服务端接口。**

理由：

1. **yudao 确实没有这个能力，但不是"接口不足"而是"没有这个概念"**。已逐文件核实
   `AreaController` 只有两个端点：`GET /system/area/tree`（返回省节点的 children）与
   `GET /system/area/get-by-ip`（按 **IP** 反查归属地，不是按文本解析）。后者常被误以为
   可以复用 —— 它需要的是 IP，不是地址串，语义完全不同。
2. **宪法原则 III 明确要求先走这条路**：「若既有能力已存在但接口不足，MUST 先评估是否可由
   前端适配解决，再考虑扩展服务端」。行政区划树**本来就是该弹层打开时必须拉的**（渲染三级联动），
   解析所需的数据在那棵树里**一个字节都不缺**。
3. **不需要服务端裁决**。原则 III 禁止前端自行实现的是「价格、库存、券可用性、订单状态、限流」
   这类**有权威值**的规则。地址解析没有权威值 —— 它是把一段自由文本映射到一棵**由服务端下发**
   的树，客户看到结果后仍可自行改，最终落库的仍是既有保存链路。
4. **SC-045 要求"感知为即时"**。客户端匹配是纯内存操作；走接口就多一次 RTT 与一个加载态。

**被否决的方案**：新增 `POST /app-api/system/area/parse`。除了以上四条，它还要求：
服务端加接口 + DTO + 单测 + 发版（后端目前单 jar、重启约 73 秒，见 [[server-deploy]]），
而收益只是"算法换个地方住"。**不做。**

## R2 —— 怎么在文本里定位一个行政区划名？

**决策**：**候选名 = 完整名 + 去后缀名；取"最早出现位置"，同位置取最长匹配。**

- 行政区划数据（`yudao-spring-boot-starter-biz-ip/src/main/resources/area.csv`）里的名字
  **都带后缀**：`浙江省` / `杭州市` / `余杭区`。而客户写的往往不带：「浙江杭州余杭区」。
- 所以每个节点生成两个候选：`浙江省` 与 `浙江`、`杭州市` 与 `杭州`、`余杭区` 与 `余杭`。
- 后缀剥离表（只剥**尾部**、且只剥已知行政区划后缀）：
  `省 / 市 / 区 / 县 / 自治区 / 自治县 / 自治州 / 特别行政区 / 地区 / 盟 / 旗`
- **MUST NOT 单独匹配后缀**：否则「文一西路 969 号」里的「路」、任何带「区」的词都会被误判。
  候选必须来自后台树里的**真实名字**（或其去后缀形式）。
- 多个候选命中时：**先取位置最靠前的**；同一位置有多个长度不同的命中时**取最长的**
  （「朝阳区」优先于「朝阳」）。

**已核实的数据事实**：`area.csv` 共 3880 行，type 1=国家、2=省（34）、3=市（390）、4=区县（3207）；
`/system/area/tree` 返回的是 id=1「中国」的 children，即 **34 个省节点**，各带完整的市 / 区县子树。

## R3 —— 直辖市怎么处理？（北京市的市级节点也叫「北京市」）

**决策**：**不用"省 → 市 → 区逐级往下匹配"，改为以区县反推市级。**

这是本特性最容易写错的一处，实测数据：

| 层级 | 北京 | 重庆 |
|---|---|---|
| 省 | `北京市`(110000) | `重庆市`(500000) |
| 市 | `北京市`(110100) ← **同名** | `重庆城区`(500100) ← **不同名，且文本里根本没有** |
| 区县 | `朝阳区`(110105) | `渝中区` … |

- 若按"逐级匹配"：北京会在市一级**要求文本里再出现一次「北京市」**（不存在）；
  重庆则要求文本里出现「重庆城区」（客户不会这么写）。两条都会解析失败。
- 改为：**先定省 → 再在省的整棵子树里找区县 → 市 = 该区县节点的 parent**。北京与重庆
  一并解决，且不依赖中间层叫什么名字。
- 若区县没匹配到，再退回"在省的子树里直接找市一级"。

## R4 —— 客户漏写省份怎么办？（「杭州市余杭区…」）

**决策**：**市名在全国范围内唯一时，才向上补出省份；不唯一则整条不填。**

- 真实粘贴里漏省份很常见。
- 规则：若文本里没有匹配到省，则拿市候选（或由区县反推的市）反查它属于哪些省；
  **恰好 1 个** → 省 / 市都填上；**多于 1 个** → 省市区都不填，只报"未识别到行政区划"。
- 依据：SC-042 要求**填错条数为 0**，宁可少填。不做"猜一个最像的"。

**📌 2026-10-12 实现时实测更正（原文写错过）**：本文早期版本写「全国 390 个市级节点，
重名的（同名不同省）确实存在」——**这是错的**。逐行统计 `area.csv`：

| 层级 | 总数 | 跨父级重名 |
|---|---|---|
| type 3（市） | 390 | **0** |
| type 4（区县） | 3207 | **47**（如「朝阳区」「江北区」各 2 个） |

所以"市名不唯一"这条分支**在今天的真实数据里不会触发**。仍然保留那个"恰好 1 个"的判据：
它只有一行，却让"不猜"这件事**不依赖"上游数据永远不出现重名市"这个假设**。
反过来，**区县重名是常态**（47 组），R5 因此是必须认真实现的一条，不是边角料。

## R5 —— 重名区县怎么办？（全国有多个「朝阳区」）

**决策**：**在已定省份的子树内匹配；仍不唯一时，若已定市级则再用市级收敛；还不行就不填。**

- 「朝阳区」在全国至少有两个（北京、长春），重庆市有「江北区」、宁波市也有「江北区」。
- 顺序：省已定 → 只在**该省的子树**里找区县（多数重名到这一步就消解了）→ 仍多个 →
  若文本里也匹配到了市，则取**该市下面**的那个 → 仍不唯一 → 区县不填。
- **MUST NOT** 取"第一个匹配"了事 —— 那会把长春的朝阳区填给北京的客户，
  正是 SC-042 里那个"填错"。

## R6 —— 「剩余文本」怎么切？

**决策**：**从归一化后的文本里，删掉被识别消耗掉的那些子串，再折叠空白并去首尾。**

- 例：「浙江省杭州市余杭区文一西路 969 号」→ 消耗 `浙江省`、`杭州市`、`余杭区` →
  剩 `文一西路 969 号`。
- **只在至少识别到一级行政区划时才产生剩余文本**（FR-121）。一级都认不出来时整段文本
  处于"没被行政区划切开"的状态，此时回填详细地址等于拿一次不可信的解析去覆盖客户已填的内容。
- 剥掉行政区划后若只剩标点或空白 → 剩余为空，此时**不回填**详细地址（Q17 的意图是回填
  "有意义的剩余内容"，不是用一个空串覆盖客户输入）。

## R7 —— 归一化到什么程度？

**决策**：**只做两类归一化：全角数字/字母转半角、连续空白折叠成一个空格并去首尾。**

- 全角：客户从微信/文档里粘来的地址常带全角数字（`９６９`）。
  📌 **2026-10-12 实现时收紧**：本文早期版本写的是"全角数字**与标点**"，
  实现时判定**标点不该转** —— 把「（」变成「(」只会让详细地址看起来不对，
  而对匹配毫无帮助（行政区划名里根本没有 ASCII 标点）。所以只转数字与字母。
- 空白：换行、制表、连续空格、全角空格（`　`）都折叠成一个半角空格 ——
  否则「浙江省  杭州市」中间的连续空格会让位置计算与剩余文本都变难。
- **不做**的：繁简转换、拼音、错别字纠正。这些都需要额外的映射表或模型，
  而任何这类映射表都会变成"客户端内置的数据"，且没有业务必要性。

## R8 —— 部分识别 / 完全失败怎么表达给组件？

**决策**：**解析器返回结构化的 `ParseResult`，绝不自己弹提示。**

```ts
interface ParseResult {
  province: Area | null
  city: Area | null
  district: Area | null
  detail: string            // 剩余文本；无剩余时为空串
  missing: Array<'province' | 'city' | 'district'>   // 未识别到的层级
  matchedLevels: number     // 0 表示完全没识别到 → 组件据此不碰任何字段（FR-121）
}
```

理由：解析器是纯函数、不持有 UI 状态；"提示什么文案、要不要禁用按钮"属于组件的事。
`matchedLevels === 0` 就是 FR-121 的唯一判据，组件只看这一个数。

## R9 —— 解析器放哪、签名长什么样？

**决策**：`storefront/src/utils/address-parse.ts`，入口 `parseAddress(text, tree)`。

- storefront 的 `utils/` 是既有约定：14 组 `<name>.ts` + `<name>.spec.ts` 同目录成对
  （`sanitize` / `money` / `tel` / `badge` …）。
- **不写进 `.vue`**：本特性要靠密集的表驱动用例（SC-042 那批样本）来锁"填错率为 0"，
  塞进 SFC 就只能挂载组件才能断言，慢且测不准。
- **不 import Vue**：保持纯函数，测试不需要 `mount`。
- 只依赖 `Area = { id, name, children? }` 三个字段（`storefront/src/types/address.ts` 已有此类型），
  与后台 `AreaNodeRespVO` 的字段完全对齐 —— 见 [contracts/address-parse.md](./contracts/address-parse.md)。

## R10 —— 撤销怎么实现？

**决策**：**组件在识别前对 `lv1 / lv2 / lv3 / detailAddress / name / mobile` 做一次快照，撤销即整体还原。**

- 只快照"识别会碰"的字段，**不碰** 是否默认 —— 识别从来不动它，把整张表单快照进去
  反而会让"撤销"变成"回退用户手打的一切"，那是错的。
- 📌 **2026-10-23 改判（Q55）**：姓名与手机号自本轮起也会被识别写回，所以它们**必须**进快照。
  否则识别覆盖了客户手打的值之后，撤销只退回地址，收件人/手机号就找不回来了。
- 每次识别**覆盖**上一次快照（Q16=A 的语义是"每次识别都是一次新的、可撤销的操作"），
  故 US3 场景 2 说"撤销回到**最近一次**识别前"。

## R11 —— 要不要引第三方地址解析库？

**决策**：**不引。自己写匹配。**

- 常见候选（`address-smart-parse`、`chinese-address-parser` 之类）**都把行政区划数据
  打进自己的包里** —— 这与 FR-118 / SC-046「客户端内置行政区划条目数 MUST 为 0」**直接冲突**。
- 而且它们的数据必然**比后台那份 `area.csv` 旧**（撤县设区、更名），会出现"前端认得出、
  后台存不进去"的错配：解析出的名字找不到对应的 `areaId`，保存时校验失败。
- 本特性的匹配逻辑约 100 行，且需要密集单测 —— 引入一个自带数据的黑盒，收益为负。
- 宪法原则 IV：「引入的新依赖 MUST 有明确理由」。

## R12 —— 测试策略（宪法原则 I 的落点）

**决策**：**纯函数表驱动为主 + 组件交互用例为辅；e2e 本期不加。**

- 纯函数：每个用例形如 `{text, 期望省/市/区, 期望剩余文本, 期望缺失层级}`，**先写见红**。
  重点覆盖 SC-042 那批样本分类：省市区齐全 / 缺后缀 / 直辖市 / 只到市 / 只到省 /
  完全无行政区划 —— 后三类必须断言**该填的是空的**（"填错率为 0"就靠这个度量）。
- 组件：新建 `AddressFormDialog.spec.ts`（该文件此前不存在；现有覆盖只有
  `AccountView.spec.ts` / `CheckoutView.spec.ts` 里"点按钮弹出弹层"这种很浅的层次）。
  必须钉住 Q16=A 的**反面**——"未识别到的层级保持客户原值"，这是最容易写错、后果最重的一条。
- e2e 不加：见 plan.md 的测试策略一节。

## R13 —— 地区树加载失败时怎么办？

**决策**：**识别入口整体不可用，并复用既有那条错误提示。**

- `AddressFormDialog.vue` 已经有 `treeError`（`地区数据加载失败，请关闭后重试`），
  且此时三级下拉本来就是空的。没有树就没有解析依据，此时若还允许点「自动识别」，
  只会得到一次"未识别到"的误导性反馈。
- 所以：`tree` 为空或 `treeError` 非空时，**识别按钮禁用**并说明原因（US2 场景 3）。
- **不新增**任何"降级方案"（比如内置一份兜底区划）—— 那正好是 FR-118 禁止的事。

# Feature Specification: 收货地址自动解析

**Feature Branch**: `004-address-auto-parse`
**Created**: 2026-10-12
**Status**: Draft
**Input**: User description: "添加地址得时候增加 解析地址功能，可以自动解析放到对应得省市区县位置"

> 编号续 003：本规格从 **FR-116 / SC-042 / US1 / Q15** 接着往下排
> （003 排到 FR-115 / SC-041 / Q14）。

## 背景

现在 C 端新增一条收货地址，要在「所在地区」里**逐个下拉选三次**（省 → 市 → 区），
再把街道门牌手打进「详细地址」。

而客户拿到地址的实际场景几乎都是**一整串文本**：从旧商城复制的、微信里对方发来的、
聊天记录里翻出来的，形如「浙江省杭州市余杭区文一西路 969 号」。客户必须自己把这一串
拆成「省 / 市 / 区」三段再去三个下拉里找——每次都得做一次人肉切分，且省市重名、简称、
缺后缀会让客户在下拉里找很久。

本特性让客户把整段地址贴进来，系统自动识别并填好省市区，剩下的部分落进详细地址。

## Clarifications

### Session 2026-10-12

- **Q15 识别的触发方式 → 表单里给一个专门的「粘贴整段地址」输入框 + 「自动识别」按钮。**
  客户把整段地址粘进**这个专门的框**，点按钮才识别。**MUST NOT** 让识别在客户往「详细地址」
  里打字时自动触发 —— 客户常常只想手打详细地址，自动改写会让他措手不及，也会把
  FR-121「不擅自修改」的边界搅浑。
- **Q16 识别结果与已填内容的冲突 → 识别到什么就覆盖对应字段，识别不到的保持原值。**
  客户刚粘进来的那串文本就是他要的地址（Q15 已保证识别是**显式触发**的，不存在误触），
  所以覆盖是符合直觉的。误识别由 FR-123 的「撤销」兜底 —— 不做"只填空字段"那种半吊子行为：
  那会让改地址的客户觉得"识别没反应"，还得先手工清掉旧值，反而更麻烦。
- **Q17 「详细地址」是否也由识别填充 → 省市区 + 剩余文本都填。**
  扣除行政区划后剩下的「文一西路 969 号」直接落进详细地址。只填省市区等于客户还要把这段
  手打一遍，本特性就只剩"省了三次下拉"；而且那段原文一旦被丢弃，客户连原文都没了。

- **Q18 一级行政区划都认不出来时，详细地址也不回填 → 不回填。**
  Q17=A 要求把剩余文本回填详细地址，于是"完全没识别到行政区划"时冒出一个岔路：整段文本
  算不算"剩余文本"？定为**不回填**—— 连一级行政区都认不出来，说明这次解析不可信，
  此时动详细地址等于拿一次不可信的解析去覆盖客户已填的内容。客户粘的原文还在识别输入框里，
  要手打也有原文可抄，并不丢东西。
  📌 这条最初（2026-10-12 早）是规格里**按一致性推出来的规则**、所有者未表态；
  同日经 `/speckit-analyze` 判为违反宪法原则 II（MUST 澄清不得猜测）后，**由所有者明确确认**，
  自此是正式决策而非推定。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 粘贴一整条地址，自动填好省市区 (Priority: P1)

客户在「新增收货地址」弹层里粘贴一条完整地址，触发自动识别后，三级地区选择被自动选中，
剩余文本被填进详细地址。客户只需再补收件人与手机号即可保存。

**Why this priority**: 这是本需求的核心价值——省掉三次下拉与一次人肉切分。没有它这个功能不存在。

**Independent Test**: 打开新增地址弹层 → 粘贴「浙江省杭州市余杭区文一西路 969 号」→ 触发识别
→ 观察三个地区下拉与详细地址被正确填充 → 保存成功。

**Acceptance Scenarios**:

1. **Given** 已打开新增收货地址弹层，**When** 粘贴「浙江省杭州市余杭区文一西路 969 号」并触发识别，**Then** 省=浙江省、市=杭州市、区=余杭区被选中，详细地址=文一西路 969 号
2. **Given** 地址写成「浙江杭州余杭区文一西路969号」（省市区都没有「省/市」后缀、无空格），**When** 触发识别，**Then** 仍定位到与场景 1 相同的省 / 市 / 区
3. **Given** 直辖市地址「北京市朝阳区建国路 88 号」，**When** 触发识别，**Then** 在该直辖市实际的层级结构上正确定位（不因文本里没有「市」这一级而失败）
4. **Given** 识别成功，**When** 客户直接点「保存」，**Then** 保存成功且存下的地区编号与识别结果一致（不需要客户再动地区下拉）

---

### User Story 2 - 识别不全或识别不出来时，不破坏客户已填的内容 (Priority: P2)

识别不可能万无一失：地址可能只写到市、区县可能已撤并、也可能整段就是「某某小区 3 号楼」
根本没有行政区划。这时系统必须**保持客户原有输入不变**，并**说清楚识别到了什么、没识别到什么**，
让客户能接着手动补。

**Why this priority**: 覆盖失败路径。这里做不好会毁掉客户已经填好的内容——比没有这个功能更糟。
它独立于 US1：即使识别完全失效，也必须不添乱。

**Independent Test**: 先手动选好「广东省 / 深圳市 / 南山区」，再粘一段无法识别的文本触发识别，
确认三级选择原样保留、且页面给出说明。

**Acceptance Scenarios**:

1. **Given** 表单里已手动选好「广东省 / 深圳市 / 南山区」，**When** 粘贴一段完全无法识别出行政区划的文本并触发识别，**Then** 三级选择保持原样不变，并提示未识别到行政区划
2. **Given** 粘贴的地址只能识别到「浙江省 / 杭州市」（文本里没有区），**When** 触发识别，**Then** 省、市被填上，区**保持客户原值**（原为空就仍为空），并提示区县未识别到
3. **Given** 地区数据加载失败（后台接口不可用），**When** 客户触发识别，**Then** 不执行识别，并告知地区数据不可用——不产生任何错误的填充

---

### User Story 3 - 识别结果可整体撤销 (Priority: P3)

识别可能猜错。客户需要一个「退回识别前」的动作，而不是逐字段手工改回去。

**Why this priority**: 提升容错。即使没有它，在 US2 的保障下客户仍能手工修正，所以优先级最低。

**Independent Test**: 触发一次识别后点「撤销」，确认三级选择与详细地址回到识别前的内容。

**Acceptance Scenarios**:

1. **Given** 刚刚触发过一次识别，**When** 点「撤销识别」，**Then** 省 / 市 / 区与详细地址回到识别前的内容
2. **Given** 撤销后又触发了一次新的识别，**When** 再点撤销，**Then** 回到**最近一次**识别前的内容

---

### Edge Cases

- 粘贴文本首尾有空白、中间有换行、有连续多个空格
- 省名用简称或带后缀不一致：「浙江省」/「浙江」、「广西壮族自治区」/「广西」、「香港特别行政区」
- 文本里出现**多个候选行政区**（例如详情里写着「从浙江发到广东，收货在杭州」）
- 识别出的区/县在行政区划树里**同名但归属不同**（不同市下有同名区）
- 通篇没有行政区划，只有「某某小区 3 号楼」
- 文本里混着收件人姓名与手机号
- 处于**编辑已有地址**状态时触发识别（表单里已有值）
- 识别出的最小层级就是该地区树的叶子（例如区县下面还有更细一级时按树的实际结构取到哪一级算哪一级）

## Requirements *(mandatory)*

### Functional Requirements

> **术语**：下文「区」「区县」「区 / 县」均指**同一层级** —— 行政区划树的第三级（`area.csv` 的 type 4，如「余杭区」）。
> 「省 / 市 / 区」是这三级的口语简称，与「省 / 市 / 区县」同义，不是两件事。

- **FR-116**: 新增 / 编辑收货地址的弹层 MUST 在表单里提供一个**专门用来粘贴整段地址的输入框**，以及一个**「自动识别」按钮**（Q15=A），接收客户粘贴或输入的整段地址文本
- **FR-117**: 系统 MUST 从该文本中识别出省、市、区县三级行政区划，并在既有三级联动控件里选中对应项
- **FR-118**: 识别 MUST 依据**后台提供的行政区划数据**，MUST NOT 在客户端内置行政区划清单（宪法原则 III）
- **FR-119**: 系统 MUST 把文本中扣除行政区划后的剩余部分填入「详细地址」（Q17=A）——一次识别就让整段文本全部就位，客户只剩收件人与手机号要补
- **FR-120**: 当文本只能识别到部分层级时，系统 MUST 只填写识别到的层级，其余层级保持客户原值，并明确提示哪些层级未识别到
- **FR-121**: 当完全无法识别出任何行政区划时，系统 MUST NOT 修改表单的任何字段——**包括「详细地址」**：一级行政区都认不出来，说明这次解析不可信，此时整段文本本就处于"没有被行政区划切开"的状态。因此 FR-119 的「剩余文本回填详细地址」**只在至少识别到一级行政区划时才发生**。客户粘的原文仍留在识别输入框里，不会丢（**Q18=A**，2026-10-12 所有者确认）
- **FR-122**: 识别 SHOULD 容忍常见书写差异：缺少「省 / 市 / 区 / 县」后缀、全角半角混用、多余空白与换行
- **FR-123**: 识别结果 MUST 可被客户一键撤销，恢复到该次识别前的完整表单状态
- **FR-124**: 识别 MUST 只在客户**显式点击识别按钮**时执行（Q15=A）；MUST NOT 在客户往「详细地址」输入或粘贴时自动触发，也 MUST NOT 读取剪贴板
- **FR-125**: 识别结果 MUST 覆盖对应字段（Q16=A）：识别出省 / 市 / 区就覆盖已选的省 / 市 / 区，识别出剩余文本就覆盖详细地址；**未识别到的字段保持客户原值不变**，误识别由 FR-123 的撤销兜底
- **FR-126**: 识别 MUST NOT 引入任何新的第三方地址数据源或外部服务；行政区划一律取自既有后台接口
- **FR-127**: 本特性 MUST NOT 改变地址表单既有的五字段必填校验与保存行为（收件人 / 手机号 / 所在地区 / 详细地址 / 是否默认，见 FR-027）
- **FR-128**: 识别 MUST NOT 试图识别收件人姓名与手机号——本期只处理行政区划与详细地址（理由见 Assumptions）

### Key Entities *(include if feature involves data)*

- **行政区划节点**：`编号` / `名称` / `层级` / `子节点`。来源是后台既有接口，客户端只读不写、不缓存于代码中。
- **收货地址**：`收件人` / `手机号` / `地区编号`（取已选中的最小层级，直辖市可能只到市级）/ `详细地址` / `是否默认`。既有实体，本特性**不改变其结构**。
- **识别结果（仅存在于表单交互过程中，不落库）**：`命中的省/市/区节点` / `剩余文本` / `未识别到的层级`。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-042**: 用一批覆盖常见书写习惯的地址样本（省市区齐全 / 缺后缀 / 直辖市 / 只到市 / 只到省 / 完全无行政区划，**「齐全」类 ≥5 条、其余每类 ≥2 条、合计 ≥20 条**）跑识别：**填错的条数为 0**（宁可少填、不可填错），其中「省市区齐全」那一类的正确填写率 ≥ 90%。
  样本集 MUST 成文固定（自动化侧 = `address-parse.spec.ts` 的表驱动用例集，人眼侧 = [quickstart.md](./quickstart.md) §五）——**分母固定，结果才可复现**
- **SC-043**: 客户从「粘贴一整段地址」到「地址表单可以保存」的交互次数，相比现在减少至少 2 次（现在必须做满三次地区下拉）
- **SC-044**: 因识别动作而丢失客户已填写内容的次数为 **0**
- **SC-045**: 客户触发识别到表单显示出结果，**全程不出现任何加载态**（识别期间页面上不出现 loading、按钮禁用、骨架屏）—— 这是"感知为即时"的**可观察判据**，可在组件测试中断言。
  📌 **计时不做自动化验证**，理由：CI 上的毫秒级断言必然 flaky；而本特性是固定 ~3.6k 节点的纯内存字符串匹配，不存在数量级风险。人眼核对见 [quickstart.md](./quickstart.md) §一。
  （宪法原则 V 要求"不打算验证的标准 MUST 显式写出并说明理由"—— 上面这句就是那条声明。）
- **SC-046**: 行政区划数据的唯一来源仍是后台接口——交付物中客户端内置的行政区划条目数为 **0**

## Assumptions

- **本期只做 C 端 Web 前台（`storefront`）**。小程序 / App 端（`yudao-ui-mall-uniapp`）不在本期范围
  —— 沿用 003 已确立的先例（`specs/003-product-filter-dimensions/spec.md:413`）。
- 本特性只在「新增 / 编辑收货地址」弹层内生效，不涉及结算页的其他字段。
- 行政区划继续来自既有后台接口 `/app-api/system/area/tree`；本特性不新增、不替换任何行政区划数据源。
- **不识别收件人姓名与手机号**：客户只要求「省市区县」；姓名与手机号混在整段文本里歧义大
  （「张先生」「13800138000」可能属于寄件人、可能是备注），猜错比不猜更糟。
- 识别在客户**显式触发**时执行，不会在客户输入过程中后台自动改写其内容。
- 地区数据加载失败时识别不可用——与现有地区下拉同源、同命运。
- 识别结果只是**表单里的一次草稿**，落库仍走既有保存链路；本特性不改变存储结构。

# 契约：管理端接口（`/admin-api`）

> 本特性的管理端改动**很小**：只是把会员的「公司名称」露出来（Q24：运营在后台也 MUST 能看到）。
> 路径前缀一律 `/admin-api`（宪法：管理端 MUST NOT 走 `/app-api`）。

---

## 1. 变更的既有接口

### `GET /system/...` 无关；下面是会员模块

| 端点 | 变化 |
|---|---|
| `GET /member/user/page` | 返回多一个 `company` 字段 |
| `GET /member/user/get?id=` | 同上 |
| `PUT /member/user/update` | 接受 `company`（后台可代客户更正） |

```json
{ "id": 1234, "nickname": "张三", "mobile": "13800138000", "company": "某某印刷厂" }
```

**约束**

- `company` **可空** —— 存量会员全部为空，后台页面 MUST NOT 把它显示成必填或报错
- 后台**只做展示与更正**，不参与任何鉴权 / 定价（规格 Assumptions 已明确）

---

## 2. ⚠️ 前置配置：**社交平台**（不是接口改动，但属管理端动作）

这一条**不是代码**，却是整个特性能否跑通的前提（见 plan.md 的「前置阻塞」）：

| 要做的事 | 在哪 |
|---|---|
| 新增一条社交平台配置：类型=**微信公众号**、**用户类型=会员**、填**真实公众号**的 appid / secret | 后台「系统管理 → 社交平台 → 新增」（表单里本来就有"用户类型"单选框） |
| 配好**网页授权域名** | 微信公众平台后台 |

**实测现状（2026-10-12，不能跳过）**：`system_social_client` 里的公众号配置**两条 `user_type` 都是 1（管理员）**，
**没有会员那条**；于是 C 端会**回退到 yaml**，而线上跑 `local,my`，那份 yaml 指向的是注释写着
「**测试号（自己的）**」的 `wx5b23ba7a5589ecbb` —— **测试号只对体验者白名单开放，真实客户用不了**。

**所以：先配、先真机扫一次验证，再写代码。** 这一条不通过，后面全是白做。

## 3. 明确不改的管理端

- 「会员等级 / 标签 / 积分」等页面：不动
- 「社交平台」的**既有两条管理员配置**：不动（它们服务的是后台登录，与本特性无关）
  ⚠️ 但值得单独留意：这两条同为 `type=31, user_type=1` 且都启用，
  而查找用的是 `selectOne` —— **同类型同用户类型存在多条时行为不确定**。
  这是**既有问题**，不是本特性引入的；本特性不碰它，但实施时若撞见不要顺手改（原则 IV：发现无关问题只指出、不自行处理）。

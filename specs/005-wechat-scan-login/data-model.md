# 数据模型：微信扫码登录与首次登录补全资料

> 本特性**只动一处表结构**：`member_user` 加一列 `company`。
> 其余全是既有表的**新增用法**，以及一个**只活在 Redis 里的临时票据**（不进库、不进备份）。

---

## 1. 会员 `member_user`（既有表，**加一列**）

现状（线上 `information_schema` 实查）：`mobile` **可空**、`nickname` / `avatar` **非空**、
**没有**任何能承载"公司名称"的列。

| 字段 | 变化 | 说明 |
|---|---|---|
| `mobile` | **不变**（仍可空） | 但本特性之后，**经微信登录进来的会员一定有值**（FR-150：补全提交成功才建号） |
| `nickname` / `avatar` | 不变 | 自动建号时必须给值 —— 优先用微信带来的昵称/头像，拿不到则用默认值 |
| **`company`** | **新增** | `varchar(64) NULL`，注释「公司名称」。**可空**：它是选填项，且既有 282+ 个存量会员都没有 |
| `register_terminal` | 复用 | 记「微信登录」，便于日后统计来源 |

**不变量**

- 走完补全页建出来的会员，`mobile` **一定不为空**（否则违反 FR-150 的时序）
- `company` 是**展示性信息**，不参与任何业务规则（不用于定价 / 开票 / 权限），见规格 Assumptions

**⚠️ `nickname` 与 `avatar` 非空** 是个容易踩的点：若微信授权只给了 openid（`snsapi_base`），
建号时必须自己补默认值，**不能直接塞 null**。

---

## 2. 社交身份 `system_social_user`（既有表，只读用法）

一条"**这个 openid 是谁**"，**不代表它属于哪个会员**。

| 字段 | 说明 |
|---|---|
| `type` | 社交平台类型。本特性用 **31（WECHAT_MP）** |
| `openid` | 微信身份。**本特性的核心凭据载体** |
| `nickname` / `avatar` | 微信侧带来的资料；补全页的默认头像就取自这里 |

**关键区分**（SC-055 就是钉这个）：扫码换 openid 时**可能落一条身份记录但没有任何绑定** ——
那是正常产物，**不是**"偷偷建了个会员"。断言时把这两个概念分开算。

---

## 3. 社交绑定 `system_social_user_bind`（既有表，**Q21=C 改变了写入规则**）

`会员 ↔ 社交身份` 的关联表。本特性对它只有一个要求，但是**硬要求**：

> **一个会员最多只能有一条「同一社交类型」的绑定。后来的必须被拒绝，不许顶掉先来的。**（Q21=C / FR-146）

**⚠️ 这就意味着不能走既有的 `bindSocialUser`** —— 它内部有两次**无条件解绑**
（`SocialUserServiceImpl.java:71-76`），第二条正是"该会员原先绑过别的社交账号 → 解绑"。
复用它不会报错，只会让**先绑的那个微信号从此登不进去**（详见 research.md R17）。

| 场景 | 正确行为 |
|---|---|
| 会员从没绑过微信 | 插入一条绑定 |
| 会员已绑过**同一个**微信 | 幂等（本来就该登进去） |
| 会员已绑过**另一个**微信 | **拒绝**，告知"该账号已绑定其他微信"（SC-053） |
| 该微信已绑过**另一个**会员 | 按 Q20/Q22 的路径走：这属于"手机号命中既有会员"的合并判断，不是这里 |

## 4. 登录票据（**新增，只在 Redis**）

一次"待扫"的临时任务。**不进数据库、不进备份、不进任何业务查询。**

| 字段 | 说明 |
|---|---|
| `ticket` | **键名本身**。必须密码学随机、不可推导（FR-149） |
| `state` | 微信授权回调用的防伪串；**与 ticket 不是同一个值**（R19） |
| `status` | **唯一口径（5 个）**：`待扫 / 待补全 / 已完成 / 已过期 / 已作废`。见下方说明 |
| `openid` | 扫码者身份。**Q26 之后它先住在这里**，提交补全页时才变成会员与绑定 |
| `wxNickname` / `wxAvatar` | 补全页的默认展示值（拿不到则为空） |
| `memberId` | 完成后才写入 |
| `token` | 完成后才写入（PC 轮询到这里才算登录成功） |
| TTL | **5 分钟**（FR-152 的默认值，计划实施时按微信侧实际寿命确认） |

**状态转移**

```
待扫 ──手机侧授权完成（code 到达）──> 待补全 ──提交成功──> 已完成 ──(轮询取走 token)──> 删除
  │                                     │
  └──────────── 超时 ───────────────────┴──> 已过期
                                        └── 客户关闭补全页 ──> 已作废
```

**📌 为什么没有「已扫待确认」（2026-10-12 去掉）**：
公众号**网页授权不回调"用户已扫"这个事件** —— 从客户扫码到服务端拿到 code，中间是**微信自己的页面**，
我们的服务端一无所知。能被观测到的第一个变化就是"code 到了"，也就是 `待补全`。
原先在 FR-144 / 本文 / 契约里写的"已扫待确认"是一个**观测不到的状态**，留着只会让实现去猜一个不存在的时刻。
（三处的状态集此前还各不相同：FR-144 列 4 个、本文列 6 个、契约列 5 个 —— 现已统一为这 5 个。）

**不变量**

1. **不可猜测**：ticket MUST NOT 由自增 / 时间戳 / 会员编号等可推导的值构成（FR-149）
2. **一次性**：`已完成` 之后 MUST 立刻失效 —— 轮询取走 token 后即删
3. **短存活**：TTL 到即 `已过期`，提交与轮询都必须能识别并给出明确提示（FR-140 / FR-152）
4. **`已完成` 之前，票据里 MUST NOT 出现 `memberId` 或 `token`** ——
   这是 FR-150（提交成功前不建会员、不签发登录态）在数据层面的样子
5. 票据里**只存 openid，不存 code** —— 微信的 code 一次性且短命（R16）

## 5. 关系总览

```
微信 openid ──(票据暂存，5min)──> 补全页提交 ──┬── 手机号是新的 ──> 新建 member_user（含 company）
                                              └── 手机号已存在 ──> 复用它，并校验验证码
                                                        │
                                                        └──> 写 system_social_user_bind（会员 ↔ openid）

member_user.company  ── 前台「个人资料」可看可改、后台可见（Q24）
```

**四处最容易被写错的地方**（每一处都有对应的验收标准）：

1. 在补全页提交**之前**就把会员建出来了 → 违反 FR-150，SC-049 会挂
2. 复用 `bindSocialUser` 导致**静默解绑**先绑的微信 → 违反 FR-146，SC-053 会挂
3. 把"社交身份"当成"社交绑定"来断言增量 → SC-055 的注释专门说了这件事
4. `nickname` / `avatar` 非空，微信没给资料时直接塞 null → 建号失败

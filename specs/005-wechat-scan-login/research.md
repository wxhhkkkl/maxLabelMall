# 技术决策与被否决方案

Phase 0 调研结论。编号 **R15~R24** 接着 003 的 R14 往下排。

---

## R15 —— 「微信扫码登录」怎么实现？**公众号网页授权 + 票据轮询**

**决策**：二维码的内容是**公众号网页授权的地址**（带一个一次性的 `state`）。客户用微信扫码 →
在**手机的微信里**打开授权页 → 点允许 → 微信回跳到我们域名上的一个页面（带着 `code` 与 `state`）→
该页面把 code+state 交给服务端 → 服务端换 openid、把票据标成"待补全" → **电脑端轮询到结果**。

**为什么不能更简单**：yudao 只有 `social-auth-redirect` + `social-login`，那是"**在微信里打开本站**"
的流程（手机端一条龙）。PC 扫码登录多出来的**就只是"把结果送回电脑"这一段**，所以票据 + 轮询是必需的，
不是多余设计。

**被否决的方案**：
- **微信开放平台的"网站应用扫码登录"（`qrconnect`）** —— 那是**另一个产品**（开放平台网站应用），
  需要单独申请，与所有者说的"**公众号**的三方应用信息"不是一回事。所有者已配好的是公众号。
- **让客户手动把手机上的结果敲到电脑上**（验证码式）—— 反而比扫码更麻烦。
- **只在手机微信内做，PC 不做** —— 被 Q19 否掉（客户大多在电脑前看货）。

**既有可照搬的骨架**：`storefront/src/components/QrPayDialog.vue` —— 它已经把
"显示二维码 → 定时轮询 → 停止条件"这套做过一遍（当前用于扫码**支付**）。照它的骨架来，别另起一套。

## R16 —— 绑定只能按 code，**必须新增"按 openid 绑定"**

**决策**：**新增一条按 openid 绑定的服务端能力**，不复用现有的按 code 绑定。

**已实查**（`SocialUserServiceImpl.java`）：

| 能力 | 现有入口 | 接受什么 |
|---|---|---|
| 绑定 | `bindSocialUser(SocialUserBindReqDTO)` | **只接受 `code`**（内部 `authSocialUser(type, userType, code, state)` 换 openid） |
| 解绑 | `unbindSocialUser(userId, userType, socialType, openid)` | openid |
| 查身份 | `socialUserMapper.selectByTypeAndOpenid(socialType, openid)` | openid |

也就是说：**按 openid 查、按 openid 解绑都有，唯独按 openid 绑没有。**

**为什么这条现在才变关键**：Q26 把"建号 + 绑定"推迟到了提交补全页那一刻，而那时离扫码已经过去一段时间。
微信的授权码是**一次性且短命**的。所以正确做法是：**扫码那一刻就把 code 换成 openid 存进票据**，
提交时按 **openid** 去建号与绑定。若照旧按 code 绑，客户在补全页上多停留几分钟就会失败。

## R17 —— **绝不能复用 `bindSocialUser`**（它会静默顶掉先绑的微信）

**决策**：新写绑定路径，**绕开** `bindSocialUser`。

**已实查**（`SocialUserServiceImpl.java:71-76`），它内部有两次**无条件**解绑：

```java
// 社交用户可能之前绑定过别的用户，需要进行解绑
socialUserBindMapper.deleteByUserTypeAndSocialUserId(...);
// 用户可能之前已经绑定过该社交类型，需要进行解绑     ← 就是这条
socialUserBindMapper.deleteByUserTypeAndUserIdAndSocialType(...);
```

第二条**正是 Q21=C 明令禁止的行为**（后绑的不许静默顶掉先绑的）。

**它为什么危险**：复用它不会报错、不会有异常、数据看着全对 —— 唯一的症状是
**先绑的那个微信号从此登不进去了**，而且没有任何提示。这种 bug 极难从现象倒查回来。

**替代做法**：绑定前先查"该会员是否已绑过同类型的社交账号"，
**有则拒绝并告知**（FR-146 / SC-053）。

## R18 —— 票据存哪、活多久？

**决策**：**Redis**，键名不可猜测，存活 **5 分钟**。

- 存 Redis 而不是 MySQL：它是一次性的临时凭据，**不该落库**（既不进备份，也不该有历史）。
- 存活 5 分钟：与 FR-152 的默认值一致，也与微信授权码的寿命量级相当。
  ⚠️ **这个 5 分钟是规格自行补的默认值**（不是所有者表态），计划实施时按微信侧实际寿命最终确认。

## R19 —— 票据的状态机、不可猜测、一次性

**决策**：状态机 `待扫 → 已扫待确认 → 待补全 → 已完成`，另有终态 `已过期` / `已作废`。

三条硬要求（FR-149，来自"票据在待补全期间等价于凭据"这个事实）：

1. **不可猜测** —— 必须是密码学随机的串，MUST NOT 用自增、时间戳、会员编号等可推导的值
2. **一次性** —— 完成后立刻失效，重放拿不到第二次
3. **短存活** —— 过期即失效

**被否决的做法**：用二维码里的 `state` 直接当票据。`state` 会出现在二维码内容与回跳 URL 里
（可能被截图、被日志记录），而票据是等价凭据 —— 两者不该是同一个值。

## R20 —— 延后建号之后，token 什么时候签发？

**决策**：**补全页提交成功的那个事务里才签发**。

于是：

| 时刻 | 有会员吗 | 有登录态吗 |
|---|---|---|
| 扫完码、还没填 | **没有** | 没有 |
| 填了但验证没过 | **没有** | 没有 |
| 提交成功 | 有（新建或原有） | **有** |

**这条同时消掉了三个东西**：僵尸会员（SC-049 回到字面意思）、"关掉补全页 = 退出登录"那套机制
（FR-148 变成"什么都没发生"）、以及"拦住已登录用户"的闸门（FR-134 变成事实而非机制）。

**代价**：服务端要新增一条"先识别、后建号"的编排，不能复用 `socialLogin`（它一扫码就建号）。

## R21 —— 「公司名称」放哪？

**决策**：`member_user` **加一列** `company`（varchar，可空）。

- 已实查：`member_user` 现有字段里**没有任何**能承载它的（`mark` 是会员备注，语义不同）
- 它是**会员档案的一项**（Q24），所以跟着会员走最自然
- **加列**而不是新建扩展表：只有一个字段，为它建一张表属于为单字段引入抽象层（原则 IV）

## R22 —— 头像为什么必须"提交后才传"？

**决策**：补全页**默认带微信头像**；客户自选的图先留在浏览器里，**提交成功之后再上传**。

**已实查**：`AppFileController.uploadFile` **没有 `@PermitAll`** → **要求登录**。
而补全页出现时客户**尚未登录**（R20）→ 传不了。

**被否决的做法**：把上传接口放开为免登录 —— 那等于**任何人都能往对象存储里灌文件**，
为一个体验细节打开一个公开写入口，代价远大于收益。

## R23 —— 轮询的心跳与停止条件

**决策**：照 `QrPayDialog` 的骨架；**必须有停止条件**，不能无限轮询（FR-144）。

要处理的：完成时停、过期时停、组件卸载时停。**还必须有兜底** —— 网络抖动 / 响应变慢时
MUST NOT 把请求叠起来（`QrPayDialog` 的注释里已经写明这个坑，照抄它的做法）。

## R24 —— 微信那部分怎么测？

**决策**：**把"能测的"和"不能测的"切开**，不假装能测微信。

| 能不能测 | 内容 |
|---|---|
| **能**（服务端单测） | 票据状态机；提交补全的三个岔口（建号 / 合并 / 拒绝重复绑定）；验证不过则什么都不建 |
| **能**（storefront 单测） | 轮询停止条件；补全页的三条提示；关闭即作废 |
| **不能**（外部系统） | 微信授权本身、真机扫码 —— 靠 quickstart 的人工清单 |
| **不做** | e2e（要真微信环境，成本远高于收益） |

**关键**：把"扫码之后"的所有逻辑都做成**可以不带微信测**的 —— 票据的输入是"一个 openid"，
而 openid 在单测里就是**一个字符串**。这样整条链路里唯一测不了的就只剩"微信给不给这个 openid"。

# Feature Specification: 微信扫码登录与首次登录补全资料

**Feature Branch**: `005-wechat-scan-login`
**Created**: 2026-10-12
**Status**: Draft
**Input**: User description: "前端用户需要可以兼容微信扫码登录，已经在后台配置好了微信公众号的三方应用信息，完后用户登录后如果没有手机号需要让用户必须填写手机号，和选填公司名称、头像等基础信息，如果手机号之前注册过那openid和原有用户绑定，如果没注册过那就注册成新用户，二次登录的时候如果有手机号就不需要再填写手机号了"

> 编号续 004：本规格从 **FR-129 / SC-047 / US16 / Q19 / R15** 接着往下排
> （004 排到 FR-128 / SC-046 / US3 / Q18 / R13）。

## 背景

现在 C 端只有两种登录方式：**手机号 + 验证码**、**手机号 + 密码**（见登录弹层的「验证码登录 / 密码登录」两个页签）。
客户第一次来必须先在手机上收一条短信才能进门 —— 而我们的客户大多是在电脑前看货的 B 端商家，
给他们加的每一条短信都是一次摩擦（还要花钱）。

公众号的三方应用信息已经配好了，仓库里也已经有 `social-login` / `social-auth-redirect` 这条路
（目前只服务于微信 JSAPI 支付拿 openid）。本特性把它接成**一条正式的登录入口**：

- 电脑上开口子 → 用微信扫 → 就进来了，不用等短信
- 第一次来的客户**先补手机号、再成为会员**（Q26）—— 没有手机号就没法发货、也没法联系，
  所以「补全」这一步既是采集资料，也是注册本身
- 补手机号时如果这个号**本来就是我们会员** → 把微信身份绑到**原来那个账号**上（积分/订单/地址都得跟着回来），
  而不是傻乎乎地再建一个空号
- 补过一次之后，以后再扫码就直接进，不再问

## 已核实的事实（写规格时查过，避免在错误前提上设计）

| 事实 | 出处 |
|---|---|
| **既有 `social-login` 目前根本没有被前台调用**（`storefront/src` 全仓搜 `social-login` / `socialLogin` 零命中）。它内部是"一扫码就 `createUser` + 绑定"，与本规格的"填完补全页才建号"（Q26）**相反** —— 所以本特性**另起一条路径，也不去改它**（原则 IV）。它另一半（**已绑定的 openid 直接读用户**）可以复用 | `MemberAuthServiceImpl.java:110-127` vs Q26 |
| 真正在被使用的是 `bindSocialUser` / `getSocialAuthRedirectUrl` —— `OrderDetailView` 的**微信 JSAPI 支付 openid 绑定**链路。本特性 MUST NOT 破坏它 | `storefront/src/views/OrderDetailView.vue` |
| 会员模块已有 `update-mobile`、`update-mobile-by-weixin`、`update`（资料）等 app 接口 | `AppMemberUserController` |
| 社交绑定表是 `system_social_user` / `system_social_user_bind`（不是 `member_*`） | 线上库实查 |
| 公众号的社交类型码是 **31**（`WECHAT_MP`） | `api/social.ts:19`；`SocialTypeEnum` |
| 前台已有"跳授权 → 用 code 换 openid → 绑定"的前端封装 | `storefront/src/api/social.ts` |
| 前台已有"PC 显示二维码 + 定时轮询结果"的现成范式（当前用于**扫码支付**） | `storefront/src/components/QrPayDialog.vue` |
| ⚠️ **绑定目前只能按授权码（code）**：`bindSocialUser` 内部先 `authSocialUser(type, userType, code, state)` 用 code 换 openid，**没有"按 openid 绑定"的入口**（而按 openid **查询**与**解绑**是有的：`selectByTypeAndOpenid` / `unbindSocialUser`） | `SocialUserServiceImpl.java:62-66` |
| → **Q26 之后这条必须补齐**：提交补全页时离扫码已过去一段时间，微信的授权码是**一次性且短命**的，很可能已经失效。所以计划阶段需要新增一条「**按 openid 绑定**」的能力；否则延后建号会在提交那一步卡死 | 本规格 |
| ⚠️⚠️ **`bindSocialUser` 内部有两次「无条件解绑」**：① 该社交身份原先绑过别的会员 → 解绑；② **该会员原先绑过别的社交账号 → 解绑** | `SocialUserServiceImpl.java:71-76` |
| → 第 ② 条**正是 Q21=C 明令禁止的行为**（后绑的不许静默顶掉先绑的）。所以 **FR-146 / SC-053 绝不能复用这个方法** —— 一复用就会被静默违反，而且违反得无声无息（数据看起来是对的，只是先绑的那个微信登不进去了） | 本规格 |
| **`member_user` 里没有"公司名称"这一列**（现有可用的资料字段：`nickname` 必填、`avatar` 必填、`name` 真实姓名、`sex`、`area_id`、`birthday`、`mark` 备注） | 线上库 `information_schema` 实查 |
| 会员手机号是**可空**的（`mobile varchar(11) NULL`）—— 所以"没手机号的会员"是系统里真实存在的状态，不是假想 | 同上 |
| 仓库里**没有任何**二维码登录 / 票据轮询的实现 | 全仓搜索 `qrconnect`/`scanLogin`/`ticket` 无命中 |

**结论**：真正要新建的是三件事 —— ①**扫码登录这条链路本身**；②**"先补全、后建号"的补全页**
（Q26 之后它不是"拦住已登录用户"的闸门，而是**建号那一步本身**）；
③**手机号命中既有会员时的合并绑定**（既有的 `socialLogin` 在"未绑定"时一律建新号，**不会**按手机号找原账号）。

## Clarifications

### Session 2026-10-12

- **Q19 电脑端扫码的交互形态 → 扫完电脑「自动」登录。**
  这要求服务端有一套「登录票据」机制（签发 / 查询 / 过期 / 归属），前端在二维码展示期间轮询它。
  仓库里**没有**这类实现；但 `QrPayDialog.vue` 的「二维码 + 定时轮询」是同类范式，可照它的骨架来
  （宪法原则 III：先看既有范式，别另起一套）。
  **不采用**「扫完在电脑上手动点确认」：多一次点击，而且"点了但没绑上"还得额外解释。
- **Q20 补手机号命中既有会员时 → 必须短信验证。**
  客户**手打**的手机号不等于他拥有这个号。没有验证，任何人只要知道某位客户的手机号，
  就能用自己的微信登录、填上那个号、**接管对方账号** —— 看得见订单、收货地址、积分。
  验证复用**既有**的发码与校验能力，不新造一套。
  代价：老客户首次绑定时仍要收一条短信（一次性）—— 与"省掉短信"的初衷相抵，
  但这条路径换来的是账号不被冒领，值得。
- **Q21 一个会员能否绑多个微信 → 只允许一个，且拒绝时要明确告知。**
  后绑的微信 MUST 被拒绝，并告知"该账号已绑定其他微信"；MUST NOT 静默顶掉先绑的那个
  —— 静默踢人会让先绑的人莫名掉线，且他无从得知原因。
- **Q22 补全的手机号要不要「一律」短信验证 → 要，不分路径。**
  Q20=A 只覆盖了"命中既有会员"那一条。补上另一半：**新号也要验**。
  理由：手机号在本站就是**登录身份**（既有两种登录方式都以它为准），一个没被验证过的登录身份
  会留下"号码被占"的隐患 —— 任何人都能用自己的微信填上别人的手机号先把号占住，
  之后那个号的主人用短信登录时会**落进别人建的账号**里。
  代价其实没有想象中大：**今天所有客户首次登录本来就要收一条短信**，选这条只是维持原样，
  换来的是**此后每次登录都免短信**（登录次数远多于首次）。
  推论：`FR-145` 不再是"特例"，而是 `FR-147` 这条通用规则的一个应用场景。
- **Q23 没手机号时"拦住"到什么程度 → 拦住一切会员功能；关掉补全页即回到匿名。**
  登录后**立即**弹出补全页；在补齐之前，**任何需要登录的功能都不可用**（加购、下单、看订单、看地址……）。
  客户可以关掉它，但关掉就等于**退出登录**，只能以游客身份继续浏览；下次再扫码仍回到补全页。
  📌 **"关掉 = 退出登录"这半句已被 Q26 取代** —— 延后建号之后**根本没有登录态**可退，
  关掉就是让这次扫码彻底作废。留下原文是为了看得出结论是怎么演进过来的。
  **为什么选这条而不是"只卡在下单前"**：所有者的诉求是"必须填手机号"，卡在所有会员功能上最贴合这句话，
  且不会出现"客户逛完、加购、走到结算才被拦"那种更挫败的时序。
  ⚠️ **两条必须一起做到的后果**（否则会留下一个半死不活的状态）：
  ① 关掉补全页 MUST 清掉登录态 —— 不能留下"已登录但没手机号"的中间态；
  ② 因此**匿名浏览必须照常可用**（商城的商品与分类本来就允许游客看），否则关掉之后就无路可走了。
  📌 注意购物车在本项目里**本来就需要登录**，所以选 B 意味着这类客户**也不能加购** ——
  这是刻意的，不是遗漏。
- **Q24 「公司名称」是什么身份 → 会员档案里的一项，前台可见可改。**
  既然要存，就得让客户看得到、改得动 —— 存下来却在任何地方都不露面的字段，客户填一次就会觉得填进了黑洞；
  而且 B 端客户**换公司名、换联系人是常事**，不能让他为此重新注册。所以它进「个人资料」页
  （与昵称 / 头像并列），运营在后台也能看到。落地时是加一列还是别的承载方式，由计划阶段定。
- **Q25 二维码被别人扫走怎么办 → 不加额外提示，与既有登录保持一致。**
  自动登录的固有代价：有人诱导电脑前的人打开二维码、自己用手机扫走并确认，电脑就会登录成**扫码者**的账号。
  微信自己的确认页会显示正在登录哪个应用，这是行业既有的第一道防线；所有者**知悉并接受**不再加"当前登录账号是谁"
  这类提示（Q25=B）。
  ⚠️ 这是一条**显式接受的风险**，不是被忽略的漏洞 —— 它写在这里与 Edge Cases 里，供将来复盘。
- **Q26 扫码后要不要先建会员 → 不建，填完补全页再建。**
  既有的 `socialLogin` 是"一扫码就 `createUser` + 绑定"；本特性改成**先只识别微信身份**
  （openid + 昵称 + 头像暂存在登录票据里），**提交补全页时才建号（或绑到原账号）**。
  收益是把两个别扭的东西一起消掉了：① 库里不会再攒下"没手机号、用不了的僵尸会员"，
  于是 SC-049 可以回到它字面的意思；② Q23=B 原来需要"关掉补全页 = 退出登录"这套机制，
  现在**天然不存在登录态**，关掉就是什么都没发生。
  代价：服务端要新增一条"先识别、后建号"的路径（不能直接复用 `socialLogin`）；
  补全页的头像改为**提交后**才上传（见 FR-135 / FR-151）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用微信登录，不用等短信 (Priority: P1)

客户在电脑上打开商城，点「微信登录」，屏幕上出现一个二维码。他用手机微信扫一下并在手机上点确认，
**电脑上的页面自己就变成已登录状态**。

**Why this priority**: 这是整个特性的入口。没有它后面两步都无从谈起。

**Independent Test**: 在一台未登录的浏览器上打开登录弹层 → 点「微信登录」→ 出现二维码 →
用一个**已经补全过资料**的微信号扫并确认 → 浏览器进入已登录状态、能看到自己的账号。

**Acceptance Scenarios**:

1. **Given** 客户在电脑上、未登录，**When** 点「微信登录」，**Then** 出现二维码，且页面上写着怎么扫
2. **Given** 二维码已显示，**When** 客户用微信扫码并在手机上确认，**Then** 电脑端**无需手动刷新**即进入已登录状态
3. **Given** 这个微信号是第一次来（系统里还没有对应的会员），**When** 扫码确认完成，
   **Then** **不直接进入已登录状态**，而是进入补全页（见 US2）——
   MUST NOT 出现独立的"注册"入口与注册表单，也 MUST NOT 在补全完成前建立任何登录态（Q26）
4. **Given** 客户用手机在微信里打开本站，**When** 点「微信登录」，**Then** **不出现二维码**，直接走微信授权并登录
5. **Given** 二维码已经长时间没人扫，**When** 它失效，**Then** 页面明确提示"二维码已失效"并给出重新获取的动作；MUST NOT 假装还在等待

### User Story 2 - 第一次登录必须补手机号（含选填的公司名称与头像） (Priority: P2)

第一次扫码进来的客户**系统里还没有他的会员**。补全页就是"把会员建出来"的那一步：
必须填手机号 —— 没有手机号我们发不了货、也联系不上。顺带让他选填公司名称和头像。
**提交并验证通过才建号（或绑到原账号）、才登录；关掉就什么都没发生。**
**补过一次之后，以后再扫码就直接进，不再问。**

**Why this priority**: 没有这一步，扫码登录会往库里灌进一批"没有手机号、无法发货"的会员，
反而比要求短信登录更糟。它独立可测：拿一个已补全过的会员扫码，这一步根本不该出现。

**Independent Test**: 用一个从未登录过的微信号扫码 → 出现补全页要求填手机号 →
填一个**站内不存在**的手机号并通过短信验证 → 此刻才建出会员并进入已登录状态；
退出后再扫同一个微信 → **不再出现这个页面**。

**Acceptance Scenarios**:

1. **Given** 该微信号在系统里还没有对应会员，**When** 扫码确认完成，**Then** 出现补全页，手机号**必填**，填不对不让过；
   此时该微信号**尚未**产生任何会员记录（Q26）
2. **Given** 补全页已出现，**When** 客户填好手机号（站点里没有这个号）、收到并填入短信验证码、提交，
   **Then** **此刻才建出会员**（手机号即它填的那个）、建立微信绑定，并**进入已登录状态**
2b. **Given** 补全页已出现，**When** 客户填了手机号但**没通过短信验证**（不填码、填错码、码已过期），
   **Then** 手机号**不被写入**、**不建会员、不建立任何绑定**，客户留在补全页（FR-147 / FR-150）
3. **Given** 该微信号**已经绑定过会员**且该会员已有手机号，**When** 再次扫码登录，
   **Then** **直接进入**，补全页不再出现
4. **Given** 补全页已出现，**When** 客户不填手机号就想跳过，**Then** 进不去（MUST NOT 允许留空继续）
5. **Given** 补全页已出现，**When** 客户填了手机号并通过验证、同时选填了公司名称与头像并提交，
   **Then** 三项都随新建的会员一起保存，且**重新登录后能看到并修改公司名称与头像**
6. **Given** 客户在补全页上把它关掉了，**When** 关闭动作完成，**Then** **什么都没发生** ——
   没建会员、没有登录态，他仍是游客且**可以照常浏览商品与分类**；
   **When** 他下次再扫码，**Then** 仍然回到补全页（MUST NOT 因为"来过一次"就放行）
7. **Given** 客户还没填完补全页（因此也**没有登录态**），**When** 他试图加入购物车或进入结算，
   **Then** 走既有的"未登录"路径 —— 引导登录；MUST NOT 出现"已登录但用不了"的中间态（Q26）

### User Story 3 - 手机号本来就是我方会员时，绑到原账号而不是另建新号 (Priority: P3)

老客户早就在小程序/短信那套里注册过，有积分有订单。他这次用微信扫码进来、补手机号时填的是**原来那个号**。
系统必须把微信身份绑到**原来那个账号**上 —— 他的积分、历史订单、收货地址都得跟着回来，
**不能**凭空多出一个同名同号的新账号。

**Why this priority**: 覆盖老客户，价值高但受众比 US1/US2 窄；做错了后果严重（客户数据裂成两份、
"我的订单"变空），所以必须单独测。

**Independent Test**: 先有一个已有手机号的老会员（有历史订单）→ 用一个从没绑过的微信号扫码 →
补全页填**那个已存在的手机号** → 进入后「我的订单」里能看到此前的历史订单。

**Acceptance Scenarios**:

1. **Given** 补全页里填的手机号**已经是本站会员**，**When** 提交，**Then** 微信身份绑定到**那个已有会员**，
   **MUST NOT** 新建会员，也 MUST NOT 出现两个同手机号的会员
2. **Given** 上面这条合并刚刚发生，**When** 客户查看账号，**Then** 他看到的昵称/积分/订单是**原账号**的
3. **Given** 该手机号对应的会员**已经被另一个微信号绑过**，**When** 现在这个微信号要绑同一个手机号（Q21=C），
   **Then** 本次绑定被**拒绝**，且明确告知"该账号已绑定其他微信"；先绑的那个微信号**不受任何影响**，
   MUST NOT 出现"后绑的把先绑的顶掉"这种静默行为
4. **Given** 客户填的手机号格式不对或为空，**When** 提交，**Then** 被拒并给出人能看懂的原因

### Edge Cases

- 二维码被另一个微信号扫了（不是当前电脑正在等的那个人）。
  ⚠️ **这条是显式接受的风险**（Q25=B：不加"当前登录的是谁"的提示）——
  最坏结果是电脑前的人登录成了扫码者的账号。微信自己的确认页会显示应用名，是既有第一道防线；
  记录在此是为了将来能复盘，不是待办
- 同一个微信在**两台电脑**上同时发起登录
- 二维码过期后客户才在手机上点确认
- 客户扫码授权后，**在补全页上一直不填**、几小时后再回来
- 手机号格式不合法（位数不对、非 1 开头）
- 客户填的手机号**正好是自己**已经绑定了的那个会员（等于什么都没变）
- 微信侧不可用 / 授权被用户拒绝 / 用户在微信里点了"取消"
- 客户在**手机微信内**打开本站时，登录态已经存在（不该再弹授权）
- 会员被禁用（`status` 非启用）后尝试扫码登录
- 补全页要保存的**公司名称**：库里目前没有这一列（见上文「已核实的事实」），
  这是一次**需要落地的数据模型改动**，不是纯前端

## Requirements *(mandatory)*

### Functional Requirements

- **FR-129**: 前端 MUST 提供一个与既有两种登录方式并列的**微信登录**入口
- **FR-130**: 电脑端 MUST 以**二维码**形式提供微信登录；客户用微信扫码并确认后，
  电脑端 MUST **在不需要手动刷新或手动点确认的前提下**进入已登录状态
- **FR-131**: ~~手机端在微信内打开时 MUST 直接走微信授权，MUST NOT 要求客户"扫自己屏幕上的二维码"~~
  📌 **2026-10-14 所有者决定：本期不做**（原话「不补131，不考虑手机微信登录问题」）。
  **当前实际行为**：手机在微信里打开时**同样会显示二维码**，即**不满足本条**。
  **为什么不只是"加个 if 判断 UA"**：手机侧是一段**独立链路** —— 授权回跳后由 `/wechat/callback`
  接管，而那个页面（跑在手机上）得自己轮询、自己完成登录、自己跳转回家；现在它只做到
  "请回电脑上继续"。补它等于把整条扫码链路在手机端重做一遍。
  **影响范围**：在微信里打开本站的客户需要"另找一台设备扫屏幕上的码"，体验差；
  **不影响电脑端（主场景）、也不影响任何已登录用户的行为**。
- **FR-132**: 某个微信身份**第一次**出现时，系统 MUST **只识别它、不建会员** ——
  把 openid 与微信侧带来的昵称 / 头像暂存在登录票据里，等补全页提交时才落库（Q26）。
  MUST NOT 在此时创建会员或建立社交绑定
- **FR-133**: 已经绑定过会员的微信身份再次登录 MUST 直接进入；该会员已有手机号时不再要求补全
- **FR-134**: 补全页就是**建号（或绑定）那一步**：手机号必填且必须经短信验证（FR-147）。
  在它提交成功之前，系统 MUST NOT 建立任何登录态 —— 于是"**已登录但没有手机号**"这个中间态
  **根本不存在**，而 Q23=B 想要的"补齐前用不了任何会员功能"也就成了事实，不再需要额外机制去拦（Q26）
- **FR-135**: 补全页 MUST 提供**选填**的公司名称与头像，与手机号同页提交。
  ⚠️ 既有的头像上传接口**要求登录**，而此刻客户尚未登录 → 补全页**默认带微信头像**；
  客户自选的头像先留在浏览器里，**提交成功（此时已登录）之后**再上传（见 FR-151）
- **FR-136**: 若补全的手机号**已经是本站会员**，系统 MUST 把该微信身份绑定到**那个已有会员**，
  MUST NOT 新建会员，也 MUST NOT 产生第二个同手机号的会员
- **FR-137**: （**已并入 FR-133 的后半句**）该微信身份对应的会员已有手机号时，
  再次登录 MUST NOT 再要求补全。
  📌 保留编号以免断号；本条与 FR-133 是**同一件事**，**一律以 FR-133 为准** ——
  实施与测试不必分两处写（2026-10-12 的 `/speckit-analyze` 判为重复）
- **FR-138**: 「公司名称」MUST 是**会员档案的一项**：首次补全时采集，之后在前台「个人资料」里
  **可见、可修改**（与昵称 / 头像并列），运营在后台也 MUST 能看到（Q24=A）。
  当前数据模型里**没有**承载它的字段 —— 这条要求意味着一次数据模型改动（具体落点由计划阶段定）
- **FR-139**: 扫码登录 MUST NOT 影响既有的两种登录方式 —— 微信侧不可用时，它们 MUST 照常可用
- **FR-140**: 二维码 MUST 有明确的失效与重新获取路径；失效时 MUST 明确告知客户，MUST NOT 无限期显示"等待中"
- **FR-141**: 首次扫码 MUST NOT 让客户感知到"注册"这个动作 —— 不出现独立的「注册」入口、
  不出现注册表单、不出现"账号已存在"这类提示。补全页就是首次客户唯一的入口形态（Q26）
- **FR-142**: 补全页提交后 MUST 让客户直接进入已登录状态，MUST NOT 要求他"再去登录一次"
- **FR-143**: 一个会员 MUST NOT 因为本特性而出现**两个账号**（同一手机号只允许对应一个会员）
- **FR-144**: 电脑端 MUST 在扫码确认完成后**自动**进入已登录状态，客户 MUST NOT 需要在电脑上再点任何东西（Q19=A）。
  因此登录二维码 MUST 有一个可被查询的状态。**状态集以 [data-model.md](./data-model.md) §4 为唯一口径（共 5 个）**：
  `待扫 / 待补全 / 已完成 / 已过期 / 已作废`。
  查询 MUST 有明确的**停止条件**（完成、过期、客户离开页面）—— MUST NOT 无限期轮询下去。
  📌 **为什么没有「已扫待确认」**：公众号网页授权**不回调"用户已扫"这个事件** ——
  从扫码到拿到 code，中间是微信自己的页面，服务端一无所知。服务端能观测到的第一个变化就是 `待补全`
- **FR-145**: 合并绑定完成后，客户看到与能用的 MUST 是**原账号**的全部数据 ——
  昵称、头像、积分、历史订单、收货地址（US18 场景 2 的落点）。
  MUST NOT 出现"订单回来了但积分没回来"这种只搬一半的结果。
  📌 本条原先是 Q20 的复述、与 FR-136 近乎逐字重复；2026-10-12 的 `/speckit-analyze` 判为重复后
  **改造**成本条（保留编号以免断号）—— 它补的正是 US18 场景 2 一直缺的那条要求
- **FR-146**: 若该手机号对应的会员**已经绑定过另一个微信**，系统 MUST 拒绝本次绑定并明确告知（Q21=C）；
  MUST NOT 静默地把先绑的那个顶掉，也 MUST NOT 因此改动先绑那个微信的任何状态
- **FR-147**: 补全页提交的手机号 MUST **一律**先经短信验证码校验通过才写入（Q22=A）——
  **不区分**它是不是既有会员。验证 MUST 复用既有的短信验证码能力与场景机制；
  MUST NOT 为了让流程更快而跳过验证（跳过即等于允许占号）
- **FR-148**: 客户 MUST 能关闭补全页；关闭 MUST 让这次扫码**彻底作废** ——
  不建会员、不建绑定、不留登录态，客户仍是游客，**匿名浏览商品与分类照常可用**（Q23=B + Q26）。
  📌 这里不涉及"登出"：**从来就没有登录过**
- **FR-149**: 登录票据 MUST 是**不可猜测**的随机标识（MUST NOT 用自增序号、时间戳、客户编号等可推导的值），
  MUST 为**一次性**（用过即失效），且 MUST 有**短存活期**（过期即失效，见 FR-140）。
  理由：票据在"已扫码待确认"的那段时间里**等价于登录凭据** —— 谁能猜中它，谁就能把别人的登录结果拿到自己手里。
  这条没有合理的替代做法，故不列入澄清项而直接作为硬要求
- **FR-150**: 系统 MUST NOT 在补全页提交成功之前创建会员、建立社交绑定或签发登录态（Q26）。
  这条是 Q26 的核心：它**从根上**消灭了"没有手机号、用不了的僵尸会员"，
  也让 Q23=B 的"拦住"从"需要实现的机制"变成"本来就登不进来"这个事实
- **FR-151**: 补全页客户自选的头像 MUST 在提交成功之后再上传到既有文件服务；
  MUST NOT 为此放开上传接口的登录要求（放开即等于任何人都能往对象存储里灌文件）
- **FR-152**: 客户在补全页上停留过久、导致这次登录凭据已失效时，提交 MUST 明确告知
  "本次登录已过期，请重新扫码"，并给出**回到二维码的路径**；MUST NOT 静默失败、
  MUST NOT 把客户留在页面上重试到天荒地老。
  📌 **这是本轮唯一一处"规格自行补的默认值"**（不是所有者表态）：凭据有效期取 **5 分钟**，
  与二维码有效期一致；这个数字由计划阶段按微信授权码的实际寿命最终确认，可见即可改

### Key Entities *(include if feature involves data)*

- **会员**：既有的 `member_user`。本特性**首次**给它加上"公司名称"这一项（FR-138）。
  注意 `mobile` 可空、`nickname`/`avatar` 非空 —— 自动建号时后两者必须被填上默认值。
- **社交身份绑定**：既有的 `system_social_user` / `system_social_user_bind`。本特性会**新增绑定**、
  也可能把一条已存在的绑定**改指**到另一个会员（FR-136 的合并）。
- **登录票据**：一次"待扫"任务 —— `票据 / 状态（待扫 · 已扫待确认 · 待补全 · 已完成 · 已过期）/
  **扫码者的微信身份（openid + 昵称 + 头像）** / 归属的会员（完成前为空）`。
  它**只在登录过程中短暂存在**、**用完即弃**，不是业务数据。
  ⚠️ Q26 之后它多担一件事：在"已扫码但还没提交补全页"的那段时间里，
  **微信身份只存在这里**（还没落成会员）—— 所以它同时也是"待补全"状态的载体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-047**: 首次来的客户从"点微信登录"到"进入已登录状态"，**全程不需要输入任何东西**（除了在手机上点一次确认），
  耗时不超过 **30 秒**
- **SC-048**: 扫码完成后，电脑端进入已登录状态**不需要任何手动动作**（不刷新、不点确认）—— 用一条自动化用例断言轮询到结果后页面状态确实变了
- **SC-049**: **经本特性建出的**会员，没有手机号的为 **0** ——
  即"走完补全页建出来的会员，`mobile` 必不为空"；等价的可操作口径：
  **本次运行前后的会员增量里，没有手机号的为 0**（Q23=B + Q26）。
  📌 **口径必须收窄到"本特性建出的"**：线上存量里本来就有 **20 个**没有手机号的会员
  （`土豆233` ×11、`芋艿…` ×6、`用户xxxx` ×3，均为 demo/测试数据，`register_terminal=20`），
  本特性不碰它们。若写成"系统里没有手机号的会员数量为 0"，**这条标准永远不可能通过**
  —— 那正是宪法原则 V 禁止的"永不验收的标准充数"
- **SC-050**: 对"填的手机号已经是既有会员"的场景，**新增会员数为 0**（断言的是"没有多出一个账号"，
  而不是"绑定成功了"）；且该场景下的绑定**未通过短信验证时一次都不发生**（Q20=A）
- **SC-051**: 已补全过的会员再次扫码登录，被要求补全的次数为 **0**
- **SC-052**: 既有两种登录方式（验证码 / 密码）的行为与改动前**逐条一致** —— 既有登录相关用例全部保持通过

- **SC-053**: 对"该手机号已绑定过另一个微信"的场景，先绑的那个微信的登录能力、绑定关系与账号数据
  **一条都不被改动**（Q21=C：拒绝就是拒绝，不是"悄悄换绑"）
- **SC-054**: **未经短信验证码校验通过而被写入会员资料的手机号数量为 0**（Q22=A）——
  不区分"新号"与"既有会员的号"两条路径，用同一组用例分别断言
- **SC-055**: 关闭补全页之后：**会员数 0 增量、社交绑定数 0 增量、登录态不存在**，
  且同一浏览器仍能正常打开商品页与分类页（Q23=B + Q26）——
  前三个"0"合起来断言"这次扫码确实彻底作废了"，最后一条断言"没把人锁在门外"。
  📌 **每条都要单独断言**：只测"没登录"是测不出"悄悄建了个会员"的
  📌 **"社交身份"与"社交绑定"要分开算**：扫码换 openid 时可能落一条"只记了 openid、
  **没有绑任何会员**"的社交身份记录 —— 那是这一步的正常产物，**不算**绑定增量。
  断言错这一处，要么把正常行为判成 bug，要么把"悄悄绑了"漏过去
## Assumptions

- **本期只做 C 端 Web 前台（`storefront`）**；小程序 / App 端（`yudao-ui-mall-uniapp`）不在本期范围
  —— 沿用 003 / 004 已确立的先例。
- 公众号的三方应用信息**已经配好**（所有者所述），包括网页授权域名。
  **若实际配置不满足扫码登录所需的能力，这是需要回到本规格调整的前提**，不是实现细节。
- 补全页的字段集定为：**手机号（必填）+ 公司名称（选填）+ 头像（选填）**，
  **不自行增加**所有者没提到的字段（真实姓名、性别、生日等本期不做）。
- 补全页可以关闭/离开，但不补手机号就**用不了需要登录的功能**；
  下次再来仍会被拦（US2 场景 6）。
- 头像沿用既有能力（上传后拿 URL，会员已有 `update` 接口）。
  ⚠️ 但那个上传接口**要求登录**，而补全页出现时客户**还没登录**（Q26）→
  所以：补全页默认展示**微信头像**（授权时本就拿得到），客户自选的头像留到**提交成功之后**再上传（FR-151）。
  **不为此放开上传接口的登录要求**。
- 登录成功后的会话/令牌机制**沿用既有的**，本特性不新造一套。
- 「公司名称」是**客户自填**的展示性信息，不参与任何业务规则（不用于定价、开票、权限）。
  ⚠️ 若将来要拿它做开票或权限判断，那需要另立规格 —— 本特性不碰。

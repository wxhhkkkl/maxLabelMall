## 一、下单时申请开票（US19）

| # | 操作 | 预期 | 对应 |
|---|---|---|---|
| 1 | 结算页保持默认（不开票）提交 | 订单详情**没有**发票区块；后台申请列表里**查不到**它 | SC-059 |
| 2 | 勾「开票」→ 选**电子普通发票** → 只填公司名 → 提交 | 下单成功；订单详情显示「待开票」（该界面呈现由 **US22** 交付；只做完 US19 时改用接口确认申请已生成） | FR-155 |
| 3 | 勾「开票」→ 选**电子增值税专用发票** → 只填公司名 → 提交 | **被拦住**，提示缺 税号 / 地址 / 电话 / 开户行 | FR-156 |
| 4 | 专票把五项填全 → 提交 | 下单成功；后台「待开票」列表里**能查到它** | SC-057 |
| 5 | 数一下第 4 步的交互次数 | ≤ 4 次（选开票 / 选票种 / 填或选抬头 / 提交） | SC-056 |
| 6 | 提交后在浏览器网络面板看**下单请求体** | 带 `invoice` 对象且与表单**逐字段一致**；不开票时**没有** `invoice` 字段 | SC-062 |
| 7 | **实付 0 元的订单**（用券抵到 0 的那一类）：看结算页 | **整张发票卡片不出现**（spec Edge Case）；试着直接调补开接口 → 被拒 | spec Edge Case |

## 四、后台开具（US21）

| # | 操作 | 预期 | 对应 |
|---|---|---|---|
| 1 | 打开「待开票」列表 | 只看到**已支付**订单的申请；每条能看清订单号 / 客户 / 票种 / 抬头 / 金额 / 时间 | FR-168/169 |
| 2 | 上传一个 PDF | 状态变「已开票」，记录开票时间与操作人 | FR-170 |
| 3 | 对一个申请上传 `.txt` | **被拒**，且**该申请状态不变** | FR-171 |
| 4 | 把刚传的 PDF 重新上传一份（模拟传错） | 覆盖成功，客户那边下载到的是**新那份** | Q31 |
| 5 | 对**未支付**订单的申请点开具 / 对**已作废**的申请点开具 | 都被拒 | FR-169 / Q30 |
| 6 | 换个**没有 `issue` 权限**的后台账号，直接调开具接口 | 被拒（不是"按钮不显示"就算过） | **SC-065** |
| 7 | 数一下第 2 步的步骤数与耗时 | ≤ 3 步、单条 ≤ 1 分钟 | SC-063 |

## 五、前台查看与下载（US22）

| # | 订单状态 | 预期显示 | 对应 |
|---|---|---|---|
| 1 | 未支付或已取消，且没申请过 | **整块不显示** | FR-176 |
| 2 | 已支付、没申请过 | 只有「申请开票」入口 | FR-176 |
| 3 | 申请了、还没开好 | 显示「待开票」，**没有下载入口** | FR-176 |
| 4 | 已开票 | 票种 / 抬头 / 金额 + **可用的下载入口** | SC-058 |

- 点下载 → 拿到的确实是**这笔订单**的发票文件（不是别笔的）。**SC-058**
- **用未登录的浏览器直接打开那个文件链接** → 记录实际表现（能打开 / 不能）。
  这是 spec 里**显式接受的风险**（既有对象存储公网可读），实测一次供复盘，**不当作缺陷**。
- ⚠️ **把链接手动改成一个不存在的文件名再点** → 观察客户看到的是什么。
  预期：新标签里是文件域自己的 404 页 + 我们那行常驻的"文件打不开？请联系我们"。
  **记下真实观感能不能接受** —— 这条只做到"不静默、有求助路径"，**做不到**"当场告知文件已失效"
  （原因见 plan 风险 R10：那个文件域**没有 CORS 头**，前端根本读不到请求结果）。
  若观感不可接受，出路是**服务端代理下载**（另一次改动）。
- 换账号访问别人的订单详情 → **看不到**任何开票信息与链接。**SC-060**

## 六、退款与取消（Q30 + **Q35** / FR-184）—— **本清单最关键的一节**

> **2026-10-15 所有者实测后改判（Q35）**：退款了票就要**撤回** —— 含**已开出的票**、也含**部分退款**。
> 原来那三条（"已开票的不动""部分退款不作废"）**都已作废**，别照旧的走。

| # | 场景 | 预期 | 对应 |
|---|---|---|---|
| 1 | 一笔**待开票**的订单 → 客户取消订单 | 申请变**已作废**、从「待开票」列表消失；客户端显示"订单已退款/已取消，开票申请已作废" | FR-184 / SC-059 |
| 2 | 一笔**已开票**的订单 → 取消 / 退款 | 申请**也变「已作废」**；**前台不再展示抬头/金额/税号，下载入口消失**；后台点「重新上传」应当被拒 | **Q35** / FR-184 |
| 3 | **部分退款**：退掉订单里的一件商品（订单**未**取消） | **同样作废**（这条走的是**逐订单项**的钩子，最容易漏） | **Q35** |
| 4 | 后台「待开票」列表 | 上面三种情况的申请**一条都不该留在**待开票列表里 | SC-059 |
| 5 | 已作废的那条申请 | 列表里能看到，但**不能开具 / 重新上传**（接口会拒） | Q35 / FR-174 |

> ⚠️ 第 2、3 条是**容易漏实现**的地方：整单取消走 `afterCancelOrder`，**部分退款不取消订单**、
> 只走 `afterCancelOrderItem` —— 只做前者的话，退了一件商品的订单上**票还挂在前台**（不报错）。

## 七、不得回归（SC-062）

1. **不带开票**走一遍完整下单 → 落库数据与改动前逐字段一致（金额、优惠、积分、库存都不受影响）。
2. 本特性上线**之前**的订单：详情页正常打开，**不出现**发票区块；后台申请列表里查不到它们。
3. C 端既有 e2e 冒烟（`storefront/e2e/`，需本地后端 + **租户 1**）全绿。

## 八、断点走查（C 端三个新位置）

在 **1100 / 768 / 480** 三个宽度下分别看：发票抬头页、结算页发票卡片、订单详情发票区块 ——
**页面无横向滚动**、不出现第二套按钮视觉。（沿用 `design-consistency.spec.ts` 的三条结构断言 +
人工看观感；**新页面已登记进那份显式清单**，漏登记等于那三条断言管不到它。）

## 九、显式不验证的项（宪法原则 V 要求写明）

- **不做 e2e**（R36：构造"下单→支付→开具→下载"四步的成本远高于它能带来的信息，核心语义已由服务端单测覆盖）。
- **不验证管理端的视觉观感**（沿用 003 的口径：只自动化纯函数与弹窗逻辑，观感靠人工）。
- **不验证性能 / 并发**（本期量级是个位数到几十条申请）。
- **不验证发票的税务正确性** —— 系统**不代替开票**（FR-180），票由人工在开票平台开出。
- **不验证发票的邮件 / 短信推送**（FR-183 要求**不做**）—— 确认全仓没有发票相关的邮件 / 短信发送调用即可。
  写在这里是为了别让"按规格没做"和"忘了做"混在一起。
- **不验证老站那 4 条发票抬头记录** —— 明确**不迁移**（spec 的 Assumptions）。
- **不验证发票文件的访问鉴权** —— 链接公网可读是**显式接受的风险**，不是待办。

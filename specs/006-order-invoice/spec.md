# Feature Specification: 订单开票（下单申请 · 后台开具上传 · 前台下载）

**Feature Branch**: `006-order-invoice`
**Created**: 2026-10-15
**Status**: Draft
**Input**: User description: "商城加入发票模块，用户下单得时候选择是否需要开发票，完后选择发票类型，以及维护自己得发票title，后台有单独得查看开票申请得菜单，后台可以根据订单开好发票后进行上传，前台用户就可以看到已经开好得发票以及进行下载。"

## 背景

**今天这个商城没有任何发票能力。** 客户下单时无处填抬头，订单里不存开票信息，后台没有开票入口，
客户下单后也看不到自己有没有发票。实际流程是：客户打电话或加微信找张经理说开票需求，
人工开好票寄出或发文件，**系统里不留任何记录**（核实过程见下表）。

老站其实做过一半：建了一个就叫「发票」的自定义表单，字段是公司 / 税号 / 地址 / 电话 / 开户行，
提交后发邮件到 `yuwangchenfa@126.com`。它有两个天然的毛病：**发完邮件就沉底**（没有"待开票"这个
状态，谁开过、谁没开过全靠翻邮箱），以及**数据没迁过来**（迁库只导了分类/商品/会员/订单四域）。

本特性把这条链路搬进系统里，闭环是四步：

1. **下单时说清楚**：要不要发票、开哪种、开给谁
2. **抬头能存下来**：下次不用重新填
3. **后台一个列表**：谁要开票一目了然，开好后把文件传上来
4. **客户自己取**：订单详情里就能看到并下载

**系统不代替开票**：发票仍然由人工在税控 / 开票平台上开出，系统负责**收集申请、挂载文件、供给下载**。

**结论**：真正要新建的是三件事 —— ①**开票申请本身**（两处入口：下单时勾选、订单详情补开，含抬头采集）；
②**发票抬头簿**（会员侧可维护）；③**管理端的开票申请工作台**（列表 + 上传发票文件 + 状态流转），
外加 C 端订单详情那一个「申请 / 下载」的位置。

## Clarifications

### Session 2026-10-15

- **Q27 可选哪些发票类型（下文简称**票种**）、各自要哪些字段 → 两种，都是电子票；不支持纸质邮寄。**
  所有者原话：「电子普通发票和电子增值税发票，不支持纸质邮寄」。落地为通行的两类
  —— **电子普通发票**与**电子增值税专用发票**（即「电子发票（普通发票）」与
  「电子发票（增值税专用发票）」）。**纸质票与邮寄这条路整体不做**：后台只上传电子文件，
  前台只下载。
  字段（📌 **本规格自行取的默认值，可收紧**）：
  - **普票**：抬头名称（必填）+ 税号（**选填**，填了就必须校验通过）
  - **专票**：抬头名称 + 税号 + 地址 + 电话 + 开户行及账号（**全部必填**）

  专票这套字段与老站那个表单收的 5 项（公司 / 税号 / 地址 / 电话 / 开户行）一致。
  **不采用**「后台可配类型清单」：类型与字段是财务口径，稳定且只有两类；
  为它做配置页 + 动态字段 + 动态校验，成本换不来收益（宪法原则 IV）。
  ⚠️ 若「电子增值税发票」实际指的是别的口径（例如「增值税电子普通发票」＝普票），
  改这一处即可 —— 它唯一的影响是**结算页那张表单要哪几个字段**。
- **Q28 下单时漏选 / 选错，事后能不能补开或改 → 能补开；申请一旦提交，开票信息不可再改。**
  补开入口放在**订单详情**，限**已支付且尚未开票**的订单（US20）。
  理由：最常见的失败是"当时没勾、事后想起"。没有补开入口，这类客户只能回去找张经理 ——
  正是本特性要消灭的那条路。
  为什么不做「未开票前可改」：所有者在"只补开"与"补开 + 可改"之间明确选了前者。
  📌 **代价写在明处**：抬头一旦填错（下单时或补开时都一样）**没有自助退路**，只能找运营。
  实际用起来如果这条太别扭，放开「未开票前可改」是**一次独立的小改动**，不是本规格的遗漏。
  📌 **本规格自行取的默认值**：补开**对上线前的历史订单同样开放**（FR-179 只要求它们
  "视为未申请"，没有禁止补开）。这会让运营在待开票列表里看到老订单的申请 ——
  **开具之前必须先核对这张票线下是不是已经开过**（老站那 4 条发票表单记录与 674 条财务流水
  都在系统之外，系统无从判断）。

- **Q29 后台谁能处理开票申请 → 登记权限点，由现有角色体系授权（不新造角色）。**
  具体做法沿用 003 / 004 的先例：新增菜单时**同时**把权限点写进菜单表，
  运营在「角色管理」里给需要的角色勾上；**超管默认可用**。
  理由：本项目已知的后端行为是**超管有旁路、真正的门禁在前端权限点**
  （`sql/mysql/004-filter-dimension-menus.sql` 里记着那次"接口能调、按钮不显示"的踩坑）。
  收窄权限不需要改代码 —— 不给某个角色勾这个权限即可。
  ⚠️ 由此推出一条硬要求（FR-174 的后半句）：**接口必须校验同一权限点**，
  因为「上传发票 = 把订单标记成已开票」是**有财务效力**的动作，MUST NOT 只靠前端藏按钮。

- **Q30 订单退款 / 取消时，那张还没开出去的申请怎么办 → 作废。**
  **订单取消**（含售后**全额退款**导致的取消 —— 口径由 **Q33** 收窄）时，**尚未开具**的申请
  MUST 变为「已作废」并移出待开票列表；客户侧 MUST 如实显示"订单已退款，开票申请已作废"。
  理由：交易既然已经退回，票就不该开 —— 留在待开票列表里等于给运营埋一个"照单开票"的坑，
  而客户侧也会停在一个**永远等不到结果**的「待开票」上。
  **不采用**"退款申请中就先移出、失败再放回"：状态要跟着退款单来回流转，
  客户端会出现"待开票 → 已作废 → 待开票"的横跳，解释成本高于收益。
  📌 **尾句已被 Q35 取代（2026-10-15）**：原来说「已**开具**的票不走这条」，现在**已开票的也一并作废**。

- **Q31 开错票重新上传时要不要留痕 → 覆盖，只留最新一份。**
  重新上传**以最后一份为准**：系统只保留最新文件，记录最后上传时间与操作人（FR-170）；
  本期**不保留**历次上传的文件，也不记替换历史。
  理由：替换是异常路径，为它单独造一张历史表属于"为单一用途造结构"（宪法原则 IV）。
  📌 **已知代价写在明处**：万一某次传错的是**别人的发票**（跨客户），补传正确的那份之后，
  系统里查不到"曾经传错过什么" —— 这类事故只能靠流程兜（上传前核对订单号与抬头）。
  将来若财务要求可追溯，加一套上传历史是**一次独立的小改动**，不动现有数据。
  **不采用**"覆盖 + 操作日志"：成本与收益跟保留历史基本一样，只是换了个形状。

- **Q32 订单与开票申请是不是同一个事务 → 是，"同生共死"。**
  FR-181 的口径据此**收窄**：它保护的是**开票域自身**的失败（抬头簿读写、发票文件上传 / 下载），
  **不包括**"订单与申请要拆开写"。理由：拆开（或用 try/catch 只兜住申请写入）会留下
  **订单成了、申请永远补不上**的状态 —— 一个订单只允许一条申请（FR-160），而申请提交后不可改（FR-182），
  客户**无路可走**；更糟的是这种丢单**不报错**，正是本仓库反复吃亏的那类静默不一致。
  同事务的代价（DB 写失败时两者都不成）实际上是**零**：那种情况下订单本身也写不进去，客户重下即可。
  **不采用**"同事务 + try/catch 兜住申请写入"：它字面满足 FR-181，却**主动制造**了"订单在、票没了"的静默状态。

- **Q33 部分退款时，那条"待开票"的申请怎么办 → 当时定为"不作废、金额不变"。**
  ⚠️ **本条已被 Q35 取代（2026-10-15）**：现在**部分退款也作废**。下面保留原文，只为留下
  "当初为什么那么定、后来为什么改"的链条 —— **以 Q35 为准**。
  Q30 的口径据此**收窄**（见上一条已同步改过）：只有**订单取消**（含售后**全额退款**导致的取消）
  才作废待开票的申请；**部分退款**（订单仍存在）不改变申请状态、也不改申请金额。
  理由：作废会走进**死结** —— 作废后客户想就剩余金额开票，而一个订单只允许一条申请（FR-160）、
  申请提交后不可改（FR-182），他**既不能改也不能重新申请**，只能回头找客服，
  等于把本特性想消灭的那条路又请回来。
  代价（票面金额可能高于订单净额）是**可见、可控**的：后台列表如实显示订单当前的实付与已退金额
  （`contracts/admin-api.md` §1 的 `orderPayPrice` / `orderRefundPrice`），运营开具前自行判断。
  **不采用**"自动把申请金额改成实付 − 已退"：违反 FR-182，且客户会看到金额在背后变动而无任何通知。

- **Q34 「下载失败要给可读提示」这条怎么落 → 只做到"不静默 + 求助路径"，承诺据实收窄。**
  实测该文件域**不返回任何 CORS 头**（见 research R37），浏览器里**读不到**那次请求的结果 ——
  `fetch` 被跨域策略挡下，`mode: 'no-cors'` 拿到的是分不出 200 与 404 的 opaque 响应。
  **"当场告知客户文件已失效"在当前架构下做不到**：这是浏览器的限制，不是实现没写。
  本期兑现为：下载走**新标签**打开 + 入口旁**常驻**"文件打不开？请联系我们" ——
  失败时客户看得见打不开，也有明确的求助路径（Edge Cases 第 7 条已按这个程度改写）。
  **出路记在这里**：要真正兑现，得由服务端**代理下载**（`GET /app-api/trade/order-invoice/download?id=`，
  后端校验订单归属后取回转发）—— 它还能顺带把"链接公网可读"这条已接受的风险一并收掉。
  所有者 2026-10-15 明确选择**本期不做**：失败场景罕见、危害低（找客服即可），
  而代理下载要多一个接口、多一层文件流量与超时处理。

- **Q35 退款后那张**已开出**的发票怎么办 → **撤回**（2026-10-15 所有者实测后改判，**取代 Q30 的尾句与 Q33**）。**
  所有者的原话：「退款了后，发票应该被撤回，前台不能显示，也不能更新」。
  落地为：
  - **任何退款**（含**部分退款**，以及全额退款导致的订单取消）→ 该订单的开票申请**一律作废**，
    **不论它当时是「待开票」还是「已开票」**；
  - **前台不再展示任何发票内容**（抬头 / 金额 / 税号 / 文件都不露面），只留一句"已作废"的状态说明；
  - 作废后**后台也不能再更新**它（不能重新上传、不能标记已开票）—— 接口会拒。
  - 📌 文件地址与作废时间**保留在库里**：前者是财务核对 / 红冲时要查的凭据，后者用于展示"什么时候撤的"。
    红冲本身仍由财务线下处理（本期不做）。
  **为什么改掉原来的口径**：Q30/Q33 当时定的是"已开票的不动，票已在客户手里"，理由是不替财务撤回。
  所有者实测一遍后发现更实际的问题是：**退款了票还挂在前台**，客户会拿着那张票来对账 ——
  系统里"可下载"本身就是一种承诺。撤回之后，客户看到的是"已作废"，与财务事实一致。
  **放弃的收益**：Q33 当初担心"部分退款也作废会让客户无路可走"（一单一条 + 申请不可改）。
  所有者的选择是**接受这一点**（退款场景下客户本来就要找客服），换取"退过款的订单上不再挂着票"。
  ⚠️ **实现上要两个钩子**：整单取消走 `afterCancelOrder`，**部分退款不取消订单**、只走
  `afterCancelOrderItem` —— 少一个就会出现"退了一件商品、票还挂着"。

- **Q36 抬头按票种分开管理 + 没合适的能就地新增（2026-10-15 所有者实测后提的新要求）。**
  原话：「发票抬头管理在个人中心，不要每次都重新填写，下次可以选，如果没有就在弹框里填写；
  **普通发票和增值税发票分开管理**」。落地为：
  - **一条抬头只服务一种票**：抬头簿加「票种」（普票 / 专票）—— 这**推翻了 Q27/Key Entities 里
    "一条抬头两种票都能用"的设计**（当初是为了"只开普票的客户不必填开户行"）。
    现在按票种分开后，同一件事换个做法解决（**字段矩阵随后又被 Q37 收敛，见下**）：**普票抬头只要求名称、专票抬头要求五项全填**，
    校验按抬头的票种判（见 `InvoiceValidator`）。
  - **每个票种各有一条默认**（"默认"的唯一性从"按会员"改成"按会员 + 票种"）。
  - **结算页与补开弹层里都能就地新增**：选抬头的地方给「+ 新增抬头」，存进抬头簿后**自动选中**它 ——
    不必先跳到个人中心。
  - 个人中心那一页**按票种分两段**管理（普票一批、专票一批）。
  - 结算/补开时**只列出与所选票种相符**的抬头。
  📌 生产库当时 `trade_invoice_title` **0 行**，所以加列不需要回填历史数据（迁移脚本里仍给了默认值兜底）。

- **Q37 发票的必填字段收敛为「名称 + 税号」（2026-10-15 所有者实测后提的）。**
  原话：「增值税专用发票 现在不是必填的不填写不能保存」「两种都是只必须填写 公司名称和纳税人识别号」。
  落地为：
  - **两种票的必填都只有两项**：抬头名称 + 纳税人识别号；
    **地址 / 电话 / 开户行及账号一律选填**（专票那三栏仍然**显示**，只是不再必填）
  - 抬头名称的占位提示去掉「或个人姓名」——就写「**公司名称**」
  - `InvoiceValidator` 的必填矩阵**不再看票种**（票种仍要判合法性）；前端 `invoiceFieldError` 同步
  ⚠️ 这条**推翻了 Q27 的字段矩阵**（普票只要名称、专票五项全填），**也覆盖了 Q36 里刚写的那句**。
  **为什么当初会那么定**：专票在税务上确实要五项齐全才能开。但所有者的现实是
  **客户常常拿不出开户行账号** —— 与其在"存抬头 / 提交开票申请"这一步把人拦住，
  不如**先把需求收下来**，那几项财务开票时会核对补齐。
  **放弃的收益**：服务端少了一道"专票信息完整性"的门；代价由开票环节（人工）承担。

- **Q38 发票加「个人抬头」（2026-10-15 所有者提的）。**
  原话：「发票加一个个人抬头」。
  **为什么必须加**：Q37 之后抬头的必填是「名称 + 税号」**两项**，而**个人客户开普票没有纳税人识别号** ——
  于是这类客户连抬头都存不下来、也提交不了开票申请。他们是真实客户，不是边界情况。
  落地为：
  - 抬头多一维**抬头类型**（`InvoiceTitleKindEnum`）：**企业（1）/ 个人（2）**——
    与「票种」并列，同样是"这一份抬头怎么填"的一部分
  - **企业**：名称 + 税号（**Q37 口径不变**）；**个人**：**只要名称**
  - ⚠️ 个人抬头的税号是**选填、不是禁止**：自然人可以用身份证号当纳税人识别号。
    写成"个人不许填税号"会把合法场景挡在门外 —— 这条是本决策最容易做错的地方
  - **「个人 + 专票」不成立**：增值税专用发票按税法只能开给一般纳税人企业。
    前端两个选择器互为约束（选专票则"个人"置灰，选个人则"专票"置灰），后端 `InvoiceValidator` 也拒
  - **抬头类型三处共用**（结算页 / 订单详情补开 / 抬头簿）—— 与票种同处 `AppInvoiceApplyBaseVO`，
    于是**当场手填**的个人抬头同样免税号，不改抬头簿也能开票
  - 开票申请表上也**存一份**（快照，FR-158），后台工作台显示「企业 / 个人」——
    财务不用靠"税号怎么空着"去猜
  📌 抬头名称的占位提示**从 Q37 的"一律写公司名称"改为按类型给**（个人 → 姓名）；
  这不算推翻 Q37（那条讲的是**企业**客户看着"或个人姓名"会以为要写自己名字），是同一个意图的补全。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 下单时说清楚要不要发票、开给谁 (Priority: P1 · US19)

客户在结算页看到「发票」这一项，默认是**不开票**（与今天的行为一致）。改成开票后，
他选发票类型、填抬头（或从存过的抬头里挑一个），然后照常提交订单、照常付款。

**Why this priority**：这是整条链路的入口。没有它，后面的列表和下载都是空转；
而它**单独上线就已经有正收益** —— 开票需求从此进系统，不再依赖客户记得给张经理打电话。

**Independent Test**：在结算页选「开票」→ 选类型 → 填抬头 → 提交订单，
断言这笔订单里带着正确的开票信息，且下单/支付链路本身照常（金额、券、积分、库存都不受影响）。

**Acceptance Scenarios**：

1. **Given** 客户在结算页，**When** 保持默认（不开票）提交订单，**Then** 这笔订单**不产生**任何开票记录
2. **Given** 客户选择了「开票」并选好类型、填全抬头，**When** 提交订单，**Then** 订单落库时同时带着开票申请，
   客户按原流程付款，**任何一步都不多要一次点击**
3. **Given** 客户选了开票但抬头必填项没填全，**When** 点提交，**Then** 提交被阻止并**明确指出缺哪一项**，
   MUST NOT 先收下订单再让对方补信息
4. **Given** 客户之前存过抬头，**When** 他选择开票，**Then** 他能直接选中某一条，不需要重新输入
5. **Given** 客户提交订单时选了开票，**When** 他事后去改自己的抬头簿，**Then** 这笔订单上的开票信息**一个字都不变**

### User Story 2 - 下单时漏选了，订单详情里还能补开 (Priority: P2 · US20)

客户当时没勾开票，事后想起来要票。他打开那笔订单，点「申请开票」，
选类型、填抬头（或选一条存过的），提交即可 —— 不用再联系任何人。

**Why this priority**：Q28=A 明确要的这条。最常见的失败就是"当时没勾、事后想起"，
而按第一版的写法（只在下单时申请）这类客户只能回去找客服 —— 正是本特性想消灭的那条路。
技术上是复用 US19 的同一套申请能力，只是换一个入口，增量小、收益直接。

**Independent Test**：拿一笔**已支付、没申请过**开票的订单 → 订单详情出现「申请开票」→
填完提交 → 这笔出现在后台「待开票」列表里。

**Acceptance Scenarios**：

1. **Given** 一笔已支付、没申请过开票的订单，**When** 客户打开订单详情，**Then** 看到「申请开票」入口
2. **Given** 客户点开「申请开票」，**When** 选好类型、填全抬头并提交，**Then** 申请生成、
   后台待开票列表里能看到，订单详情随之改为显示开票状态
3. **Given** 一笔**还没付款**或**已取消**的订单，**When** 客户打开订单详情，**Then** **没有**该入口
4. **Given** 一笔**已经申请过**（无论开没开好）的订单，**When** 客户打开订单详情，**Then**
   入口**不再出现**（一个订单最多一条申请，FR-160）
5. **Given** 客户补开时提交了抬头，**When** 他之后想改这个抬头，**Then** **改不了**（Q28=A）

### User Story 3 - 后台看到开票申请，开好后把文件传上来 (Priority: P2 · US21)

运营打开「开票申请」这个菜单，看到谁要开票、开给谁、开多少钱；拿着这张票去开票平台开好，
把文件传回这条申请上，这条申请就变成「已开票」。

**Why this priority**：把"翻微信聊天记录 + 翻邮箱"变成"看一个列表"。它是 US19 / US20 的下游 ——
没有它，申请攒在库里没人处理。

**Independent Test**：造一条已支付订单的开票申请 → 后台列表里能看到 → 上传一个发票文件 →
该条状态变为「已开票」、文件可访问、记录了开票时间与操作人。

**Acceptance Scenarios**：

1. **Given** 有若干开票申请，**When** 运营打开「待开票」列表，**Then** 只看到**已支付**订单的申请，
   每条都能看清订单号、客户、发票类型、抬头、开票金额、申请时间
2. **Given** 一条待开票申请，**When** 运营上传发票文件，**Then** 状态变为「已开票」，
   并记录开票时间与上传人
3. **Given** 运营传错了文件，**When** 他重新上传一份，**Then** 以最后一份为准，客户下载到的就是新的那份
4. **Given** 运营上传了不支持的文件格式，**When** 提交，**Then** 明确报错且**这条申请的状态不变**
5. **Given** 一笔订单还没付款，**When** 运营看待开票列表，**Then** 这笔的申请**不在**待开票列表里

### User Story 4 - 客户自己看到并下载发票 (Priority: P3 · US22)

客户回到订单详情，看到这笔订单的发票状态；开好后能直接把文件下载下来，不用再找人要。

**Why this priority**：这是客户感知到的最终收益，但依赖 US21 先把文件传上来。

**Independent Test**：后台已上传发票 → 客户打开该订单详情 → 看到发票信息与下载入口 → 点下载能拿到文件。

**Acceptance Scenarios**：

1. **Given** 一笔**未支付或已取消、且没申请过**开票的订单，**When** 客户打开订单详情，
   **Then** **不出现**发票区块（没有就是没有）。
   📌 已支付且没申请的订单相反 —— 那里要出现「申请开票」入口（US20），两者不要混
2. **Given** 一笔申请了但还没开好的订单，**When** 客户打开订单详情，**Then** 显示「待开票」状态，
   **没有**下载入口（MUST NOT 给一个点了没东西的按钮）
3. **Given** 一笔已开好票的订单，**When** 客户打开订单详情，**Then** 看到发票类型、抬头、金额与**可用的下载入口**
4. **Given** 客户 A 已登录，**When** 他访问客户 B 的订单，**Then** 看不到 B 的任何开票信息与下载链接

### User Story 5 - 抬头簿：下次不用重新填 (Priority: P3 · US23)

客户在个人中心维护自己的发票抬头（可以存多条，比如给两家公司开票），下单时直接选一条。

**Why this priority**：纯便利性。US19 / US20 都允许"当场填"，所以没有它链路依然完整。

**Independent Test**：新增一条抬头 → 下单时能选到它 → 编辑/删除它，历史订单的开票信息不受影响。

**Acceptance Scenarios**：

1. **Given** 客户在个人中心，**When** 他新增一条抬头，**Then** 结算页选择开票时能选到它
2. **Given** 客户有两条抬头并设了一条默认，**When** 他选择开票，**Then** 默认那条被预先选中（仍可改选）
3. **Given** 某条抬头已被历史订单用过，**When** 客户把它删掉，**Then** 那些历史订单的开票信息**逐字段不变**

### Edge Cases

- **订单一直没付款**：申请已经生成，但票不该开 —— 未支付的申请 MUST NOT 进入待开票列表；
  订单超时取消后，这条申请 MUST 一并作废（MUST NOT 留在列表里等运营去开一张不存在的交易的票）
- **已付款、已申请开票，但票还没开出来时客户退款成功（或订单被取消）**：
  这条申请 MUST 变为「已作废」并移出待开票列表，客户侧 MUST 如实显示"订单已退款，开票申请已作废"
  （Q30）—— MUST NOT 让客户停在一个永远等不到结果的「待开票」上
- **全额抵扣、实付 0 元的订单**（券把订单抵到 0，后端不创建支付单）：没有可开票金额，
  MUST NOT 提供开票入口
- **部分退款**（退掉订单里的一件商品、订单**未**取消）：该订单的开票申请**同样作废**（Q35，
  2026-10-15 改判）—— 后台不能再对它开具、前台不再展示发票内容。
  ⚠️ 注意它**不取消订单**，所以走的是**逐订单项**的钩子（`afterCancelOrderItem`）；
  只实现整单取消那条钩子的话，这个场景会**静默漏掉**（票还挂在前台）
- **已开票之后订单退款 / 取消**：**票要撤回**（Q35，2026-10-15 改判）—— 申请转为「已作废」，
  前台 MUST NOT 再展示发票内容、也 MUST NOT 还有下载入口；后台也 MUST NOT 再更新它。
  文件地址留在库里供财务核对；**红冲本身仍由财务线下处理**（本期不做，见 Assumptions）。
  展示口径：页面 MUST **两件事都如实呈现** —— 订单当前的状态（已取消 / 退款中）与该发票
  已开出且**仍可下载**（票已交到客户手里，系统不会替财务把它撤回）。
  MUST NOT 因为订单取消就把发票藏起来或删掉；红冲由财务线下处理
- **抬头填写异常**：超长抬头、税号位数不对（15/18/20 位）、含空格 / 大小写混排 —— MUST 在提交前校验并明确提示
- **重复提交**：客户连点提交按钮 —— 下单时与订单详情补开时**同理** —— MUST NOT 产生两条申请
  （一个订单最多一条，FR-160）
- **上传异常**：超过大小上限、非 PDF / 图片、上传中途失败 —— MUST 明确报错且不改变申请状态
- **发票文件在对象存储里丢了**：MUST NOT **静默**失败 —— 下载走**新标签**打开（客户看得见"打不开"，
  不会以为自己没点中），且下载入口旁 MUST **常驻**求助路径（"文件打不开？请联系我们"）。
  ⚠️ **承诺到此为止（Q34）**：**当场告知**"文件已失效"**做不到** —— 该文件域不返回 CORS 头，
  浏览器读不到那次请求的结果。要真正兑现需**服务端代理下载**（见 Clarifications 的 Q34 与 research R37）
- **账号合并**（005 的场景）：合并后订单归属的账号变了，发票信息 MUST 跟着订单走，MUST NOT 出现"订单在、发票没了"
- **同一浏览器切换账号**：换账号后 MUST NOT 还能看到上一个账号的发票入口

## Requirements *(mandatory)*

### Functional Requirements

**C 端 · 下单时申请开票**

- **FR-153**: 结算页 MUST 提供「发票」区块，**默认「不开票」**（不选即与今天的行为完全一致）；
  客户可切换为「开票」
- **FR-154**: 选择开票时 MUST 让客户在**两种**发票类型中二选一：**电子普通发票**、**电子增值税专用发票**（Q27）。
  二者都是**电子票** —— 本特性 MUST NOT 提供纸质发票，也 MUST NOT 涉及邮寄
- **FR-155**: 选择开票时 MUST 采集**开票抬头信息**，字段随类型而异（Q27）：
  **普票** = 抬头名称（必填）+ 税号（选填，填了就必须通过格式校验）；
  **专票** = 抬头名称 + 税号 + 地址 + 电话 + 开户行及账号（**全部必填**）
  📌 **本条的字段矩阵已被 Q37 与 Q38 两次取代，以这两条为准**（上面这段只作来龙去脉）：
  **必填随「抬头类型」而变** —— **企业**要「名称 + 税号」（Q37），**个人只要名称**（Q38）；
  **地址 / 电话 / 开户行及账号一律选填**（两种票、两种抬头类型都一样）；
  另外 MUST 采集**抬头类型**，且 **「个人 + 专票」MUST 被拒**（Q38）
- **FR-156**: 开票信息的**必填项**没填全时 MUST 阻止本次提交（下单时是阻止下订单，补开时是阻止提交申请），
  并**指出缺哪一项**；MUST NOT 先收下再让对方补
- **FR-157**: 抬头 MUST 支持**当场新填**，也 MUST 支持**从已保存的抬头中选一条**（US23）
- **FR-158**: 开票信息 MUST 在下单那一刻**快照**进这笔订单 —— 之后改动抬头簿 MUST NOT 回溯修改任何历史订单
  （与商品名称 / 价格 / 收货地址的快照同理）
- **FR-159**: 提交订单时选了开票，就必须**同时**产生一条开票申请；**未选开票的订单 MUST NOT 产生任何开票记录**
- **FR-160**: 一个订单 MUST 最多只有一条有效开票申请 —— 本期**不支持拆票 / 部分开票**；
  重复提交 MUST NOT 产生第二条
- **FR-161**: 开票金额 MUST 取**订单实付金额**（口径见 Assumptions），MUST NOT 让客户填写或修改
- **FR-162**: 开票的选择 MUST NOT 改变结算与支付的任何行为 —— 价格、优惠、积分、库存、支付方式一律不变

- **FR-163**: **已支付且尚未申请过**开票的订单，客户 MUST 能在**订单详情**自助提交开票申请（US20，Q28=A）；
  入口 MUST 对**未支付 / 已取消 / 已申请过**的订单一律不出现。
  申请所需的信息与校验 MUST 与下单时**完全一致**（同一套类型与字段规则），MUST NOT 走一条更宽松的旁路

**C 端 · 抬头簿**

- **FR-164**: 客户 MUST 能在个人中心维护自己的发票抬头：**多条**、可新增 / 编辑 / 删除 / 设为默认
- **FR-165**: 抬头 MUST 只对其所属会员可见可改；任何其他账号 MUST NOT 看到（US22 场景 4 的同一口径）
- **FR-166**: 删除或修改抬头 MUST NOT 影响任何历史订单 —— 历史订单存的是**快照**（FR-158），不是引用

**管理端 · 开票申请工作台**

- **FR-167**: 管理端 MUST 有**独立的「开票申请」菜单**（不是塞进订单页的某个角落），
  供运营集中处理开票
- **FR-168**: 列表 MUST 展示：订单号、下单客户、发票类型、抬头、开票金额、申请时间、状态；
  并 MUST 支持按状态筛选
- **FR-169**: 「待开票」列表 MUST 只包含**已支付**订单的申请（未支付 / 已取消的不出现）
- **FR-170**: 管理端 MUST 能把**发票文件**（PDF / 图片）上传并挂到指定申请上；
  上传成功即状态变为「已开票」，并 MUST 记录**开票时间**与**操作人**
- **FR-171**: 上传 MUST 校验文件格式；不支持的格式 MUST 明确报错，且**申请状态不变**
- **FR-172**: 已开票的申请 MUST 允许**重新上传**（开错时的补救），**以最后一次上传为准**；
  系统只需保留**最新一份**文件，MUST NOT 要求保留历次版本或替换历史（Q31）——
  但 MUST 记录最后上传时间与操作人（FR-170）
- **FR-173**: 管理端 MUST 能看到申请与订单的对应关系，并可从申请跳到该订单
- **FR-174**: 新增的菜单与按钮权限点 MUST 登记进菜单表（否则连超管都看不到按钮，
  既有踩坑记录见 `sql/mysql/004-filter-dimension-menus.sql`）；且后端接口 MUST 用**同一权限点**做校验，
  MUST NOT 只靠前端隐藏 —— 尤其「上传发票 / 标记已开票」这个动作（Q29）。
  权限的授予 MUST 走既有角色体系，MUST NOT 为此新造角色

**C 端 · 查看与下载**

- **FR-175**: 订单详情 MUST 显示这笔订单的发票状态（各状态分别怎么显示见 FR-176）；
  已开票时展示的发票信息 MUST 与后台开出时的一致（类型、抬头、金额）
- **FR-176**: 订单详情的发票区块 MUST 按实际状态呈现，四种情形不得混淆：
  **已支付且未申请** → 显示「申请开票」入口（FR-163）；**申请了但还没开好** → 只显示开票状态，
  **MUST NOT** 给下载入口（不给一个点了没东西的按钮）；**已开票** → 显示发票信息与下载入口；
  **未支付 / 已取消且没申请过** → 整个发票区块不显示
- **FR-177**: 下载入口 MUST 只对**订单所属会员**出现；系统 MUST NOT 在任何**界面**上把该发票的信息或
  链接展示给其他账号。
  ⚠️ **口径收窄（2026-10-15）**：链接本身是**公网可读**的（既有对象存储的既有性质，见 Assumptions 的
  显式接受风险），所以"别人拿到链接也打不开"这件事**做不到**；本期的承诺是"界面不展示"。
  要真正防住，得改成服务端代理下载 —— [research.md](./research.md) 的 **R37** 记了这条路与它为什么不在本期
- **FR-178**: 订单列表 MUST 能看出该笔订单的开票状态，用词 MUST 与别处统一：
  **未申请 / 待开票 / 已开票**（不用「开票中」这类同义词）

**跨端 / 兼容**

- **FR-179**: 本特性上线**之前**的既有订单 MUST 一律视为「未申请开票」，MUST NOT 需要补任何历史数据
- **FR-180**: 发票 MUST 由**人工开具后上传**；系统 MUST NOT 自行开票，也 MUST NOT 对接税务 / 第三方开票平台（本期）
- **FR-181**: 开票**域自身**的失败（抬头簿读写、发票文件上传 / 下载、后台开具）MUST NOT 让客户
  **下不了单** —— 开票是下单的附加信息，MUST NOT 成为下单主链路的新故障点。
  ⚠️ **口径（Q32）**：**不包括**订单与开票申请的写入 —— 二者 MUST 在**同一事务**里，要么都成、要么都不成。
  MUST NOT 把申请写入用 try/catch 兜成"订单成功、申请丢失"（那是**不报错的丢单**）
- **FR-182**: 开票申请**一经提交**，其开票信息 MUST NOT 再被修改 —— 含**尚未开具**的那段时间，
  客户侧与运营侧都不提供修改入口（Q28=A）。票据已被税务系统开出后，改它本身也不成立
  （要改只能红冲，而红冲本期不做）
- **FR-183**: 电子发票的交付方式 MUST 只有**文件下载**；MUST NOT 做邮箱 / 短信推送
  （所有者没提，不自行增加交付渠道）
- **FR-184**: 订单**取消**（含售后**全额退款**导致的取消）或**发生退款**时，其开票申请 MUST 转为「已作废」
  并移出待开票列表（Q30 + **Q35**）；客户侧 MUST 如实显示该申请已作废且给出原因（订单已退款 / 已取消），
  MUST NOT 停留在「待开票」。
  **已开具的申请同样作废**（Q35，取代原来的"不受影响"）：作废后前台 MUST NOT 再展示任何发票内容
  （抬头 / 金额 / 税号 / 文件），后台也 MUST NOT 再对它开具或重新上传。
  **部分退款**（订单未取消）同样 MUST 作废（Q35）—— 它不取消订单，所以走的是**逐订单项**的钩子
  （`afterCancelOrderItem`），少实现这一个钩子就会漏

### Key Entities *(include if feature involves data)*

- **发票抬头**：会员维护的开票资料 —— `所属会员 / 票种 / **抬头类型** / 抬头名称 / 税号 / 地址 / 电话 / 开户行及账号 / 是否默认`。
  📌 **2026-10-15 起改为按票种分开管理（Q36）**：一条抬头**只服务一种票**。
  📌 **必填由 Q37 + Q38 定**：**企业**抬头的必填是「名称 + 税号」，
  **个人**抬头**只要名称**（税号选填，且只能开普票）。下面这段原文保留，只作来龙去脉：
  这五项就是老站那个发票表单收的全套（Q27）。**同一条抬头两种票都能用**：
  开**普票**只用到「名称 + 税号（选填）」，开**专票**要求五项全有（**均已被 Q37 取代**）。
- **开票申请**：一笔订单的开票诉求 —— `订单 / 会员 / **开票信息快照**（类型 + 抬头类型 + 抬头各字段）/
  开票金额 / 状态（待开票 · 已开票 · 已作废）/ 发票文件 / 开票时间 / 操作人`。
  它**依附于订单**，一个订单最多一条有效申请（FR-160）
- **发票文件**：开好的发票（PDF / 图片），存在既有文件服务上，申请只保存它的引用
- **交易订单**：既有实体。本特性**不改变订单的金额与状态**，只是让它多挂一条开票申请（FR-162）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-056**: 客户在下单时完成开票申请，**不重复输入**任何已保存过的抬头信息；
  从"选开票"到"提交成功"不超过 **4 次交互**（选开票 / 选类型 / 选或填抬头 / 提交）
- **SC-057**: 下单成功产生的开票申请，在管理端「待开票」列表里**漏单数为 0**（100% 可见）
- **SC-058**: 后台上传发票文件后，客户在订单详情页**无需任何人工干预**即可看到下载入口，
  且该链接能打开、内容确为该订单的发票文件
- **SC-059**: **未申请**开票的订单产生的开票记录数为 **0**；
  未支付订单的申请出现在「待开票」列表里的条数为 **0**；
  **已退款 / 已取消订单**的申请（**不论当时是待开票还是已开票**，Q35）留在「待开票」列表里的条数为 **0**，
  客户侧看到的是「已作废（订单已退款）」而不是「待开票」，**且发票内容与下载入口都不出现**（三条分别断言）
- **SC-060**: 客户 A 在**站内**看到或下载到客户 B 的发票信息 / 文件的次数为 **0**（跨账号，逐条断言）。
  ⚠️ 口径与 FR-177 一致：这条断的是**界面与入口**（A 登录后逛不到 B 的任何开票信息）；
  直链本身是公网可读的（Assumptions 的显式接受风险），"拿到 URL 也打不开"不在本条承诺内
- **SC-061**: 修改或删除抬头簿里的条目后，历史订单的开票信息**逐字段不变**（0 处被回溯改动）
- **SC-062**: 下单主链路不受影响 —— 既有结算 / 下单 / 支付用例**全部保持通过**；
  未开票订单落库的数据与改动前**逐字段一致**
- **SC-063**: 运营处理一条申请（从打开列表到上传完成）不超过 **3 步**、
  单条耗时不超过 **1 分钟**（以上传一个已开好的 PDF 计）
- **SC-064**: 已支付且未开票的订单，客户能在订单详情**自助**提交开票申请（无需联系任何人），
  且提交后开票信息被改动的次数为 **0**（含尚未开具的那段时间，Q28=A）——
  两条一起断言："自助办得成" + "办完不可改"
- **SC-065**: **未获该权限**的后台账号：菜单与按钮不出现，且**直接调用接口也被拒绝**
  （0 次成功），订单的开票状态不因此发生任何变化（Q29）——
  两条一起断言，只测"按钮不显示"是测不出后端有没有真的拦的

## Assumptions

- **本期只做 C 端 Web 前台（`storefront`）+ 管理端 Web（`yudao-ui-admin-vue3`）**；
  小程序 / App 端（`yudao-ui-mall-uniapp`）不在本期范围 —— 沿用 003 / 004 / 005 已确立的先例。
- **发票类型只有两种，且都是电子票**：电子普通发票、电子增值税专用发票（Q27）。
  **不提供纸质发票、不涉及邮寄** —— 这一整条路本期不存在
- **开票金额口径**：取订单**实付金额**（商品金额 − 各类优惠 + 运费），即客户实际支付的数
- **一个会员可以维护多条抬头**，其中可设一条默认（US23）—— 所有者说的"维护自己的发票 title"
  按"能维护一个抬头簿"理解；**不做**抬头与订单类型的绑定、不做企业资质审核
- **补开对上线前的历史订单同样开放**（Q28 的 📌）—— 运营处理这类申请前须先核对
  线下是否已经开过这张票，系统无从判断
- **发票文件沿用既有对象存储**：上传后是一个**公网可读**的链接（实测见事实表），
  本期**不加**签名 URL / 权限校验 —— 即"知道链接的人能打开"。
  ⚠️ 这是一条**显式接受的风险**（发票文件含公司名、税号），写在这里供将来复盘；
  若要加鉴权，那是另一次改动（需改下载链路），不在本规格范围
- **系统不代替开票**：发票由人工在税控 / 开票平台上开出，系统只负责收集申请、挂载文件、供给下载（FR-180）
- **本期不做**：纸质发票与邮寄、发票的邮箱 / 短信推送（FR-183）、红冲 / 作废发票流程、
  拆票与部分开票、按开票状态自动催办或提醒、发票与优惠券 / 积分的税务口径调整
- **老站那 4 条发票抬头数据不迁移**：样本极小（4 条）、且是老站表单的一次性提交记录，
  不是"抬头簿"；老客户下次下单时重新选一次抬头即可（若将来决定导入这批记录，回到这里改）
- 会员登录态、文件上传、列表与分页、状态展示等**一律复用既有能力**，本特性不新造

# 功能规格：虚拟商品（软件）—— 买软件不填收货地址

> 编号续 006：本规格从 **FR-185 / SC-066 / US24 / Q39 / R38** 接着往下排
> （006 排到 FR-184 / SC-065 / US23 / Q38 / R37）。

**Feature Branch**: 与 006 同一条 `006-order-invoice` 分支（本仓库按时序推进，未按特性开分支）

---

## 背景与问题

站里既卖**标签纸（实物）**也卖**软件（虚拟）**。客户买软件时，结算页会拦住他：

> `CheckoutView.onSubmit()`：`if (!addressId.value) → '请先选择收货地址'`

软件不需要寄，客户却必须先编一个收货地址才能付款 —— 这是一条**走不通的路**。

⚠️ 值得注意的是：**后端本来就不要求地址**（`getAddress()` 里 `if (addressId != null)`，
「用户自提」就是这么走的）。真正缺的是**商品模型里没有"虚拟商品"这一档** ——
`DeliveryTypeEnum` 只有 `快递(1) / 自提(2)`，于是系统没有一个办法说"这个商品不用送"。

## Clarifications

### Session 2026-10-16

- **Q39 虚拟商品怎么落地（2026-10-16 所有者拍板，五条口径）。**
  起因：所有者问「如果我买的是软件，不需要填写收货地址怎么处理」。落地为：
  - **① 交付方式 = 客服线下联系**：下单后由你们人工联系客户交付软件。
    **系统不落任何交付信息**（不做授权码、不做下载链接、不做邮件推送）。
  - **② 标识方式 = 新增 `VIRTUAL(3)`「虚拟商品」配送方式**（推翻了我在方案里列的
    "复用空运费模板""靠商品分类"两个替代项 —— 那两个要么会误判、要么语义不对）。
  - **③ 允许与实物混买；只要单里有实物就仍要收货地址**（做的是**整单**判定，不是按件）。
  - **④ 纯软件单付款后留在「待发货」**，客服联系完由运营在后台标记为已交付。
    —— 所有者明知"客户会看到待发货会困惑"仍然选它，**为的是后台有一份现成的待办清单**。
  - **⑤ 虚拟商品照常设库存**：运营把 SKU 库存填成大数即可，**不动库存逻辑**。
  - **⑥ 「整单虚拟」由服务端判定，不由前端算**（宪法原则 III：业务规则不得由前端裁决）。
    判定规则：**所有商品都只支持虚拟商品** → 虚拟；否则 → 快递。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 买软件不用填收货地址 (Priority: P1 · US24)

客户在结算页买了软件（购物车里只有软件），**页面上不出现「收货地址」这一块**，
他直接选券、提交、付款。订单在后台出现，运营看到后线下联系客户交付。

**Why this priority**：这是本特性存在的**唯一理由**。没有它，软件这条路根本走不通。

**Independent Test**：把购物车只放一件虚拟商品 → 结算 → 断言页面上没有「收货地址」卡片、
提交能成功、订单里没有收货人信息。

**Acceptance Scenarios**：

1. **Given** 购物车里只有软件，**When** 打开结算页，**Then** **不渲染**收货地址卡片，
   且**不提示**"请先选择收货地址"
2. **Given** 同上，**When** 提交订单，**Then** 下单成功；订单的配送方式是**虚拟商品**、
   **没有**收货人 / 地址 / 运费
3. **Given** 购物车里**既有软件又有标签纸**（混买），**When** 打开结算页，
   **Then** **照旧要收货地址**、照旧算运费（实物要寄）
4. **Given** 购物车里只有实物，**When** 没选地址就提交，**Then** **仍然被拦住**并提示
   —— 这条**不能**被本特性改松

### User Story 2 - 运营把软件单标记为已交付 (Priority: P2 · US25)

运营在后台看到一笔虚拟商品订单（状态「待发货」、配送方式「虚拟商品」），
联系完客户后点「发货 → **无需发货**」，把它推进到「已发货」。

**Independent Test**：后台打开一笔虚拟商品订单 → 点发货 → 选「无需发货」→ 提交 →
状态变「已发货」。

**Acceptance Scenarios**：

1. **Given** 一笔「待发货」的虚拟商品订单，**When** 打开后台订单详情，
   **Then** 有「发货」按钮（改之前**没有** —— 它只对快递显示）
2. **Given** 同上，**When** 点发货并选「无需发货」，**Then** 状态变「已发货」、
   **不需要**填物流公司与单号
3. **Given** 一笔「用户自提」订单，**When** 直接调发货接口，**Then** **仍然被拒**
   （自提走核销，不走发货）

### Edge Cases

- **商品的配送方式为空**（`delivery_types = ''`，建表默认值就是它，历史数据里有）：
  MUST 判为**快递**（要地址）—— 当成虚拟会让实物商品收不到地址。
- **同时勾了「快递发货」和「虚拟商品」**（`[1,3]`）：MUST 判为**快递** —— 它支持快递，就该要地址。
  ⚠️ 这是刻意的保守选择，已在商品编辑页给出提示（运营应只勾「虚拟商品」一项）。
- **整单虚拟但客户端仍传了 `deliveryType=1`**：服务端 MUST 以**自己判定的**为准
  （不是信任请求里的值）。
- **虚拟商品单的「确认收货」**：走完发货后客户仍需点「确认收货」才到「已完成」
  —— 这是复用既有状态机的必然结果，**本次不改**。

## Requirements *(mandatory)*

### Functional Requirements

**C 端 · 结算与下单**

- **FR-185**: 结算响应 MUST 回传**本单实际采用的配送方式**（`deliveryType`），
  取值 1 快递 / 2 自提 / 3 虚拟商品。**判定 MUST 在服务端完成**（原则 III）。
- **FR-186**: 判定规则 MUST 是「**所有商品都只支持虚拟商品** → 虚拟；否则 → 快递」。
  MUST NOT 把"配送方式为空"或"同时勾了快递与虚拟商品"当成虚拟（见 Edge Cases）。
- **FR-187**: 整单虚拟时，结算页 MUST NOT 渲染收货地址区块、MUST NOT 要求选地址。
- **FR-188**: 整单虚拟时，结算页 MUST NOT 为"算运费"而自动选中默认地址。
- **FR-189**: 下单时前端 MUST 回传结算响应里的 `deliveryType`；
  **服务端 MUST 以自己计算的值为准**（请求里的值不参与落库与地址分支）。
- **FR-190**: 整单虚拟的订单 MUST NOT 有收货人 / 收货地址 / 核销码，开票金额 MUST 不含运费
  （虚拟商品本来就不产生运费）。
- **FR-191**: **含实物的订单 MUST 仍然要求收货地址** —— 本特性 MUST NOT 放宽它。

**服务端 · 发货**

- **FR-192**: 虚拟商品订单 MUST 能通过「发货」推进到「已发货」，且 MUST NOT 要求物流公司与单号
  （复用既有的「无需发货」分支）。
- **FR-193**: 「用户自提」订单 MUST 仍然**不能**走发货（它有专门的核销入口）。

**管理端 · 商品与订单**

- **FR-194**: 商品编辑的「配送方式」MUST 能勾选「虚拟商品」；勾了它时 MUST 给出
  "只勾这一项、否则会被当成实物"的提示。
- **FR-195**: 商品的**运费模板 MUST 只在勾了「快递发货」时必填** —— 修掉"只勾自提/虚拟商品
  就存不下来（字段被隐藏、校验仍跑）"这个既有缺陷。
- **FR-196**: 后台订单列表与详情的「发货」按钮 MUST 对虚拟商品订单可见；
  「用户自提」MUST NOT 出现该按钮。

**跨端 / 兼容**

- **FR-197**: `deliveryType` 的取值 MUST 四端一致：服务端 `DeliveryTypeEnum.VIRTUAL(3)`、
  字典 `trade_delivery_type`、管理端 `utils/constants.ts`、C 端 `api/order.ts`。
  ⚠️ 商品编辑的选项来自**字典**，服务端校验来自**枚举** —— **两边都改才算改完**。
- **FR-198**: 既有订单与本特性的改动 MUST NOT 互相影响：历史订单的 `deliveryType` 仍是 1/2。

### Key Entities

- **商品（`product_spu.delivery_types`）**：既有字段，逗号分隔的多选。
  本特性新增取值 **3**；**"是虚拟商品"的判据就是"只含 3"**。
- **订单（`trade_order.delivery_type`）**：既有字段。新增取值 **3**。
  为 3 时 `receiver_*` / `pick_up_verify_code` 全为空 —— **不需要新表、不需要新列**。
- **字典（`system_dict_data`）**：新增 `trade_delivery_type / 3 / 虚拟商品`。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-066**: 购物车只放虚拟商品时，结算页**不出现**「收货地址」任何字样
  （卡片标题与两个按钮都不在），且提交**成功**。
- **SC-067**: 购物车含实物时，结算页**照旧**要求收货地址，且下单请求里带 `addressId`。
- **SC-068**: 后台对虚拟商品订单点「发货 → 无需发货」后，订单状态变「已发货」。
- **SC-069**: 商品编辑只勾「虚拟商品」**能保存成功**（改之前报「【物流设置】不完善」）。

## Assumptions

- 软件的交付**由客服线下完成**，系统不参与（Q39①）。因此**不存在**"授权码 / 下载链接 /
  交付状态"这类字段，也不做邮件或短信推送。
- 虚拟商品**占用普通库存**（Q39⑤）—— 运营需把库存设成足够大的数。
- 客户在订单详情里看到的状态是「待发货」（Q39④），**这是已知且接受的**。
- 结算页当前不提供"配送方式切换"（FR-027a），本特性**也不提供** ——
  配送方式由服务端按商品判定，客户无需选择。

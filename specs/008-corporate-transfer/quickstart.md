# 手工验证清单（008 对公转账）

> ⚠️ 先说清楚哪一半是自动化的：
> **自动化** —— 判定与流转的纯函数/服务层（"是不是对公单"、"确认收款后进待发货"、
> "重复确认幂等"、"待收款单不进自动取消候选集"）、C 端「待收款」不出现支付入口
> （**列表与详情两处都有断言**）、结算页选「对公转账」的请求体。
> 另外**管理端 UI 没有自动化测试**（本仓库的管理端只有 6 个 spec，惯例如此）——
> 权限点登记（T484）、按钮显隐、配置页表单**都只能手工验**，见下。
> **手工** —— 下面全部（要登录后台、要真的造一笔打款凭证）。

## 零、前置核对（**上线必做，漏了就报错**）

1. **`012-corporate-transfer.sql` 已执行**：建 `trade_order_offline_payment`、
   给 `trade_config` 加 5 个字段、往 `pay_channel` 插 `offline`、往字典插渠道名。
2. **交易配置里已填收款账户**（户名 / 账号 / 开户行）并**启用对公转账**。
   位置：管理端「商城 → 交易配置 → **对公转账**」页签（008 新增的那个页签）。
   ⚠️ **首次保存会被前端拦住**：空表单上「分佣模式 / 分销关系绑定模式 / 提现方式」
   三项是必填（页面默认值就是空的，其余数字项是 `0`，不算空）。**先在这三项里各选一个**再保存
   —— 它们不会把分销打开（该页签的「分佣启用」开关默认是关的）。
   📌 拦的是前端校验，请求根本没发出去（`grep -c 'trade/config/save' /var/log/nginx/access.log` = 0）。
   ⚠️ **打开这个页签会看到一张空表单 —— 这是正常的**：线上 `trade_config` 表里
   **只有 `tenant_id = 1` 的行，本项目（162）没有行**（2026-10-16 实测）。
   **"保存"那一下会为租户 162 建出配置行**（`saveTradeConfig` 里"不存在则插入"），
   所以：**先填好账户再保存**，不要空着保存（空着保存 = 建出一行"对公转账未启用"的配置，
   还得再改一次）。
   ⚠️ **这是业务事实，必须由所有者填** —— 没填的话客户看到的收款账户是空的。
3. **`013-corporate-transfer-menus.sql` 已执行** —— 登记 `trade:order:confirm-paid`。
   ⚠️ 漏了它，**连超管都看不到「确认收款」按钮**（而接口是通的）。
   这一条**只能手工验**，自动化测试看不见。
3. **后端 / C 端 / 管理端均已发版**。
4. 上线顺序：**先跑脚本 → 再发后端 → 最后发两个前端**（枚举与渠道在后端）。

> 用于验证的账号：**一个普通 C 端会员账号** + **一个有 `trade:order:confirm-paid` 权限的后台账号**。

## 一、客户用对公转账下单（US26 / Q40①② / Q41 / Q44）

| # | 操作 | 预期 | 对应 |
|---|---|---|---|
| 1 | 结算页看支付方式 | 除原有的在线支付外，多出**「对公转账」**可选项 | FR-199 |
| 2 | 选「对公转账」→ 提交 | 下单成功；**跳转到订单详情**（不是支付页） | FR-199 |
| 3 | 订单详情 | 状态显示「**待收款**」（**不是「待支付」**）；显示收款户名/账号/开户行/提示语 | **SC-070 / FR-200 / FR-201** |
| 4 | 同上，把页面拉到最底 | **没有任何"去支付 / 立即支付"入口**（防重复付款） | **FR-201** |
| 5 | ⚠️ 特别看一眼 | **不要出现"无需支付"** —— 对公单**没有**支付单，容易被误判成"全额抵扣那类无需支付" | R47 |
| 6 | 浏览器网络面板看下单请求体 | 带 `payChannelCode: "offline"`；响应里 `payOrderId` 为 **null** | 契约 §1 |
| 7 | 订单详情勾了开票的话 | 显示「待开票」（申请随订单落库，但**财务还看不到**） | **Q46** |
| 8 | 换成**在线支付**下另一单 | 行为与改动前**逐字一致** | FR-211 |
| 9 | 回到「**我的订单**」列表看那笔对公单 | 标签是「**待收款**」（不是「待支付」），且**没有「立即支付」按钮** | **FR-200 / FR-201** |
| 10 | 顺手看列表的筛选胶囊 | 仍叫「待支付」（对公单在后端就是未支付，本来就在那一格）—— **换个名字就会筛不出来** | FR-200 |
| 11 | 在列表上直接点那笔单的「**取消订单**」 | 能取消（与普通未支付订单一致） | spec Edge Case |
| 12 | 看一笔**待收款**的对公单详情 | **不显示**「支付截止 …，逾期订单将自动取消」（对公单不参与自动取消，FR-212） | FR-212 |

## 二、财务确认收款（US27 / Q40③④ / Q42）

| # | 操作 | 预期 | 对应 |
|---|---|---|---|
| 1 | 后台订单列表按**支付方式 = 对公转账**筛 | 能筛出刚才那笔（且**只有**它） | **FR-209** |
| 2 | 打开那笔单 → 点「**确认收款**」 | 弹层要求填**银行流水号** | FR-203/204 |
| 3 | **不填流水号**直接提交 | **被拦住** | FR-204 |
| 3b | 确认**前后**各看一眼订单列表 | 确认前：那行状态是「**待收款**」标签（不是「待支付」）；确认后变成「待发货」 | **FR-209 / 488b** |
| 4 | 填上流水号（+ 可选打款方/到账时间）→ 提交 | 订单变「**待发货**」；子表记下流水号与**确认人 / 确认时间** | **SC-071 / FR-205** |
| 5 | 再点一次「确认收款」 | **无效果 / 被拒**（幂等） | **SC-072 / FR-206** |
| 5b | 回到订单详情，看「**对公转账**」区块 | 流水号 / 打款方 / 到账时间 / **确认人 + 确认时间**都在（对账就靠这几行） | **FR-205 / 488b** |
| 5c | 打开一笔**普通**订单的详情 | **没有**「确认收款」按钮，**也没有**「对公转账」区块（`offlinePayment` 为 null） | FR-207 |
| 6 | 用**没有 `confirm-paid` 权限**的账号直接调接口 | **被拒**（不是"按钮不显示"就算过） | FR-203 |
| 7 | 对这笔已确认的单**发货** | 正常发货；⚠️ **看后台日志有没有 ERROR**（微信物流同步在渠道 ≠ `wx_lite` 时应自动跳过） | R46 |
| 8 | 对这笔单发起**退款** | **能走通**（证明确实复用了支付单链路，而不是绕开它改状态） | **SC-073 / Q40⑧** |
| 9 | **发票**：确认收款**前**，客户想在订单详情「申请开票」 | **打不开 / 被拒**（补开要求订单已支付） | **FR-215 / Q46** |
| 10 | **发票**：确认收款**后**，后台「开票申请」列表 | 那笔单的申请**出现了**（006 的列表只含已支付订单）—— 这就是"款到开票" | **FR-215 / Q46** |
| 11 | 确认收款后，客户在订单详情「申请开票」 | **可以补开了** | FR-215 |

## 三、弃单与取消（Q45 / FR-212~214）

| # | 操作 | 预期 | 对应 |
|---|---|---|---|
| 1 | 下一笔对公单，**什么都不做，等超过 2 小时** | 订单**依然存在**、仍是「待收款」（**没有被自动取消**） | **SC-075 / FR-212** |
| 2 | 同上那笔单，后台点「**取消订单**」并填原因 | 订单变「已取消」；库存释放；已作废；**原因出现在商家备注里** | **FR-213** |
| 2b | 对一笔**已支付**的订单点「取消订单」 | 列表/详情**根本不出现**这个入口；直接调接口也被拒（要走退款） | FR-213 |
| 3 | 对已取消的对公单再点「确认收款」 | **被拒** | FR-214 |
| 4 | 下一笔**普通未支付**订单，等超过 2 小时 | **照旧被自动取消**（既有行为不受影响） | FR-211 |
| 5 | **客户侧**打开一笔待收款订单，点「**取消订单**」 | **能取消**（与普通未支付订单一致）—— 这是"打款前反悔"的正常路径 | spec Edge Case |
| 6 | 在交易配置里**关掉「对公转账」** → 再去结算页 | 选不到了；但**已经产生的待收款订单不受影响** —— 仍能确认收款、仍能取消 | **FR-210** |
| 7 | 关掉开关后，直接调**下单接口**带 `payChannelCode: "offline"` | **被拒** | FR-210 |

## 四、不得回归（FR-211）

1. 在线支付订单：下单 → 支付 → 发货 → 退款，**逐字段与改动前一致**
2. 超时自动取消：普通未支付订单仍按 2 小时取消
3. 既有订单的 `pay_channel_code` 语义不变（**仍然是"支付成功的渠道"**）
4. 开票：普通订单的开票流程不受影响（Q46 明确不改）
5. **订单列表**：普通未支付订单仍显示「待支付」+「立即支付」；
   全额抵扣（`payPrice = 0`）的普通订单仍显示「无需支付」—— 两条都不能被对公转账改掉（FR-211）

## 五、显式不验证的项（宪法原则 V 要求写明）

- **不做 e2e**：与 006/007 同口径 —— 构造"下单→线下打款→确认→发货"的成本高于它带来的信息；
  核心判断已由服务端测试覆盖。
- **不验证真实银行流水**：系统**不接银行**（Q43），财务看到的那笔到账**由人工判断是否确认** ——
  这是方案的固有代价，不是待办。
- **不验证金额不一致的自动处理**：少打 / 多打 / 一笔打多单，**系统不做校验**（Q40⑤），
  判断权在财务。规格里已如实写明。
- **不验证钱包**：C 端没有余额页，本期不做（Q40⑦）。
- **不验证账期 / 授信 / 对账单**：本期不做（Q40⑥）。
- **不验证 uniapp**：该端当前未投用。

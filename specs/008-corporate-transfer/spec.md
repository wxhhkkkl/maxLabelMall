# 功能规格：对公转账（客户线下打款，财务确认收款）

> 编号续 007：本规格从 **FR-199 / SC-070 / US26 / Q40 / R42** 接着往下排
> （007 排到 FR-198 / SC-069 / US25 / Q39 / R41）。

**Feature Branch**：与 006/007 同一条 `006-order-invoice` 分支（本仓库按时序推进，未按特性开分支）

---

## 背景与问题

**一部分客户是对公打款**（企业网银/柜台转账到公司账户），他们不走支付宝、也不想走微信 ——
走公司的付款流程、要留银行凭证、常常还要配合开票。而站里**只有在线支付**：

- 结算页只有「去支付」，点下去走支付宝/微信
- 这类客户的实际做法只能是：**私下转账 + 找客服手工处理**，系统里订单永远停在「待支付」；
  或者干脆不走线上

于是：**订单和收款对不上**（系统说待支付、实际钱已到账），**财务没有地方核销**，
**客户也不知道该往哪打钱**。

## Clarifications

### Session 2026-10-16

- **Q40 对公转账怎么落地（2026-10-16 所有者拍板，八条口径）。**
  起因：所有者问「我的客户有的会对公打款，给我一个思路」，并在看过三条思路后选了 **A**
  （后台「确认收款」）并要求成规格。落地为：
  - **① 客户在结算页能选「对公转账」作为一种支付方式。**
  - **② 选了它 → 不生成在线支付单**，订单进入「**待收款**」；客户侧展示**收款账户信息**。
    ⚠️ 这一条同时是**防重复付款的关键**：订单既然没有在线支付单，前台也就**必须**
    不给任何在线支付入口 —— 否则客户打款后又去点支付宝，就重复付款了。
  - **③ 财务核对银行流水后，在后台点「确认收款」** → 订单进入「待发货」。
  - **④ 确认收款必须留痕**：银行流水号（必填）+ 打款方 / 到账时间 / 备注（选填），
    以及**操作人与操作时间**。这是财务动作，必须可追溯。
  - **⑤ 一单一确认** —— 本期**不做**"一笔打款抵多笔订单"。
  - **⑥ 先款后货** —— 本期**不做**账期 / 授信额度 / 对账单。
  - **⑦ 不动钱包** —— `pay` 模块的会员钱包是现成的，但 **C 端没有余额页面**；
    本期**不做**"后台充值 + 余额支付"那条路（它更适合"预付一笔慢慢扣"的常客，是另一个特性）。
  - **⑧ 确认收款时，服务端造一笔 `offline` 渠道的支付单并置为已支付** —— 复用既有的
    "支付成功 → 订单待发货"链路。**刻意不走"直接改订单状态"**：退款、对账、统计
    全都挂在支付单上，绕开它会让**退款链路断掉**。
  - **⑨ 收款账户信息由所有者提供**，规格与实现里一律**留占位符**，不得编造
    （宪法 FR-054/055/056：业务事实不得编造）。

- Q41: 「对公转账」这个支付方式，客户在**什么时候**选？
  → A: **结算页下单时就选**（与"在线支付"并列）。下单即定「待收款」、**不生成在线支付单**
  （与 Q40② 一致）；**下单后不可改**，要改就取消订单重下。
  ⚠️ 刻意**不选**"下单后在支付页选"：那样下单时**支付单已经生成了**，选对公后还得补一套
  "作废未支付的支付单"的逻辑，与已经定下的 Q40② 打架。

- Q42: 确认收款要不要**二级复核**（财务提交 → 主管审核）？
  → A: **不需要**。一个有权限的后台账号确认即生效。
  **理由**：本特性是**先款后货**，确认收款登记的是"**一笔已经到账的钱**"，钱早就在公司账上，
  不存在"放款"风险；加复核只会拖慢发货。
  ⚠️ 真正需要复核的是**账期/授信**（先发货后收钱）—— 那个已在 Q40⑥ 明确本期不做。

- Q43: 财务对账要不要支持**导入银行流水**（CSV/Excel）自动匹配？
  → A: **不做，纯人工核销**。财务对着网银/短信流水，在后台按订单号 / 客户 / 金额 / 下单时间
  搜到订单，逐笔确认。
  **理由**：① 各家银行、各个账户的流水导出格式都不一样（列名/编码/金额正负号），做导入得先定义格式
  再处理差异；② Q40⑤ 已经把"金额对不对"的判断权交给财务，**系统拿到流水也替不了这个判断**。
  先用手工核销跑一段，看这条路的实际量，再决定要不要自动化。

- Q44: 客户在订单列表 / 详情看到的**状态文案**是什么？
  → A: 客户侧**显示「待收款」**（只对"对公转账"的订单），与普通未支付订单的「待支付」区分开。
  **理由**：Q40② 明确"不给任何在线支付入口"，若状态还写「待支付」，客户与客服会以为"还能点支付宝"，
  正好与那条防护对着干。改文案代价很小（按标记换一句话），但它**直接决定客户会不会去打款、
  要不要问客服**。
  📌 这里只说**用户可见文案**；底层用"新状态值"还是"独立标记"表达，仍由**计划阶段**定
  （见 Key Entities）。

- Q47: 对公单的**退款**怎么走？
  → A: **复用既有的在线退款链路**（`offline` 渠道提供一个"本地直接返回成功"的 `PayClient`），
  **钱的进出由财务线下银行转账完成**。
  **触发原因**（实现时才发现的）：对公收款是打进**银行账户**的，支付渠道退不了钱 —— 所以系统里的
  "退款成功"**只是记账**。⚠️ **代价所有者已知情并接受**：**客户会先看到「已退款」，而钱还没到账**。
  **为什么不加"人工确认已线下退回"**：与 Q42 / Q43 同一个方向 —— **先把链路跑通、把人工环节留在人身上**；
  而且复用既有退款链路能**白拿** 006 的"退款 → 作废已开票申请"（Q35）那条联动，不用自己维护。

- Q45: 对公转账订单会不会被「**超时未支付自动取消**」干掉？
  → A: **不参与自动取消**（它只等人工确认收款或人工取消）；但**必须同时新增后台「取消订单」入口**。
  **背景（写规格时漏掉的一条致命边界）**：线上 `yudao.trade.order.pay-expire-time = 2h`，
  且 XXL-Job 的 `tradeOrderAutoCancelJob` **每分钟跑一次、处于开启** —— 也就是**未支付订单 2 小时后
  会被系统取消**。而公司走对公打款流程通常要**几天**，照这样**钱还没打出去、单子已经没了**。
  **为什么不选"给个更长的期限"（如 30 天）**：那不是不行，但所有者要的是"这类订单**只由人管**" ——
  期限到了自动取消，等于把"客户其实还想付、只是慢"的单子也砍掉。
  ⚠️ **代价必须一起承担**：后台**目前没有「取消订单」功能**（只有 发货/备注/改价/改地址/核销）——
  所以"不自动取消"必须**配套新增后台取消**，否则客户弃单会**永久积压**、连财务都没法清。

- Q46: 对公转账订单的**发票什么时候能开**？
  → A: **保持 006 的现状，本特性不改开票逻辑**，但把行为写清楚。三条**代码事实**：
  ① 客户**下单时就能勾开票** —— 开票申请在下单那刻随订单落库，**不校验是否已付款**；
  ② 客户**确认收款前「补开」不了** —— 补开要求订单已支付（`INVOICE_ORDER_NOT_PAID`）；
  ③ 但**财务侧天然就是"款到开票"** —— 006 的「待开票」列表**只显示已支付订单**的申请（FR-169）。
  也就是：**申请先落库、财务却看不见**，要等确认收款后才浮出来。
  **为什么不改成"对公单下单时禁止勾开票"**：那等于动 006 的既有口径，而且对公客户本来就要
  一次把抬头填完 —— 让他事后再回来补开没道理。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 客户用对公转账下单 (Priority: P1 · US26)

企业客户在结算页选「对公转账」下单，订单页告诉他"**待收款**"以及**往哪个账户打多少钱**（附言写订单号）。
他让财务按这个信息转账，之后不用再在站上做任何操作。

**Why this priority**：这是本特性的入口。没有它，这类客户还是无路可走。

**Independent Test**：结算页选「对公转账」→ 下单 → 断言订单是「待收款」、
页面展示收款账户、且**没有任何在线支付入口**。

**Acceptance Scenarios**：

1. **Given** 客户在结算页，**When** 选「对公转账」并提交，**Then** 下单成功，
   订单状态是「**待收款**」（**不是「待支付」**）
2. **Given** 一笔待收款订单，**When** 客户打开订单详情，**Then** 看到收款账户信息
   与"我们确认到账后发货"的说明，且**页面上没有任何"去支付"入口**
3. **Given** 客户选的是「对公转账」，**When** 下单完成，**Then** **没有生成任何在线支付单**
   （用接口验证）
4. **Given** 客户在结算页，**When** 选在线支付（现状），**Then** 行为与改动前**逐字一致**

### User Story 2 - 财务确认收款 (Priority: P1 · US27)

财务打开银行流水，找到某笔到账，在后台搜到对应订单，点「**确认收款**」，
填上银行流水号（和可选的打款方/到账时间），订单随即进入「待发货」，仓库照常发货。

**Independent Test**：后台打开一笔待收款订单 → 点「确认收款」→ 填流水号 → 提交 →
订单变「待发货」，且能查到是谁、什么时候、依据哪个流水号确认的。

**Acceptance Scenarios**：

1. **Given** 一笔「待收款」订单，**When** 财务点「确认收款」并填流水号，**Then** 订单变「**待发货**」
2. **Given** 同上，**When** **不填流水号**就提交，**Then** **被拦住**（留痕是硬要求）
3. **Given** 已经确认过的订单，**When** 再点一次确认（或两个人同时点），
   **Then** **幂等** —— 状态不变、不产生第二条痕迹
4. **Given** 一笔普通在线支付订单，**When** 直接调「确认收款」接口，**Then** **被拒**
   （它只能用在待收款订单上）
5. **Given** 一笔已确认收款的订单，**When** 后续发货 / 退款 / 售后，
   **Then** 与在线支付订单**行为一致**（退款能走通）

### Edge Cases

- **客户选了「对公转账」后又去在线支付**：结构上**不可能** —— 不生成在线支付单、
  前台也不给入口（Q40②）。这是本设计最要紧的一条防护。
- **打款金额与订单金额不一致**（少打 / 多打 / 一笔打款想抵多单）：
  系统拿不到银行流水，**不做金额校验**（Q40⑤）。财务**自行判断是否确认**；
  确认时的**流水号必填**就是为了事后能对上账。
  ⚠️ 规格里如实写明：这是**把判断权交给财务**，不是在系统里解决对账。
- **客户打款后没通知任何人**：财务**主动**对着银行流水核销（这正是他们现在的工作方式），
  所以后台 MUST 能按**订单号 / 客户 / 金额 / 下单时间**筛出待收款订单。
- **客户在打款前想取消**：待收款订单 MUST 能像普通未支付订单一样取消（取消后不可再确认收款）。
- **客户下了单就再也没动静（弃单）**：因为对公转账订单**不参与自动取消**（FR-212），
  它会一直留在待收款里 —— **必须由财务在后台手工取消**（FR-213）。
  ⚠️ 这条不是"顺带一提"：后台**本来没有取消订单这个功能**，不新增的话这批单子**永远清不掉**。
- **客户下完单才想改成对公转账**：本期 **MUST NOT 支持**（Q41）—— 支付方式在**下单那一刻**就定了；
  客户只能**取消订单重新下**。⚠️ 这是刻意取舍：支持"下单后改"就意味着要在下单时**先不生成支付单**、
  再允许事后选，等于把两种支付方式的选择推迟到支付环节，既有的"下单即生成支付单"链路要跟着改。
- **重复确认**：两个财务同时点 → 只有一次生效（FR-203 幂等）。
- **确认收款后要退款**：走既有的退款链路（这正是 Q40⑧ 要造 `offline` 支付单的原因 ——
  没有支付单，退款无处可挂）。
- **收款账户变更**：账户信息 MUST **可配置**，不能写死在代码里（FR-207）——
  换开户行、换账号时不该改代码重新发版。

## Requirements *(mandatory)*

### Functional Requirements

**C 端 · 下单**

- **FR-199**: **结算页** MUST 提供「**对公转账**」作为一种支付方式供客户选择（与"在线支付"并列，
  **下单前**就选）；选它下单时 MUST **不生成在线支付单**（Q41）。
  MUST NOT 提供"下单后在支付页再改成对公转账"这条路。
- **FR-200**: 通过「对公转账」下的订单 MUST 处于「**待收款**」状态
  （MUST NOT 是普通未支付订单的「待支付」）—— 财务要能把"还没打款"与"打了没核销"分开。
  **客户侧的订单列表与详情也 MUST 显示「待收款」**（Q44），MUST NOT 沿用「待支付」——
  否则客户会以为"还能点支付宝"，与 FR-201 的"不给在线支付入口"自相矛盾。
  📌 底层用新状态值还是独立标记表达，由计划阶段定（Key Entities）；本条约束的是**用户可见文案**。
- **FR-201**: 待收款订单的**订单详情** MUST 展示**收款账户信息**与"确认到账后发货"的说明；
  且 MUST NOT 提供任何**在线支付入口**（Q40② 的防重复付款）。
- **FR-202**: 客户侧 MUST NOT 能自行把待收款订单改回在线支付；要改 MUST 取消订单重下。

**管理端 · 确认收款**

- **FR-203**: 管理端 MUST 提供「**确认收款**」动作，且**受独立权限点保护**
  （如 `trade:order:confirm-paid`）—— 不是所有后台角色都该能确认收款。
  **MUST NOT 要求二级复核**（Q42）：一个有权限的账号确认即生效，不再加"主管审核"这一环。
- **FR-204**: 确认收款时**银行流水号 MUST 必填**；打款方 / 到账时间 / 备注选填。
- **FR-205**: 系统 MUST 记录**确认人与确认时间**（财务动作必须可追溯）。
- **FR-206**: 确认收款 MUST **幂等** —— 重复提交（含并发）MUST 只生效一次，
  且 MUST NOT 产生第二条痕迹。
- **FR-207**: 「确认收款」MUST 只能作用于**待收款**订单；对其它状态的订单 MUST 被拒。
- **FR-208**: 确认收款后，系统 MUST 生成一笔 **`offline` 渠道的支付单并置为已支付**
  （Q40⑧），从而使订单进入「待发货」，且**后续发货 / 退款 / 售后与在线支付订单完全一致**。
- **FR-209**: 待收款订单 MUST 能从管理端订单列表**筛出来**（按订单号 / 客户 / 金额 / 下单时间），
  这是财务对着银行流水逐笔核销的入口。
  **MUST NOT 要求导入银行流水文件**（Q43）—— 本期只保证"搜得到 + 能确认 + 留痕"。

**跨端 / 配置**

- **FR-210**: 收款账户信息（户名 / 账号 / 开户行 / 给客户的附言提示）MUST **可配置**，
  MUST NOT 写在代码或前端里。同时 MUST 能**整体启用 / 关闭**这个支付方式。
  ⚠️ **关闭只影响"新下单"**：已经产生的待收款订单 MUST **不受影响**（照旧能确认收款、能取消）——
  否则运营一关开关，等于把在途的订单卡死。
- **FR-211**: 本特性 MUST NOT 影响既有在线支付订单的任何行为（下单、支付、发货、退款）。
- **FR-212**: 对公转账订单 MUST **不参与「超时未支付自动取消」**（Q45）——
  它只等**人工**确认收款或人工取消。
  ⚠️ 现状是 `pay-expire-time = 2h` + 每分钟一次的 `tradeOrderAutoCancelJob`；
  不改的话公司还没走完付款流程、订单就被系统砍了。
- **FR-213**: 管理端 MUST 提供**取消订单的入口**（**所有未支付订单**，不只对公单 ——
  一经做出就是通用的，没必要只给对公单开这个口子）—— 这是 FR-212 的**配套**：
  没有它，客户弃单会**永久积压**，财务连清理的手段都没有。
  取消后 MUST NOT 还能确认收款。
  ⚠️ 只能取消**未支付**订单；已支付的（含确认收款后的）MUST 走**退款**，
  MUST NOT 用取消（金额对不上）。
- **FR-214**: 取消一笔待收款订单 MUST 与取消普通未支付订单**行为一致**
  （不产生退款 —— 因为本来就没收到钱）。
- **FR-215**: 本特性 MUST NOT 改动 006 的开票口径（Q46）。明确既有的三条行为、
  并 MUST 保证它们对公转账订单同样成立：
  ① 下单时**可以**勾开票（申请随订单落库，不校验付款）；
  ② 确认收款前**补开不了**（订单未支付）；
  ③ 申请**要等确认收款后才**出现在财务的「待开票」列表里（由 006 的 FR-169 保证 ——
     该列表只含**已支付**订单的申请）。

### Key Entities

- **订单（`trade_order`）**：新增一个**状态或标记**来表达「待收款」。
  ⚠️ 具体是"加一个状态值"还是"加一个独立标记"，由计划阶段定 —— 但它 MUST 能：
  ① 与「待支付」区分开；② 参与列表筛选（FR-209）；③ 取消逻辑与未支付订单一致。
- **支付单（`pay_order`）**：新增 `offline` 渠道。确认收款时由服务端创建并直接置为已支付。
- **收款确认痕迹**：流水号 / 打款方 / 到账时间 / 备注 / 确认人 / 确认时间。
  ⚠️ 落在订单表、支付单扩展信息还是新表，由计划阶段定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-070**: 客户在结算页选「对公转账」能**下单成功**；订单详情显示「待收款」与收款账户，
  且**页面上找不到任何在线支付入口**。
- **SC-071**: 财务在后台点「确认收款」并填流水号后，订单变「**待发货**」；
  不填流水号则**提交不了**。
- **SC-072**: 对同一笔待收款订单**重复**（或并发）提交确认，只生效**一次**。
- **SC-073**: 一笔确认收款后的订单，其**退款**能正常走通（证明确实复用了既有支付链路，
  而不是绕开它改状态）。
- **SC-074**: 既有在线支付订单的下单 / 支付 / 发货 / 退款 **逐字段不变**（回归）。
- **SC-075**: 一笔对公转账订单在**超过 2 小时**之后**依然存在**且仍是「待收款」
  （证明它确实绕开了自动取消）；同时后台能把它**手工取消**掉。

## Assumptions

- **先款后货**：不收账期、不做授信额度与对账单（Q40⑥）。账期是**另一个特性**，
  工作量差一个量级。
- **一单一确认**：一笔银行打款抵多笔订单**本期不做**（Q40⑤）。
  真要做，需要一张"收款单"表 + 核销关系，那是更大的一套。
- **收款账户信息**由所有者提供；规格与实现里**留占位符**，不得编造（Q40⑨）。
- **不做钱包**：`pay` 的会员钱包虽然现成，但 C 端没有余额页面；
  "后台充值 + 余额支付"是**另一条路**（更适合预付款常客），本期不做（Q40⑦）。
- **不接银行直连**：对公转账没有通用的实时回调，银行直连成本高、性价比最低。
- **不做金额自动核对、也不做流水导入**：系统不接银行流水，是否确认由财务判断（Q43 / 见 Edge Cases）。
- 发票仍按 006 的既有口径（跟着订单、金额取实付），本特性**不改开票逻辑**（Q46）：
  客户下单时就能勾开票、申请随订单落库；但它**要等确认收款后**才进入财务的「待开票」列表
  （006 的 FR-169 保证），所以财务侧天然是"款到开票"。

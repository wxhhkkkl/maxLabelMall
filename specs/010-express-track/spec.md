> （009 排到 FR-252 / SC-087 / US34 / Q54）。

**Feature Branch**: `010-express-track`
**Created**: 2026-10-24
**Status**: Draft
**Input**: User description: "对接快递100,下单用户可以在快递发货后查看到快递信息，后台管理人员在订单页也可以查看"

## 背景与问题

**客户只知道「发货了」，不知道「到哪了」。** 001 首期就把「用户侧的物流轨迹跟踪」
明确排除在外（原文：「物流轨迹不在本期范围」），只做到订单状态显示「已发货」。
于是 Web 前台的订单详情页里，客户看不到快递公司、运单号，更看不到轨迹 ——
「发货了吗 / 到哪了」只能来问客服。

**服务端其实不是空白，缺的是接线与可用性。** yudao 已内置快递100 查询客户端、
C 端与管理端两个物流查询接口、以及按运单缓存的机制；管理端订单列表也已有
「运单号 + 查看物流」入口。真正缺的是：

1. **C 端 Web 前台没有展示** —— 订单详情不调用轨迹接口，页面上没有任何物流信息；
2. **查询目前跑不通生产** —— 仓库里的授权码是上游演示值，快递公司编码又是另一种
   体系（快递鸟短码），两者叠加，任何一次查询都必然失败；
3. **失败路径没有定义** —— 第三方超时、限频、编码不识别时，客户会看到什么，今天没人回答。

**本特性是一条完整的用户路径，不是一次「接个接口」。** 它要交付的是：
客户在发货后能稳定看到真实物流；运营在后台能回答同样的问题；拿不到时，
两端都给出**可信的提示**而不是错误原文或空白。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 客户在订单详情看到物流轨迹 (Priority: P1 · US35)

客户的一笔快递订单已经由运营发货。客户打开「我的订单 → 订单详情」，
能看到这笔货由哪家快递承运、运单号是多少、什么时候发的，以及到目前为止的
每一个物流节点，最新的在最上面。

**Why this priority**: 这是本特性唯一直接面向客户的增量，也是用户提出需求的
原话（「下单用户可以在快递发货后查看到快递信息」）。没有它，整个特性没有意义。

**Independent Test**: 取一笔已有运单号的已发货订单，打开 C 端订单详情，
即可独立演示与验收；不需要管理端、也不需要其它故事先完成。

**Acceptance Scenarios**:

1. **Given** 一笔快递订单已发货（有快递公司、运单号、发货时间），**When** 客户打开订单详情，
   **Then** 看到「物流信息」区块：快递公司名称、运单号、发货时间，
   以及按发生时间**倒序**排列的轨迹（每条含发生时间与描述）。
2. **Given** 订单尚未发货，**When** 打开订单详情，**Then** 不出现物流区块。
3. **Given** 订单是虚拟商品或到店自提，**When** 打开订单详情，**Then** 不出现物流区块。
4. **Given** 已发货但服务商暂时返回空轨迹，**When** 打开订单详情，
   **Then** 物流区块仍显示快递公司与运单号，轨迹区给出「暂无轨迹信息」的明确提示，而不是一片空白。
5. **Given** 已发货订单，**When** 客户在「我的订单」列表查看该行，
   **Then** 看到「查看物流」入口，点击后进入订单详情（列表不直接展示轨迹）。

### User Story 2 - 运营在后台订单页查询物流 (Priority: P1 · US36)

客服接到「我的货到哪了」的电话，在后台订单列表里找到这笔订单一键查看物流，
在同一个工作台里直接回答，不必再去快递公司官网粘贴单号。

**Why this priority**: 与客户侧同等重要 —— 它是客服每天真正会用的路径。
**现状已基本满足**（E4），本故事的主要工作是验收既有能力、并把它接入统一的降级口径。

**Independent Test**: 在后台订单列表找到已发货订单 → 点击「查看物流」→
看到轨迹时间轴，即可独立验收。

**Acceptance Scenarios**:

1. **Given** 已发货订单，**When** 运营在订单列表点击物流入口，**Then** 看到该运单的轨迹时间轴。
2. **Given** 轨迹查询失败，**Then** 详情页其余内容正常展示，物流区给出可辨识的提示。
3. **Given** 账号没有 `trade:order:query` 权限，**Then** 物流查询被拒绝（沿用既有权限体系）。

---

### User Story 3 - 物流拿不到时不误导客户 (Priority: P2 · US37)

第三方服务超时、限频、凭据过期、快递公司编码缺失，都是会发生的常态。
发生这些情况时，客户看到的应该是一句**说得通的中文提示**，
订单其余信息照常可用；而不是一串错误码、一片空白，或者一条编造的轨迹。

**Why this priority**: 它不产生新功能，但决定了功能"看起来坏没坏"。
放在 P2 是因为它依附于 US35/US36；一旦缺失，前两个故事的可信度会被拖垮。

**Independent Test**: 人为制造查询失败（断开第三方、把快递公司编码清空），
分别打开 C 端与管理端订单页，确认提示一致、页面其余部分可用。

**Acceptance Scenarios**:

1. **Given** 轨迹查询超时或报错，**When** 客户打开订单详情，
   **Then** 物流区显示站内统一提示，订单的金额、商品、售后等其余内容照常可用。
2. **Given** 快递公司编码缺失（历史数据中确有留空的快递公司），
   **Then** 仍显示快递公司名称与运单号，轨迹区提示「暂不支持查询」，**不编造**任何轨迹节点。
3. **Given** 任意失败场景，**Then** 页面上不出现第三方错误码、英文异常原文，
   也不出现服务商未提供的「预计送达」等承诺性文案。

### Edge Cases

- **已签收 / 已完成订单**：轨迹继续可查，不因订单状态推进而隐藏物流区块。
- **运单号在、快递公司编码为空**：展示快递公司与运单号，轨迹区降级提示（US37-2）。
- **收件人手机号缺失**（历史导入单可能存在）：顺丰、中通等要求手机号，查询会失败
  —— 走统一降级，不影响订单其余内容。
- **同一运单被多个客户或多次打开**：服务端合并查询，不重复计费。
- **命中快递100 限频**（同一运单 30 分钟内重复查询 / 24 小时超 48 次）：
  直接降级提示，**不重试、不绕过**，避免被服务商锁定。
- **已取消订单（未支付时才会取消）**：不展示物流（没有有效运单）；
  **已发货后退款的订单仍照常可查** —— 轨迹是历史事实，不随退款消失。
- **小程序 / App**：既有查看物流能力不受影响（回归项）。
- **快递100 服务整体不可用**：C 端与后台表现一致 —— 都是「暂时无法获取」，订单其余功能正常。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-253**: 对「已发货且有运单号」的快递订单，C 端订单详情 MUST 展示物流信息：
  快递公司名称、运单号、发货时间，以及按发生时间**倒序**的轨迹列表（每条含时间与描述）。
  MUST NOT 额外展示「当前物流状态」标签（Q57：只展示轨迹节点）。
- **FR-254**: 订单尚未发货时，C 端订单详情 MUST NOT 展示物流区块（不显示空标题、空卡片）。
- **FR-255**: 虚拟商品订单与到店自提订单 MUST NOT 展示物流区块。
- **FR-256**: 物流轨迹 MUST 由服务端向快递100 实时查询；前端 MUST NOT 直连第三方，
  MUST NOT 内置、预置或本地缓存轨迹数据。
- **FR-257**: 物流轨迹 MUST 只对该订单的归属客户可见；任何越权请求 MUST 被拒绝
  （管理端可见性由 FR-265 的权限点另行约束）。
- **FR-258**: 物流查询失败（网络、超时、凭据失效、编码不识别、限频）MUST NOT 阻塞
  订单详情的其余内容；物流区 MUST 显示站内统一的可辨识提示。
- **FR-259**: 系统 MUST NOT 向客户展示第三方原始错误码、异常信息或英文原文。
- **FR-260**: 已发货但服务商返回空轨迹时，MUST 保留快递公司与运单号，
  并显示「暂无轨迹信息」的明确提示。
- **FR-261**: 若快递公司编码缺失或无法被服务商识别，MUST 仍展示快递公司名称与运单号，
  轨迹区降级为「暂不支持查询」；MUST NOT 编造轨迹或预计送达时间。
- **FR-262**: 同一运单的重复查看 MUST 由服务端合并，避免重复计费；
  合并窗口 MUST 不少于服务商允许的最小查询间隔（30 分钟），且沿用现状的 1 小时上限。
- **FR-263**: 系统 MUST 遵守快递100 的查询频率限制 —— 同一运单 30 分钟内不重复请求、
  24 小时不超过 48 次；命中限制时 MUST 降级，MUST NOT 反复重试。
- **FR-264**: 管理端订单列表 MUST 对已发货订单显示运单号，并提供进入物流轨迹的入口；
  管理端订单详情 MUST 展示与 C 端一致的轨迹（时间 + 描述）。
  本期维持「列表显示运单号 + 查看物流 → 详情页时间轴」的现状，MUST NOT 新增列表内联展开（Q56）。
- **FR-265**: 管理端物流查询 MUST 受既有权限点（`trade:order:query`）约束。
- **FR-266**: 物流轨迹 MUST 只做展示，MUST NOT 回写订单状态、订单字段，
  MUST NOT 产生任何金额、库存或售后变化。
- **FR-267**: 物流信息 MUST 来自服务商真实返回；MUST NOT 编造、猜测或补全任何轨迹节点。
- **FR-268**: 快递100 的授权码与密钥 MUST 由部署配置提供（Q55：已有企业版授权码），
  MUST NOT 出现在前端代码中，生产凭据 MUST NOT 明文提交到版本库。
- **FR-269**: 系统 MUST 让租户 162 现有 13 家快递公司能被快递100 识别：能确认对应关系的
  MUST 配置其快递100 编码；无法确认的 MUST 留空并按 FR-261 降级，MUST NOT 猜测编码。
  **MUST NOT 改动微信小程序物流同步所用的公司编码**（E11 / R48）。
- **FR-270**: 轨迹发生时间 MUST 与订单其余时间采用同一时区与展示格式。
- **FR-271**: 小程序 / App 既有的物流查看能力 MUST NOT 因本特性回归。
- **FR-272**: 进入 C 端订单详情时 MUST **自动加载**轨迹，客户无需额外点击（Q58）；
  MUST NOT 提供会绕过合并窗口的手动刷新入口。
- **FR-273**: C 端订单列表 MUST 对已发货订单提供「查看物流」入口，点击进入该订单详情（Q59）；
  列表 MUST NOT 直接展示轨迹内容，MUST NOT 为列表新增物流轨迹查询。
- **FR-274**: 物流查询失败 MUST 记录服务端日志，至少包含订单号、快递公司、失败摘要（Q60）；
  日志 MUST NOT 记录收件人手机号原文或第三方完整响应体。

### Key Entities *(include if feature involves data)*

- **订单（Order）**：物流展示的判定依据与查询入参 —— 配送方式、订单状态、
  快递公司、运单号、发货时间、收件人手机号。无运单号即无物流区块。
- **快递公司（Express Company）**：名称与**查询编码**。编码必须能被快递100 识别；
  编码缺失不等于公司名称缺失，两者要分开降级。
- **物流轨迹（Track）**：第三方的**实时数据，不落库**。每条含发生时间与描述
  （是否含「当前物流状态」见 Q57）。它的生命周期只有一次请求 + 一层服务端缓存。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-088**: 已发货订单：客户打开订单详情后 **5 秒内**看到物流区块（成功路径）；
  失败路径在 **10 秒内**出现降级提示，页面其余部分始终可用。
- **SC-089**: 「待发货 / 虚拟商品 / 到店自提」订单中出现物流区块的比例为 **0**。
- **SC-090**: 运营从后台订单列表到看到轨迹，不超过 **2 次点击**。
- **SC-091**: 同一运单在 1 小时内被重复打开 10 次时，对快递100 的**计费查询 ≤ 1 次**。
- **SC-092**: 在断网、凭据失效、编码为空、服务商限频四类异常下，

### User Story 4 - 客户/运营查看物流地图 (Priority: P2 · US38)

已发货订单的详情页可以在时间轴之外展开一张地图，看到包裹的大致运输路线。

**Acceptance Scenarios**:

1. **Given** 已发货、有运单号、有 `receiver_area_id`、快递公司有 `kd100_code` 的订单，
   **When** 点击「查看物流地图」，**Then** 详情页内出现快递100 的地图 iframe。
2. **Given** 发货地址/地图模板未配置，**Then** 显示「物流地图暂未配置」且**不渲染空 iframe**。
3. **Given** 历史订单没有 `receiver_area_id`，**Then** 显示「该订单暂无法生成物流地图」。
4. **Given** 未点击「查看物流地图」，**Then** 不发起地图查询（地图查询独立计费）。

### Functional Requirements（地图）

- **FR-275**: 已发货、有运单号、`receiver_area_id` 非空、快递公司 `kd100_code` 非空、
  且已配置发货地址与地图模板的快递订单，C 端与后台订单详情 MUST **进入即自动加载并展示地图**，
  **不需要点击**（Q63 修订）；同一运单 1 小时内由服务端缓存，避免重复计费。

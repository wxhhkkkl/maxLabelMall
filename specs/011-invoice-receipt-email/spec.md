**Feature Branch**: `011-invoice-receipt-email`

**Status**: Draft
**Input**: User description: "发票模块增加一个收据的选项；所有的前端开票加一个邮箱的选填项；选择抬头的显示顺序，应该先选企业/个人，再选 电子普通发票/电子增值税专用发票/收据 完后再出现选择抬头"

## 背景与问题

006 的发票模块目前只支持两种**电子发票**（普票 / 专票），且：

- 抬头选择器在票种**之前**出现，且只按票种过滤 —— 客户还没选企业/个人，就已经看到了一批抬头；
- 开票申请与抬头簿**没有邮箱**，运营开好后无法按客户指定的邮箱发送；
- 没有「收据」—— 非税票场景只能开普票。

本特性做三件事：**加收据**、**加邮箱**、**把「企业/个人 → 票种 → 抬头」的顺序理顺**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 开票时可选收据、留邮箱，并按新顺序选抬头 (Priority: P1 · US39)

客户在结算页（或订单详情补开）勾选开票后：

1. 先选 **企业 / 个人**；
2. 再选 **电子普通发票 / 电子增值税专用发票 / 收据**（收据企业与个人都能选）；
3. **之后**才出现「从已保存抬头里选一条」——列表只列**同企业/个人、同票种**的抬头；
4. 可填一个**选填邮箱**；抬头与邮箱在提交时一起落库。

**Why this priority**: 这是本特性唯一的用户可见增量，三个需求都在这一条路径上。

**Independent Test**: 结算页勾选开票 → 选「个人」→ 选「收据」→ 只看到个人的收据抬头 →
填邮箱 → 下单；请求体与订单详情里的开票信息都正确。

**Acceptance Scenarios**:

1. **Given** 勾选开票，**When** 依次选择企业/个人与票种，**Then** 抬头选择器在这两步**之后**出现，
   且只列与之相符的抬头。
2. **Given** 选择收据（企业或个人），**When** 只填抬头名称，**Then** 表单通过（不要求税号）。
3. **Given** 邮箱留空，**When** 提交，**Then** 通过；**Given** 填写非法邮箱，**Then** 提交被拦并提示「邮箱格式不正确」。
4. **Given** 选中一条已保存抬头，**Then** 抬头的字段与邮箱一起填进表单。
5. **Given** 个人 + 专票，**Then** 仍被拒（006 Q38 不变）；个人 + 收据允许。

### Edge Cases

- 收据的税号：填了要合法（选填不等于不校验）；不填通过。
- 抬头簿里没有当前「企业/个人 + 票种」的抬头：选择器仍显示「+ 新增抬头」。
- 历史抬头（006 时期没有邮箱）：邮箱为空，选中时表单邮箱为空，客户可补填。
- 后台列表/开具弹层：票种显示「收据」；邮箱为空显示「—」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-282**: 票种 MUST 增加「收据」（后端 `InvoiceTypeEnum.RECEIPT=3`，名称「收据」）；
  收据 MUST 允许企业与个人开；**抬头只要名称**，不要求税号。
- **FR-283**: 开票申请（下单时与订单详情补开）与抬头簿 MUST 都有一个**选填邮箱**；
  填了 MUST 通过格式校验，长度 ≤ 128；申请与抬头簿各存一份，选中抬头时带出。
- **FR-284**: 开票界面 MUST 按 **企业/个人 → 票种（普票/专票/收据）→ 抬头选择** 的顺序展示；
  抬头选择器 MUST 按「企业/个人 + 票种」双重过滤；MUST NOT 在票种之前展示。
- **FR-285**: 后台开票列表与「开具发票」弹层 MUST 展示**票种**（含收据）与**邮箱**（为空显示「—」）；
  收据的文件上传、状态、作废、退款撤回规则与发票一致。
- **FR-286**: 抬头簿 MUST 增加「收据」分段，收据抬头按企业/个人保存；各段的「新增」MUST 预选本段票种。
- **FR-287**: 006 的既有规则 MUST NOT 回归：企业普票/专票仍要「名称 + 税号」；个人 + 专票仍被拒；
  抬头快照、一单一条申请、退款撤回等行为不变。

### Key Entities

- **票种（InvoiceType）**：普票 / 专票 / **收据**；收据的必填只有抬头名称。
- **邮箱（Email）**：开票申请与抬头簿上的选填字段；后台展示，人工发送。
- **抬头（InvoiceTitle）**：票种 + 企业/个人 + 名称 + 可选税号/地址/电话/开户行/**邮箱**。

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 企业与个人都能成功提交「收据」开票申请（只填名称），**100%** 通过校验。
- **SC-102**: 邮箱留空可提交；填写非法邮箱 **100%** 被拦并给出「邮箱格式不正确」；合法邮箱原样落库。
- **SC-103**: 抬头选择器只出现与当前「企业/个人 + 票种」相符的抬头，**0 条**跨组合抬头。
- **SC-104**: 后台列表/开具弹层能看见票种「收据」与邮箱；普票/专票既有用例 **0 回归**。

---

## Assumptions

- 收据与发票共用同一套申请、状态、作废/退款撤回与文件上传流程；不新增独立表。
- 邮箱只做轻量格式校验，不验证可达性；本期不自动发送邮件。
- 006 的抬头簿按票种分开管理（Q36/Q38）继续有效，本特性只是把「收据」加进同一套分段与过滤。

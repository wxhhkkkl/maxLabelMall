## 背景与问题

桌面端已经具备应用内更新能力（018），但**更新源与分发物都没有落地的管理手段**：

| # | 现状 | 证据 |
|---|---|---|
| E1 | 桌面端把更新源地址**写死**在客户端里，打包后不可改 | `maxlabel/app/src/main/update/updateConfig.ts` 的 `DEFAULT_UPDATE_FEED`；`updateService.ts` 用它 `setFeedURL` |
| E2 | 该地址指向**本站服务器**目录，而该目录目前**并不存在** | `https://new.yuwangchenfa.com/updates/` → `/var/www/maxlabel/updates/`（未创建）；nginx 为 catch-all `root /var/www/maxlabel` |
| E3 | 安装包 200 MB 量级，一次更新就是一次完整下载 | 线上 `yudao-server.jar` 257 MB，桌面端安装包同量级 |
| E4 | 服务支持页目前只有内容，没有可下载的软件/驱动清单 | storefront `/support`、`/support/load-labels`、`/support/contact` 均为内容页 |
| E5 | 商城已有分类、文件上传与后台管理能力，但「软件版本」不是交易商品 | 既有 `product_category` / 文件上传 / 管理端页面框架 |

**问题**：每台客户端更新都要从应用服务器出一次 200 MB 流量；驱动文件同样没有统一的存放与分发入口，客服只能人工发文件。

## Clarifications

### Session 2026-10-27

- **Q83 桌面端如何确定「最新的更新包在哪」？**（2026-10-27 所有者拍板）
  → A: **客户端启动时向商城查询，拿到「最新版本 + 对象存储直链」后再下载**。
  不把存储地址写死在客户端里 —— 换存储、换域名、挂 CDN 都不用再发一次桌面端版本；
  商城只承担一次很小的版本查询，安装包仍然零经过应用服务器。
  代价：商城成为更新链路上的一环，因此查询失败 MUST 静默降级（FR-348）。

- **Q84 服务支持页对「桌面端软件」开放到什么程度？**（2026-10-27 所有者拍板）
  → A: **驱动 + 桌面端软件的「当前发布版本」**；历史版本不对外展示。
  这样「想装/重装最新版」的用户有官方入口，同时避免把已知缺陷的旧版本长期暴露在外、也避免被刷流量。
  历史版本仍保留在后台，供客服排障与回退。

- **Q85 下载直链用公开永久地址还是签名过期地址？**（2026-10-27 所有者拍板）
  → A: **公开永久直链**。地址长期有效、可被 CDN 充分缓存；防刷由 CDN / 对象存储侧的限流、
  Referer 白名单与异常告警承担，**不进入本功能的需求范围**。
  理由：签名地址会因时间戳不同而使 CDN 缓存命中率大幅下降，反而推高流量成本；
  安装包本身也不是需要保密的资产。

- **Q86「当前发布版本」按什么粒度唯一？**（2026-10-27 所有者拍板）
  → A: **软件 × 平台 × 架构**各至多一个「当前发布」，由系统保证唯一（含并发）。
  Windows x64 / Windows arm64 / macOS arm64 各自独立推进，互不干扰。

- **Q87 软件与版本能否删除，删除后文件如何处理？**（2026-10-27 所有者拍板）
  → A: **只做软删除**。删除后从后台列表与所有对外入口消失，但版本记录与对象存储文件保留，
  已经发出去的下载地址仍然可用（客服发过的链接不会变成 404）。物理删除不做。

- **Q88 服务支持页的信息结构？**（2026-10-27 所有者拍板）
  → A: **分类列表页 + 每款软件独立的详情页**，详情页有稳定、可分享、不需登录的地址；本期**不做搜索**。
  理由：客服最常用的动作是「把驱动链接发给客户」，独立地址直接支撑它；驱动数量在几十款量级，搜索暂不需要。

- **Q89「有没有更新」由谁判定？**（2026-10-27 所有者拍板）
  → A: **服务端判定**。客户端上报「当前版本 + 平台 + 架构」，服务端直接返回「有无更新 + 目标版本 + 直链 + 校验和」。
  客户端 MUST NOT 自行比较版本号 —— 版本比较是业务规则（宪法原则 III），
  也避免各平台客户端各写一套 `1.0.9` / `1.0.10` 的比较逻辑。

- **Q90 回滚「当前发布」后，已升级的客户端怎么办？**（2026-10-27 所有者拍板）
  → A: **视为已是最新**。客户端版本 ≥ 当前发布时返回「无可用更新」，**不降级、不打扰**。
  回滚的目的是拦住还没升级的人，而不是把已经升上去的人拽回来；降级还可能让旧版本读坏新数据。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运营维护软件、版本与更新包 (Priority: P1)

运营在管理端「软件分发」里新建一个软件（选择分类、填写标题与介绍），随后为它上传多个版本的安装包：填版本号、选择目标平台与架构、上传文件、填发布日期。上传完成后系统记录文件位置与校验和。运营可以把某个版本设为「当前发布」，也可以下架旧版本。

**Why this priority**：没有这一步，后面既没有可供客户端拉取的更新包，也没有可供用户下载的驱动，是整个模块的地基。

**Independent Test**：在后台新建一个软件 + 一个版本并完成上传 → 该版本出现在列表里且状态为可发布；下架后状态变为不可下载。

**Acceptance Scenarios**：

1. **Given** 运营已登录管理端，**When** 新建软件并填写分类、标题、介绍，**Then** 软件出现在列表中，分类与标题可被检索
2. **Given** 软件已存在，**When** 上传一个安装包并填写版本号、平台、架构、发布日期，**Then** 保存成功，列表显示版本号、平台、文件大小与发布日期
3. **Given** 同一软件已有 v1.0.22，**When** 再上传 v1.0.23 并设为当前发布，**Then** v1.0.23 成为该软件在该平台的当前发布版本，v1.0.22 变为历史版本
4. **Given** 某版本已发布，**When** 运营将其下架，**Then** 该版本不再出现在任何对外的下载入口，已被下载的文件不受影响
5. **Given** 上传过程中网络中断，**When** 运营重试，**Then** 不产生重复版本记录，也不产生残缺文件条目

### User Story 2 - 桌面端客户端更新不占应用服务器带宽 (Priority: P1)

已安装旧版本的客户端启动后检查更新，拿到最新版本的下载地址后**直接从对象存储下载**安装包，应用服务器只承担一次很小的版本查询（或完全不参与，取决于 Q83 的结论）。下载完成后校验文件，自动安装并重启。

**Why this priority**：这是提出本功能的直接动因——把 200 MB 量级的重复下载从应用服务器上挪走。

**Independent Test**：发布一个新版本 → 用旧版客户端触发更新 → 观察应用服务器出网流量在下载期间基本为零，客户端版本号变为新版本。

**Acceptance Scenarios**：

1. **Given** 客户端版本低于最新发布版本，**When** 启动检查更新，**Then** 向商城查询得到新版本号、对象存储直链与校验和，下载地址指向对象存储而非应用服务器
2. **Given** 客户端已开始下载，**When** 下载完成，**Then** 校验和与商城返回的一致后才安装；不一致则中止并保留当前版本
3. **Given** 客户端已是最新版本，**When** 检查更新，**Then** 提示已是最新，不发起下载
4. **Given** 最新版本在对象存储上的文件被删除或不可读，**When** 客户端尝试更新，**Then** 失败可感知且不破坏已安装版本
5. **Given** 一次完整更新，**When** 统计应用服务器的出网流量，**Then** 安装包流量为 0（只有一次很小的版本查询请求）
6. **Given** 商城版本查询不可用或超时，**When** 客户端检查更新，**Then** 静默跳过本次更新，软件各功能照常可用
7. **Given** 客户端是 macOS，**When** 检查更新，**Then** 拿到的是 macOS 的版本与文件，不会拿到 Windows 的安装包

### User Story 3 - 用户在服务支持里下载驱动 (Priority: P2)

用户打开服务支持页，按分类浏览打印软件驱动，看到每个软件的标题、介绍与可用版本（版本号、适用系统、文件大小、发布日期），点击即可直接从对象存储下载，无需登录。

**Why this priority**：这是对外的价值出口，但它依赖 US1 的录入；且在核心更新链路之外，可稍后交付。

**Independent Test**：后台录入一个驱动并发布 → 服务支持页出现该驱动与其版本 → 点击下载得到文件。

**Acceptance Scenarios**：

1. **Given** 运营已发布某驱动且标记为对外展示，**When** 用户打开服务支持页，**Then** 该驱动按分类出现在列表中，显示标题与介绍
2. **Given** 用户进入某个软件的详情，**When** 查看版本，**Then** 只看到**当前发布版本**（含版本号、适用系统、大小与发布日期）；桌面端软件的历史版本不对外展示
3. **Given** 用户点击某版本的下载，**When** 请求发出，**Then** 浏览器/客户端直接从对象存储下载，不经过应用服务器中转
4. **Given** 用户未登录，**When** 访问服务支持页并下载，**Then** 流程可完成，不要求登录
5. **Given** 某驱动被下架，**When** 用户刷新服务支持页，**Then** 该驱动不再出现，直接访问其详情页给出明确提示
6. **Given** 客服把某款软件详情页的地址发给客户，**When** 客户未登录直接打开该地址，**Then** 页面正常展示该软件的介绍与当前发布版本，可直接下载
7. **Given** 用户在服务支持页浏览，**When** 页面加载完成，**Then** 可按分类浏览并进入各软件详情页；页面**不提供**软件搜索入口（Q88）

---

### User Story 4 - 运营维护分类与展示范围 (Priority: P3)

运营新增、改名、排序、启用或停用软件分类，并控制每个软件是否出现在服务支持页。

**Why this priority**：属于运营效率与内容组织，没有它也能先跑通核心链路。

**Independent Test**：新建一个分类并排序 → 服务支持页按新顺序展示；停用分类后其下软件不再出现。

**Acceptance Scenarios**：

1. **Given** 运营新建分类并设置排序，**When** 保存，**Then** 服务支持页按该顺序分组展示
2. **Given** 某软件被设为「不在服务支持展示」，**When** 用户浏览服务支持页，**Then** 该软件不出现，但其在用的更新包仍可被客户端正常拉取
3. **Given** 某分类被停用，**When** 用户浏览服务支持页，**Then** 该分类及其下软件均不出现

### Edge Cases

- **文件已入库但对象存储上传失败**：不允许出现「有版本记录、点下载却 404」的状态；上传未确认前版本不可发布。
- **同一软件同一平台同一架构被并发设为两个「当前发布」**：按 Q86 由系统保证唯一——最终只有一个当前发布，另一个请求要么被拒绝，要么成为历史版本，MUST NOT 出现双当前发布。
- **版本号格式不合法**（例如 `1.0`、`v1.0.23-beta` 等）：给出明确提示，不允许进入列表。
- **下架或删除的版本仍被旧客户端引用**：已下载的用户不受影响；未下载的用户下次检查时拿到新的当前发布版本。
- **超大文件上传超时或中断**：可重试、可续传或至少可重新上传，不留下半截记录。
- **对象存储直链被外部刷流量**：按 Q85 使用公开永久直链，防刷由 CDN / 对象存储的限流、Referer 白名单与异常告警承担；本功能只负责「地址不失效」，不承担防刷。
- **客户端拿到的下载地址失效**（对象存储迁移/重命名）：更新失败必须可感知，且不影响已安装版本。
- **同一版本既给客户端更新、又作为对外下载**：两处展示的版本信息必须一致，不出现「客户端更新到 A、官网挂着 B」。
- **商城版本查询不可用或响应异常**：客户端静默跳过本次更新、软件照常可用（Q83 引入的新依赖，必须有降级路径）。
- **客户端平台/架构在后台没有对应版本**：返回「无可用更新」，不得回退到其他平台的文件。
- **服务支持页与客户端对「当前发布」的理解不一致**：两者 MUST 使用同一份「当前发布」数据，不允许各判各的。
- **软删除后仍有人用过旧的下载链接**：按 Q87，文件与地址必须继续可用；删除只影响列表可见性，不制造 404。
- **运营回滚「当前发布」**：已经升级到更高版本的客户端视为已是最新，不降级、不提示；尚未升级的客户端拿到回滚后的版本（Q90）。
- **客户端上报的版本号格式异常或不可解析**：服务端按「无法判定」处理并返回「无可用更新」，不得据此下发任何文件。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 软件、分类与版本

- **FR-330**: 系统 MUST 支持运营维护**软件分类**，至少包含名称、排序、启用状态；分类 MUST 可新增、改名、排序、启用与停用。
- **FR-331**: 系统 MUST 支持运营维护**软件**，至少包含所属分类、标题、介绍、类型（桌面端软件 / 打印驱动）、是否在服务支持页展示、发布状态。
- **FR-332**: 同一个软件 MUST 支持**多个版本**；每个版本至少记录版本号、目标平台、目标架构、文件名、文件大小、校验和、发布日期、是否当前发布、发布状态。
- **FR-333**: 系统 MUST 校验版本号的格式与唯一性：同一软件同一平台同一架构下，版本号 MUST NOT 重复。
- **FR-334**: 桌面端客户端 MUST 在检查更新时向商城上报「当前版本 + 平台 + 架构」，由服务端返回**「有无更新 + 目标版本 + 下载直链 + 校验和」**（Q83 / Q89）；MUST NOT 把存储地址写死在客户端里，也 MUST NOT 由客户端自行比较版本号。查询请求的响应 MUST 足够小，MUST NOT 携带安装包本体。
- **FR-335**: **安装包文件本身 MUST NOT 经过应用服务器**；对外下发的下载地址 MUST 是对象存储（或其加速域名）的**公开永久直链**，MUST NOT 带过期时间或用户维度的签名（Q85）。商城的版本查询响应 MUST NOT 承载文件本体。
- **FR-351**: 已发布版本的下载地址 MUST 长期有效：发布后不得因时间推移而失效；地址变更 MUST 只发生在存储迁移等运维动作中，且 MUST 保留旧地址**至少 90 天**仍可下载（与 FR-335 同源，不重复定义直链形态）。
- **FR-352**: 同一软件在**同一平台与架构**下 MUST 至多有一个「当前发布」版本；并发设置当前发布时 MUST 由系统保证唯一，MUST NOT 出现双当前发布（Q86）。设为当前发布后，同平台同架构的原当前发布 MUST 自动降为历史版本。
- **FR-336**: 下载地址 MUST 带校验信息；客户端与浏览器下载后 MUST 能验证文件未被篡改或截断。

#### B. 上传与存储

- **FR-337**: 运营上传安装包/驱动时，系统 MUST 在文件成功写入对象存储后才把版本置为可发布；上传失败 MUST NOT 留下可发布的残缺记录。
- **FR-338**: 系统 MUST 记录并展示每个版本的文件大小与校验和。**文件大小** MUST 由服务端在上传后回源核对，与实际对象不一致时 MUST 拒绝登记；**校验和** 由上传端计算并登记，并由客户端在下载完成后最终验证（SC-131）。服务端 MUST NOT 为了核对校验和而下载整个安装包。
- **FR-339**: 文件 MUST NOT 长期存放在应用服务器本地磁盘；仅允许作为上传过程中的临时中转，且 MUST 有清理策略。

#### C. 对外的服务支持页

- **FR-340**: 服务支持页 MUST 按分类展示已发布且标记为对外展示的软件，至少显示标题与介绍。
- **FR-341**: 软件详情 MUST 列出可用版本（版本号、适用系统、文件大小、发布日期），并提供直接下载入口。
- **FR-354**: 每款对外展示的软件 MUST 拥有**稳定、可直接访问、可分享**的详情地址，且该地址 MUST NOT 依赖登录态（Q88）；本期 MUST NOT 提供软件搜索功能。
- **FR-342**: 服务支持页与下载 MUST 对**未登录用户**开放。
- **FR-343**: 服务支持页 MUST 展示**打印驱动**与**桌面端软件的当前发布版本**（Q84）；桌面端软件的**历史版本 MUST NOT** 在该页对用户展示，但仍保留在后台供客服排障与回退。

#### D. 管理端与运营

- **FR-344**: 运营 MUST 能在管理端完成分类、软件、版本的增删改查与排序。
- **FR-345**: 运营 MUST 能对单个版本执行发布与下架；下架 MUST NOT 删除历史记录与已上传文件。
- **FR-353**: 删除 MUST 为**软删除**（Q87）：删除后软件/版本 MUST 从后台列表与所有对外入口消失，但版本记录与对象存储文件 MUST 保留，已对外发出的下载地址 MUST 仍然可以下载；系统 MUST NOT 提供物理删除。
- **FR-346**: 运营在软件与版本上的关键操作（创建、发布、下架、删除）MUST 记录操作人与时间。

#### E. 与既有更新链路的衔接

- **FR-347**: 桌面端「当前版本 → 最新版本」的判定 MUST 由**服务端**做出并与后台的「当前发布」一致（Q89）；客户端 MUST NOT 自行实现版本比较规则，MUST NOT 因为后台数据缺失而把已安装版本判为过期。
- **FR-355**: 客户端上报的版本**大于或等于**当前发布版本时（含运营回滚后的场景），服务端 MUST 返回「无可用更新」；系统 MUST NOT 自动降级安装，也 MUST NOT 因此打扰用户（Q90）。
- **FR-348**: 客户端检查更新失败（网络、服务不可用、数据缺失）MUST 静默降级为「本次不更新」，MUST NOT 影响软件正常使用。
- **FR-349**: 系统 MUST NOT 因本功能改变既有桌面端的本地编辑、打印与授权判定行为。
- **FR-350**: 版本查询 MUST 按客户端上报的**当前平台与架构**返回匹配的版本；无匹配版本时 MUST 明确返回「无可用更新」，MUST NOT 返回其他平台的文件。

### Key Entities

- **软件分类**：名称、排序、启用状态。
- **软件**：所属分类、标题、介绍、类型（桌面端软件 / 打印驱动）、是否在服务支持页展示、发布状态。
- **软件版本**：所属软件、版本号、目标平台、目标架构、文件名、文件大小、校验和、存储地址、发布日期、是否当前发布、发布状态。
- **更新元数据**（派生，不单独录入）：由「当前发布」的版本汇总而来，供桌面端判断「有无更新、去哪下载、校验和是多少」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-126**: 一次完整客户端更新期间，应用服务器的安装包出网流量为 **0**（允许存在不超过 10 KB 的版本查询请求）。
- **SC-127**: 运营从「新建软件」到「完成一个版本发布」≤ **5 分钟**，且不需要工程人员介入。
- **SC-128**: 用户从进入服务支持页到开始下载某驱动 ≤ **3 次点击**。
- **SC-129**: 100% 的对外下载地址指向对象存储直链；抽查 10 个版本，经应用服务器中转的数量为 **0**。
- **SC-130**: 发布后 100% 的旧版本客户端在一次检查内能看到新版本（在客户端处于联网且未关闭更新检查的前提下）。
- **SC-131**: 文件校验不通过的下载 **100%** 被拒绝安装/安装中止，且已安装版本保持可用。
- **SC-132**: 后台录入并发布的软件/驱动在服务支持页的可见性正确率为 100%（对外展示与下架状态一致，抽样 20 条）。
- **SC-133**: 服务支持页**不出现**桌面端软件的历史版本：抽样 20 个已发布软件的历史版本，出现次数为 **0**（Q84）。
- **SC-134**: 商城版本查询不可用时，客户端仍能正常启动并使用全部功能，成功率 100%（降级路径，负向测试）。
- **SC-135**: 已发布版本的下载地址长期有效：抽样 10 个已发布版本，**30 天后**重新访问仍可直接下载，成功率 100%（Q85）。
- **SC-136**: 同一软件 × 平台 × 架构下的「当前发布」恒为 1 个：并发发起 10 次「设为当前发布」，最终当前发布数量为 1，无失败残留（负向并发测试，Q86）。
- **SC-137**: 软删除不影响已发出的链接：抽样 10 个已删除版本的下载地址，仍可下载的成功率为 100%，且它们不再出现在任何列表（Q87）。
- **SC-138**: 每款对外展示的软件都有可直接分享的详情地址：未登录直接打开 10 个抽样地址，正常展示并可直接下载的比例为 100%（Q88）。
- **SC-139**: 回滚「当前发布」后，已升级到更高版本的客户端 **100%** 被判定为「已是最新」，不触发下载、不出现降级提示（负向测试，Q90）。

## 范围边界（非目标）

- **不做**灰度发布、分批推送、指定用户群更新。
- **不做**强制更新、最低版本限制、更新倒计时。
- **不做**增量/差分更新的自研实现（若既有更新客户端支持差量，沿用其能力，不在此另行设计）。
- **不做**软件授权、License 校验、下载鉴权与付费下载。
- **不做**驱动与具体打印机型号的自动匹配/自动安装。
- **不做**多语言版本管理（标题与介绍按站点现有语言策略处理）。
- **不改**商城既有的商品、订单、支付链路。

## Assumptions

- 商城已经具备（或复用）对象存储/文件上传能力，本功能只负责组织与分发，不新造一套存储体系。
- 软件与驱动共用同一套「分类 → 软件 → 版本」结构；驱动只是软件的一种类型。
- 对外下载**公开、免登录、地址永久有效**（Q85）；防刷与防盗链策略在 CDN / 对象存储侧配置，不属于本功能需求。
- 版本号采用通行的语义化三段式（如 `1.0.23`），预发布标记本期不支持。
- 桌面端当前版本号来源沿用 018 既有实现；本功能不改客户端的版本比较规则。
- 已装机且版本低于首个支持本功能的客户端，仍需**人工安装一次**才能进入自动更新链路。
- 按 Q83，商城成为更新链路的**查询方**：其可用性只影响「本次能否更新」，不影响软件本身的任何功能；客户端必须有超时与静默降级。
- 按 Q84，服务支持页只暴露**当前发布版本**；历史版本保留在后台，仅运营/客服可见。
- 平台与架构按「客户端上报什么就匹配什么」处理；本期不要求同一版本跨平台共用一个包。
- 单个上传文件按对象存储的常规限制处理（默认 ≤ 2 GB）；更大的包由运维另行协调，不纳入本期需求。
- 后台权限沿用商城既有 RBAC；本规格只要求「运营可管理分类、软件与版本」，具体权限点划分在计划阶段确定。
- 安装包与驱动由运营在后台手工上传，本期不做自动化流水线接入。
- 对象存储的直链域名与防护策略（限流/签名/CDN）由运维配置，属于上线前置条件。

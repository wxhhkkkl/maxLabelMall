# 功能规格：代客下单（运营管理端）

> 编号续 016：本规格从 **FR-431 / SC-161 / US54 / Q123** 接着往下排
> （016 排到 FR-430 / SC-160 / US53 / Q122）。

**Feature Branch**: `017-agent-order`
**Created**: 2026-11-06
**Status**: Draft
**Input**: User description: "管理员后台做一个代客下单的功能，由运营人员替代客户使用客户账户的名义下订单，后台记录是谁帮忙下单的。"

---

## 背景与问题

| # | 现状 | 证据 |
|---|---|---|
| E1 | 管理端只能处理**已经存在**的订单（查询、调价、改地址、发货、取消、确认收款），没有创建订单的入口 | `TradeOrderController` 只有 page / get-detail / delivery / update-price / cancel 等操作 |
| E2 | 下单与计价完全在 C 端完成，价格由服务端按**当前登录会员**计算；运营无法替客户走这条链路 | `TradeOrderUpdateServiceImpl#settlementOrder(userId, …)` / `#createOrder(userId, …)` |
| E3 | 支付渠道已经具备「微信扫码 / 支付宝扫码」在线支付与「对公转账」线下支付；管理端已有收银台页面可展示二维码 / 支付链接 | `PayChannelEnum`；管理端 `views/pay/cashier` |
| E4 | 已有「用户端不允许自助退款、后台人工通道保留」的先例（企业授权订单、个人订阅订单、印刷定制订单） | `AfterSaleServiceImpl#validateOrderItemApplicable` |
| E5 | 订单没有记录「谁替客户下的单」；订单日志只记录操作类型，不能按代下单人筛选 | `trade_order` 无代下单人字段；`TradeOrderOperateTypeEnum` 只有「用户下单」 |

**问题**：客户不方便自己下单时（例如电话沟通、企业采购、老年客户），运营只能口头指导客户操作，
既慢又容易出错；即使运营代为操作，系统也**无法证明**这笔订单是谁替客户建的。需要新增一条
「运营以客户账户名义下单」的受控通道，并把**代下单人**作为订单的正式属性记录下来。

## Clarifications

### Session 2026-11-06

- **Q123 代客下单支持哪些支付方式？**（2026-11-06 所有者拍板）
  → **A：复用现有渠道，不新增渠道**。支持「微信扫码」「支付宝扫码」两种真实在线支付，
  以及「对公转账」；**不支持**后台把订单直接标记为已收款。在线支付必须由客户实际扫码付款，
  以支付平台回调成功为准。
- **Q124 哪些商品允许代客下单？**（2026-11-06 所有者拍板）
  → **A：复用现有下单校验**。普通实物、虚拟商品、企业授权商品都可以；**印刷定制商品不允许**；
  **门店自提不允许**；只支持快递配送与纯虚拟商品（无需配送）。
- **Q125 价格与优惠怎么算？**（2026-11-06 所有者拍板）
  → **A：按目标客户的正常价格计算**（会员价、活动价、运费等服务端规则），
  **不使用优惠券、不抵扣积分**；运营不能直接指定成交价。下单后如需改价，沿用现有「订单调价」并留痕。
- **Q126 代客订单的退款怎么处理？**（2026-11-06 所有者拍板）
  → **A：客户侧禁止自助退款，运营可在后台代客户发起售后**。C 端不显示退款/售后入口，
  服务端也拒绝对代客订单直接发起售后；运营在后台订单详情可**代客户创建售后单**，复用现有
  售后审核与退款动作。在线支付（微信/支付宝）按现有链路原路退款；对公转账与线下收款仍由
  财务线下打款。售后单 MUST 记录代操作的后台用户，客户侧 MUST NOT 因此获得自助退款入口。
- **Q127 客户能不能看出这是代客订单？**（2026-11-06 所有者拍板）
  → **A：能看出「客服代下单」，但看不到具体是谁**。C 端订单列表与详情显示中性标识；
  **不显示**运营人员姓名、账号或内部编号。后台列表与详情显示代下单人。
- **Q128 目标客户与收货地址有什么限制？**（2026-11-06 所有者拍板）
  → **A：客户必须是已注册会员**（不提供"先注册再下单"）；收货地址只能从**客户地址簿**中选择，
  运营不能手工新建或修改客户地址；客户没有可用地址时拒绝下单，并提示客户先在 C 端添加。
- **Q129 权限与留痕怎么定？**（2026-11-06 所有者拍板）
  → **A：独立权限点 + 订单级留痕**。只有被授予「代客下单」权限的后台角色才能看到入口并调用接口；
  每笔代客订单持久记录代下单的后台用户与下单时间；订单日志额外记录一条「运营代客下单」；
  后台列表可按「代客 / 客户自助」筛选，列表与统计同一口径。
- **Q130 在线支付未完成时，之后能不能继续收款？**（2026-11-06 所有者拍板）
  → **A：不能，支付只在代客下单页面内完成**。提交成功后的支付步骤内可重新生成二维码并重试
  （可重新选择微信 / 支付宝）；**离开该页面后**，后台订单详情 MUST NOT 提供「继续收款」入口，
  未支付订单只能由运营取消后重新代客下单，或等待现有超时规则取消。
- **Q131 客户能不能自行取消代客订单？**（2026-11-06 所有者拍板）
  → **A：不能**。C 端订单详情 MUST NOT 显示「取消订单」入口；服务端 MUST 拒绝客户取消代客订单，
  并提示联系客服。取消只能由运营在后台按现有「取消订单」能力处理（仍仅限未支付订单）。
  客户仍可正常支付未支付的代客订单。
- **Q132 代客订单在后台「订单来源」怎么显示？**（2026-11-06 所有者拍板）
  → **A：新增独立来源「后台代客」**。代客订单的来源 MUST 显示为「后台代客」，来源筛选与报表
  MUST 能直接区分；MUST NOT 落入「未知」或伪装成客户常用终端。
- **Q133 后台「代客发起售后」由谁使用、用什么权限？**（2026-11-06 所有者拍板）
  → **A：新增独立的「代客售后」权限**，与「代客下单」权限分离；只有被授予该权限的角色
  （通常是客服主管 / 财务）能发起，能代下单不代表能退款。实际售后审核与退款动作仍由现有
  售后权限控制，形成两道关。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运营以客户名义创建订单 (Priority: P1 · US54)

运营人员在管理端打开「代客下单」，先搜索并选定目标客户，再选择商品与数量、从客户的地址簿中选择
收货地址，看到服务端算出的价格后用客户账户创建订单。订单出现在**客户自己的订单列表**里，
与客户自助下单的订单形态一致；后台同时记下是哪位运营替客户下的单。

**Why this priority**：这是整个特性的主干。没有它，后面的支付、留痕与退款限制都无从附着。

**Independent Test**：选一个已有地址的客户，选一件实物商品，提交后：
① 后台订单列表出现该订单且「代下单人」为该运营；② 用客户账号登录 C 端能看到这笔待支付订单；
③ 订单金额与客户自己买同款同数量一致。

**Acceptance Scenarios**：

1. **Given** 运营拥有代客下单权限，**When** 搜索客户手机号并选定客户，**Then** 能看到客户昵称、手机号与可用地址
2. **Given** 已选定客户与一件实物商品，**When** 选择客户地址并预览价格，**Then** 服务端返回商品明细、原价、优惠、运费、应付金额与配送方式
3. **Given** 预览无误，**When** 选择在线支付并提交，**Then** 订单创建成功，所属客户为目标客户，金额等于服务端最终计价
4. **Given** 客户没有可用地址，**When** 为实物商品提交，**Then** 被拒绝，提示客户先在 C 端添加收货地址
5. **Given** 客户选择的是纯虚拟商品，**When** 提交，**Then** 不要求地址，且不产生运费
6. **Given** 商品库存不足或已下架，**When** 提交，**Then** 被拒绝并说明具体原因，不产生订单

### User Story 2 - 在线支付：微信 / 支付宝扫码 (Priority: P1 · US55)

订单创建后，运营选择微信或支付宝，后台向现有在线支付渠道发起支付并展示二维码或支付链接。
客户用自己的微信 / 支付宝扫码付款；支付平台回调成功后，订单自动进入待发货。运营在页面上看到
支付结果，并可跳转到订单详情。

**Why this priority**：这是代客下单最常用的收尾方式；没有它，订单只能停在待支付。

**Independent Test**：创建一笔代客订单，选择微信或支付宝，后台出现二维码；用测试账号扫码支付后，
后台与 C 端订单状态都变为待发货；未支付时订单保持待支付。

**Acceptance Scenarios**：

1. **Given** 一笔待支付的代客订单，**When** 运营选择微信扫码，**Then** 后台展示微信支付二维码
2. **Given** 一笔待支付的代客订单，**When** 运营选择支付宝扫码，**Then** 后台展示支付宝支付二维码或链接
3. **Given** 客户扫码并完成支付，**When** 支付回调到达，**Then** 订单变为待发货，后台页面显示支付成功
4. **Given** 客户未支付，**When** 运营离开代客下单页面，**Then** 订单保持待支付，后台订单详情不出现「继续收款」入口；运营只能取消后重建，或等待现有超时规则取消
5. **Given** 支付渠道未配置或调用失败，**When** 运营选择该渠道，**Then** 返回可读原因，订单仍为待支付
6. **Given** 客户在 C 端自行打开这笔代客订单并支付，**When** 支付成功，**Then** 与后台发起的支付结果一致

---

### User Story 3 - 对公转账 (Priority: P2 · US56)

运营选择对公转账时，订单创建为「待收款」，不生成在线支付单；客户或企业按现有对公账户线下打款，
财务在后台用现有的「确认收款」流程把订单推进到待发货。

**Why this priority**：企业客户常用对公转账；它复用现有 008 流程，增量小，但能覆盖重要的采购场景。

**Independent Test**：创建对公转账代客订单 → 订单显示待收款且没有在线支付二维码；财务确认收款后
订单变为待发货，确认人、流水号照常记录。

**Acceptance Scenarios**：

1. **Given** 对公转账开关已开启，**When** 运营选择对公转账并提交，**Then** 订单创建为待收款，不产生在线支付单
2. **Given** 对公转账开关未开启，**When** 运营选择对公转账，**Then** 被拒绝并说明未开启
3. **Given** 一笔待收款的代客订单，**When** 财务确认收款，**Then** 订单进入待发货，确认信息照常留痕
4. **Given** 一笔待收款的代客订单，**When** 在 C 端查看，**Then** 订单显示待收款，不显示在线支付入口

---

### User Story 4 - 代下单留痕与查询 (Priority: P1 · US57)

后台订单列表与详情都能看到「代下单人」，列表支持只看代客订单或只看客户自助订单；
订单日志里有一条明确的「运营代客下单」记录。即使运营账号后来改名或停用，历史订单仍然能追溯到
当初下单的后台用户编号。

**Why this priority**：所有者明确提出「后台记录是谁帮忙下单的」；没有可查询的留痕，这条需求没有落地。

**Independent Test**：创建一笔代客订单后，在列表筛选「代客下单」能看到它、筛选「客户自助」看不到；
详情显示代下单人；订单日志出现「运营代客下单」。

**Acceptance Scenarios**：

1. **Given** 一笔代客订单，**When** 打开后台订单列表，**Then** 该行显示代下单人
2. **Given** 混合了代客与客户自助订单，**When** 筛选「代客下单」，**Then** 只出现代客订单；筛选「客户自助」时相反
3. **Given** 代客订单列表与顶部统计，**When** 应用同一筛选，**Then** 统计数字与列表条数口径一致
4. **Given** 打开代客订单详情，**When** 查看基础信息，**Then** 能看到代下单人与下单时间
5. **Given** 查看订单操作日志，**When** 找到创建记录，**Then** 内容为「运营代客下单」且包含代下单人
6. **Given** 一笔客户自助订单，**When** 查看列表与详情，**Then** 不显示代下单人，也不出现代客日志
7. **Given** 一笔代客订单，**When** 查看后台订单来源，**Then** 显示「后台代客」，且来源筛选可按它筛出

### User Story 5 - 客户侧标识与禁自助退款 (Priority: P1 · US58)

客户在自己的订单列表与详情里能看到「客服代下单」标识，但看不到具体是哪位运营；
代客订单不出现「申请退款 / 申请售后」入口。即使客户直接调用退款接口，服务端也会明确拒绝，
并提示联系客服处理。

**Why this priority**：这是所有者拍板的两个客户可见口径，直接决定客户体验与资金风险。

**Independent Test**：用客户账号打开代客订单列表与详情 → 看到「客服代下单」标识、看不到运营姓名；
已支付后仍无退款入口；直接调用售后接口被拒绝且文案可读。

**Acceptance Scenarios**：

1. **Given** 代客订单在客户账号下，**When** 查看订单列表，**Then** 该订单显示「客服代下单」标识
2. **Given** 打开代客订单详情，**When** 查看页面，**Then** 显示「客服代下单」标识，且不出现运营姓名/账号
3. **Given** 代客订单已支付且进入待发货，**When** 客户查看订单项，**Then** 不显示「申请退款」入口
4. **Given** 客户绕过界面直接请求退款，**When** 服务端处理，**Then** 明确拒绝并提示联系客服
5. **Given** 一笔客户自助订单，**When** 客户查看，**Then** 不显示「客服代下单」标识，退款规则与改动前一致
6. **Given** 一笔未支付的代客订单，**When** 客户查看详情，**Then** 不显示「取消订单」入口；直接调用取消接口被拒绝并提示联系客服

### User Story 6 - 后台代客户发起售后 (Priority: P2 · US59)

客户不能自助退款，但运营可以在后台订单详情为代客订单**代客户发起售后**，填写退款原因与金额后
进入现有售后审核与退款流程。在线支付（微信/支付宝）按现有链路原路退款；对公转账与线下收款
由财务线下打款。售后单能看出是后台代操作发起的，客户仍能在「我的售后」里看到处理进度。

**Why this priority**：它是「客户不能自助退款」的必要配套；没有它，代客订单一旦需要退款，
系统里没有任何可走的通道，只能靠线下口头记录，账实会对不上。

**Independent Test**：对一笔已支付的代客订单，在后台发起售后并审核通过；客户在 C 端「我的售后」
能看到该记录；在线支付订单的退款按原支付渠道原路退回，对公订单由财务线下打款并留痕。

**Acceptance Scenarios**：

1. **Given** 一笔已支付的代客订单，**When** 运营在后台发起售后并填写原因与退款金额，**Then** 售后单创建成功
2. **Given** 售后单创建成功，**When** 客户打开 C 端「我的售后」，**Then** 能看到该售后单及处理进度
3. **Given** 在线支付的代客订单，**When** 财务按现有流程同意并退款，**Then** 款项按原支付渠道退回
4. **Given** 对公转账的代客订单，**When** 财务处理退款，**Then** 由财务线下打款，系统记录处理结果
5. **Given** 一笔客户自助订单，**When** 运营查看后台订单详情，**Then** 不出现「代客发起售后」入口
6. **Given** 客户绕过界面直接调用售后接口，**When** 服务端处理，**Then** 仍按 FR-462 明确拒绝
7. **Given** 运营只有「代客下单」权限、没有「代客售后」权限，**When** 打开代客订单详情或直接调用接口，**Then** 不出现「代客发起售后」入口，接口也拒绝

### Edge Cases

- **客户在运营操作期间自己下了同一商品**：两笔订单相互独立；库存与价格在各自提交时由服务端重新校验，
  不因另一笔在途订单而放行超卖。
- **客户想取消代客订单**：C 端不显示取消入口，客户联系运营；运营在后台对未支付订单执行取消。
- **地址在下单前被客户删除或修改**：提交时服务端重新校验地址归属；地址已不存在时拒绝并提示重新选择。
- **预览价格与提交价格不一致**：以提交时服务端重算结果为准；若金额变化，返回最终金额让运营知晓。
- **支付二维码过期或客户长时间未付**：在代客下单页面内可重新生成二维码并重试（允许换微信/支付宝）；
  离开页面后订单保持待支付，直到现有超时规则取消，或由运营在后台取消后重建。
- **客户在 C 端先一步支付了代客订单**：支付回调正常推进订单，后台页面刷新后显示已支付，不重复收款。
- **在线支付渠道未配置 / 被停用 / 调用失败**：返回可读原因，订单不进入已支付；不影响对公转账。
- **客户账号被禁用或删除**：拒绝代客下单并说明客户状态不可用。
- **企业授权商品**：客户不是该企业 OWNER/ADMIN、企业已停用、续费席位数少于当前有效席位时，
  按现有企业订单规则拒绝。
- **运营账号被停用或权限被收回**：无法进入入口；已创建的历史订单与代下单记录不受影响。
- **重复点击提交**：提交期间入口禁用，避免产生两笔相同订单；若仍产生两笔，按现有后台取消流程处理。
- **对公转账开关未开启**：不展示/不允许选择对公转账；已存在的待收款订单不受影响。

## Requirements *(mandatory)*

### 入口与权限

- **FR-431**: 管理端 MUST 提供「代客下单」入口；只有被授予独立「代客下单」权限的后台用户
  才能看到入口并成功调用。无权限用户 MUST NOT 看到入口，直接调用 MUST 被拒绝。
- **FR-432**: 代客下单 MUST 先选定目标客户；客户 MUST 是已注册且状态正常的会员；
  支持按手机号、昵称、会员编号检索；未选定客户时 MUST NOT 进入商品选择与提交。
- **FR-433**: 系统 MUST NOT 为不存在、已注销或被禁用的会员创建订单；MUST NOT 代未注册用户下单。
- **FR-434**: 「代客下单」权限 MUST 独立于「订单更新」与「确认收款」权限；
  没有该权限的角色 MUST NOT 通过任何入口创建代客订单。

### 商品、地址与计价

- **FR-435**: 允许的商品范围 MUST 复用客户自助下单的服务端校验：普通实物、虚拟商品、
  企业授权商品均可；印刷定制商品 MUST 被拒绝。
- **FR-436**: 代客下单 MUST NOT 支持门店自提；只支持快递配送与纯虚拟商品（无需配送）。
- **FR-437**: 价格 MUST 由服务端按目标客户的正常价格规则计算；运营 MUST NOT 直接输入成交价；
  创建时 MUST NOT 使用优惠券、MUST NOT 抵扣积分。
- **FR-438**: 提交前 MUST 提供服务端计价预览，至少包含商品明细、数量、原价、优惠、运费、
  应付金额、配送方式与收件地址。
- **FR-439**: 提交时 MUST 以服务端重新计算的结果为准；MUST NOT 采用客户端传来的金额；
  若与预览不一致，MUST 向运营回传最终金额。
- **FR-440**: 库存不足、商品下架/禁用、企业授权商品无购买资格、企业续费席位数不足等情形
  MUST 被拒绝，并给出可读的失败原因。
- **FR-441**: 实物订单 MUST 从目标客户的地址簿中选择收件地址；运营 MUST NOT 手工新建或修改客户地址；
  客户没有可用地址时 MUST 拒绝下单，并提示客户先在 C 端添加。
- **FR-442**: 纯虚拟商品订单 MUST NOT 要求收货地址，且 MUST NOT 产生运费。
- **FR-443**: 计价预览与订单创建 MUST 使用同一套服务端价格规则，MUST NOT 出现无原因的
  「预览一个价、下单另一个价」。

### 支付

- **FR-444**: 下单时 MUST 由运营显式选择支付方式：微信扫码、支付宝扫码或对公转账。
- **FR-445**: 微信/支付宝 MUST 使用现有在线支付渠道发起**真实支付**；MUST NOT 由后台直接把订单
  标记为已支付，也 MUST NOT 使用模拟支付渠道。
- **FR-446**: 在线支付成功后，后台 MUST 展示支付渠道返回的二维码或支付链接，供客户扫码/打开付款。
- **FR-447**: 在线支付 MUST 以支付平台回调成功为准；回调到达前订单 MUST 保持待支付。
- **FR-448**: 在线支付渠道未配置、被停用或调用失败时 MUST 拒绝发起并返回可读原因；
  订单 MUST 保持待支付。运营 MUST 能在**当前代客下单页面**内重试（可重新选择微信/支付宝）；
  离开该页面后 MUST NOT 再提供继续收款入口。
- **FR-449**: 对公转账 MUST 沿用现有「待收款 → 财务确认收款」流程；
  MUST NOT 为对公转账单创建在线支付单，MUST NOT 在代客下单时直接确认收款。
- **FR-450**: 对公转账开关未开启时，代客下单 MUST NOT 允许选择对公转账。
- **FR-451**: 代客订单 MUST 沿用现有订单状态机、库存扣减、发货、收货、评价与超时取消规则；
  除退款限制与客户侧标识外，行为 MUST 与客户自助订单一致。

### 代下单留痕

- **FR-452**: 每笔代客订单 MUST 持久记录代下单的后台用户身份与下单时间；
  该记录 MUST 在订单生命周期内可追溯。
- **FR-453**: 后台订单列表 MUST 显示代下单人；客户自助订单 MUST 显示为空或「客户自助」。
- **FR-454**: 后台订单详情 MUST 显示代下单人及下单时间。
- **FR-455**: 后台订单列表 MUST 支持「全部 / 仅代客下单 / 仅客户自助」筛选；
  列表条数与统计数字 MUST 使用同一筛选口径。
- **FR-456**: 订单操作日志 MUST 记录一条明确的「运营代客下单」，并包含代下单人；
  该记录 MUST NOT 被后续订单操作覆盖或删除。
- **FR-457**: 后台 MUST NOT 提供修改或清除代下单人的功能。
- **FR-458**: 代下单人 MUST 以后台用户编号为准记录；展示时解析为用户昵称，
  账号被删除时 MUST 显示可辨识的兜底（例如编号），MUST NOT 显示空白。

### 客户侧可见性与退款

- **FR-459**: C 端订单列表 MUST 显示「客服代下单」标识；MUST NOT 显示运营人员姓名、账号或内部编号。
- **FR-460**: C 端订单详情 MUST 显示「客服代下单」标识；MUST NOT 显示运营人员姓名、账号或内部编号。
- **FR-461**: C 端 MUST NOT 为代客订单显示「申请退款 / 申请售后」入口。
- **FR-462**: 客户侧（C 端接口）MUST 拒绝对代客订单发起售后/退款，并返回明确文案
  （例如「请联系客服处理」），MUST NOT 返回通用系统异常；后台代客发起售后 MUST 走独立入口
  （见 FR-463），MUST NOT 复用客户侧接口的鉴权。
- **FR-463**: 运营 MUST 能在后台订单详情为代客订单**代客户发起售后**；售后 MUST 复用现有
  售后审核、退款与状态机，MUST NOT 新增独立的退款单体系。在线支付 MUST 按现有链路原路退款；
  对公转账与线下收款仍由财务线下打款。
- **FR-464**: 客户 MUST 能在自己的订单列表中看到代客订单，并能查看详情、支付未支付订单；
  但 MUST NOT 自行取消代客订单。

### 边界与审计

- **FR-465**: 本特性 MUST NOT 支持代客申请发票；客户可在支付后按现有 C 端开票能力自行申请。
- **FR-466**: 代客下单 MUST NOT 修改客户的地址簿、购物车、优惠券、积分或会员资料。
- **FR-467**: 提交期间页面 MUST 禁用重复提交，避免双击产生两笔相同订单。
- **FR-468**: 代客下单 MUST NOT 改变现有「确认收款」权限边界；确认收款仍需独立的资金动作权限。
- **FR-469**: 本特性 MUST NOT 支持印刷定制、门店自提、代客注册、代客修改客户资料或代客使用优惠券/积分。
- **FR-470**: 后台代客发起的售后单 MUST 记录发起操作人的后台用户身份；客户侧 MUST NOT
  因此获得自助退款入口。
- **FR-471**: 「代客发起售后」入口 MUST 只对代客订单显示；客户自助订单 MUST 沿用客户自己的
  售后流程，MUST NOT 出现该入口。
- **FR-472**: 后台订单详情 MUST NOT 为代客订单提供「继续收款 / 重新发起支付」入口；
  未支付的代客订单只能由运营取消后重新代客下单，或等待现有超时规则取消。
- **FR-473**: C 端订单详情 MUST NOT 为代客订单显示「取消订单」入口；服务端 MUST 拒绝客户
  取消代客订单，并返回明确文案（提示联系客服）。取消只能由运营在后台按现有能力处理，
  且仍仅限未支付订单。
- **FR-474**: 代客订单 MUST 使用独立来源「后台代客」；后台订单来源筛选与报表 MUST 能直接
  区分代客订单，MUST NOT 落入「未知」或伪装成客户常用终端。
- **FR-475**: 后台「代客发起售后」MUST 由独立的「代客售后」权限控制，并与「代客下单」权限
  分离；只有被授予该权限的角色才能看到入口并成功调用。实际售后审核与退款动作 MUST 仍由
  现有售后权限控制，MUST NOT 因拥有「代客售后」权限而绕过。

### Key Entities *(include if feature involves data)*

- **代客订单归属**：订单与「代下单后台用户 + 下单时间」的关联；属于订单的正式属性，
  与「订单操作日志」相互独立、互为佐证。
- **代下单操作日志**：订单生命周期内的审计事件，类型为「运营代客下单」，包含代下单人。
- **客户地址（只读引用）**：代客下单只读取目标客户地址簿中的地址作为订单收货快照，
  不回写、不新建、不修改。
- **支付方式**：复用现有在线支付渠道与对公转账；不新增渠道。
- **计价结果**：提交前的预览与提交时的最终结果，二者使用同一套服务端规则。
- **代客售后**：由运营在后台代客户发起的售后单，复用现有售后实体与状态机；
  客户为售后归属人，发起操作人为后台用户。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-161**: 运营从进入「代客下单」到订单创建成功，在商品已选好的情况下不超过 **3 分钟**。
- **SC-162**: **100%** 的代客订单在后台列表与详情可查到代下单人；抽查 0 笔缺失。
- **SC-163**: 客户完成在线支付后 **10 秒内**，后台与 C 端均显示订单已支付/待发货。
- **SC-164**: **0 笔**代客订单在 C 端显示自助退款入口；**100%** 的代客订单退款请求被明确拒绝并给出可读文案。
- **SC-165**: 同商品、同数量、无券无积分时，代客订单应付金额与客户自助下单金额 **100% 一致**。
- **SC-166**: 印刷定制、门店自提、未注册/禁用客户等不支持场景 **100%** 被拒绝，且提示可读。
- **SC-167**: 没有「代客下单」权限的后台账号 **0 次**看到入口、**0 次**成功创建订单。
- **SC-168**: 在线支付渠道不可用时，**100%** 返回可读原因，且不产生「已支付」订单。
- **SC-169**: 代客订单在发货、收货、评价、超时取消上与客户自助订单一致；抽样场景 **100%** 通过。
- **SC-170**: 代客下单的**创建请求**对客户地址簿、购物车、优惠券、积分的写入次数为 **0**；
  支付后的积分/经验赠送沿用现有规则，不计入本项（见 Assumptions）。
- **SC-171**: **100%** 的后台代客售后单可追溯到发起操作人；客户侧仍为 **0** 个自助退款入口。
- **SC-172**: **100%** 的代客订单来源显示为「后台代客」，且来源筛选与报表能据此区分。
- **SC-173**: 没有「代客售后」权限的账号 **0 次**看到代客售后入口、**0 次**成功发起；仅有该权限
  也不能绕过现有售后审核与退款权限。

## Assumptions

- 目标客户必须已经注册；本特性不提供「先注册再下单」或代建账号。
- 运营角色已具备会员检索、商品检索所需的现有只读权限（沿用后台现有权限体系）。
- 在线支付依赖现有微信扫码/支付宝扫码渠道的配置；渠道未启用时按 FR-448 报错，
  不影响对公转账与订单创建。
- 现有价格规则拒绝应付金额 ≤ 0 的订单；本特性不额外处理零元订单。
- 代客订单沿用现有营销规则：除不使用优惠券、不抵扣积分外，仍按现有规则赠送积分与经验、参与会员成长（若需关闭赠送，另行确认）。SC-170 的「零写入」指**创建请求**，不含支付后的赠送。
- 代客订单沿用现有待支付超时取消规则；客户可自行支付，但不能自行取消，取消由运营在后台处理。
- 未支付的代客订单离开创建页面后不提供继续收款入口；运营通过取消后重建处理。
- 代客订单的退款走「后台代客发起售后」：在线支付按现有售后链路原路退款，
  对公转账与线下收款由财务线下打款并在售后单记录处理结果；不新增独立退款单体系。
- 后台代客发起的售后单，客户在 C 端能否撤销沿用现有售后撤销规则；本特性不额外禁止。
- C 端只显示「客服代下单」中性标识，不展示运营人员身份。
- 本特性不新增客户通知渠道（短信 / 站内信）；客户通过 C 端订单列表与详情的标识感知代客订单。
- 租户内持有权限的运营可以服务该租户下的任意客户；企业授权商品仍受现有企业归属与席位规则约束。
- 管理端订单列表与详情已有的操作（调价、改地址、发货、取消、确认收款）行为不变。

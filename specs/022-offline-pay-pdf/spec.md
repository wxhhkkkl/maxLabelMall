# 功能规格：对公转账订单导出 PDF 凭证

> 编号续 021：本规格从 **FR-585 / SC-217 / US71** 接着往下排
> （021 排到 FR-584 / SC-216 / US70 / Q164）。

**Feature Branch**: `022-offline-pay-pdf`
**Created**: 2026-11-25
**Status**: Draft
**Input**: User description: "如果客户选择对公支付，订单详情页加个功能，用户可以导出一个 pdf，包含支付的对公账户信息，以及采购的内容列表，和订单相关的信息"

---

## 背景与问题

对公转账客户（企业财务 / 采购）打款时，需要把**收款账户、订单号、应付金额、采购明细**
交给公司走内部付款审批。今天这些信息只能：

| 客户想做的事 | 今天怎么做 | 问题 |
|---|---|---|
| 把收款账户与金额交给财务 | 截图订单页、手抄账户 | 抄错账号/金额；截图里混入手机状态栏与导航 |
| 采购明细进内部审批 | 手动复制商品名、单价、数量 | 规格容易漏，金额对不上要来回确认 |
| 付款后留档 | 订单页截图 | 确认收款后账户区块消失（008：区块只在「待收款」显示），无法再导出 |

本特性在**门面站订单详情页**增加「导出对公转账单 PDF」：一键下载一份 A4 凭证，
包含对公收款账户、采购商品清单、订单与金额信息。**只改门面站，不新增后端接口、
不改数据库**。

## 现状与证据（棕地事实）

| # | 现状 | 证据 |
|---|---|---|
| E1 | 订单详情接口对**每一笔对公转账订单**都返回 `offlinePay`（非对公单为 `null`），字段含 `accountName / accountNo / bankName / tip / waiting` | `AppTradeOrderController#buildOfflinePay`；`AppOrderOfflinePayRespVO` |
| E2 | 收款账户来自交易配置 `trade_config.offline_pay_*`，后台维护，服务端下发；前端不得编造 | 同上；`storefront/src/types/order.ts` `OfflinePayInfo` |
| E3 | 订单详情页的「待收款」区块**只在 `offlinePay.waiting = true` 时渲染**；确认收款后区块消失 | `storefront/src/views/OrderDetailView.vue` `#offlinePay` |
| E4 | 订单详情响应已包含：商品项（名称/规格/单价/数量/项应付）、订单号、下单时间、实付金额、金额拆分（商品总额/运费/券/积分/会员优惠）、收货信息、开票信息、买家留言 | `storefront/src/types/order.ts` `OrderDetail` / `OrderInvoice` |
| E5 | 门面站技术栈为 Vue 3 + Vite + TS，依赖极少（axios / pinia / qrcode / crypto-js / dompurify）；**没有** PDF 或截图库 | `storefront/package.json` |
| E6 | 订单项图片可能来自独立上传域名，跨域图片会让前端画布被污染、无法导出 | 既有图片上传服务 |

## Clarifications

### Session 2026-11-25（所有者已拍板）

- Q165：PDF 怎么生成？ → A：**前端直接下载**。允许新增 `jsPDF` + `html2canvas` 两个运行时依赖；
  中文以图片形式渲染（文字不可复制/搜索，文件稍大），不新增后端接口。
- Q166：哪些订单显示导出入口？ → A：**所有对公转账订单**（`offlinePay` 非空）。
  「待收款」时用于打款，确认收款后仍保留入口用于留档。
- Q167：PDF 包含哪些内容？ → A：固定内容 = 对公收款账户（户名/账号/开户行）、
  采购商品清单（名称/规格/单价/数量/小计）、订单号、下单时间、实付金额；
  附加内容**全部包含** = 收货信息、金额明细、开票信息（已申请时）、买家留言。

### Session 2026-11-25（分析修订，所有者确认）

- Q168：**已取消的对公订单**要不要能导出？ → A：**不能**。入口只对未取消的对公订单显示；
  PDF 的订单信息里必须带**订单状态**（待收款 / 已付款等），避免凭证被误当作仍可付款。
- Q169：**已作废的发票**要不要出现在 PDF？ → A：**不出现**（与订单详情页一致：
  退款/作废后不展示发票内容）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 待收款时导出 PDF 去付款 (Priority: P1)

客户在结算页选择「对公转账」并下单后，进入订单详情，看到收款账户与「待收款」提示；
点「导出对公转账单」下载一份 PDF，交给财务按单付款。

**Why this priority**：这是对公客户付款链路的最后一公里 —— 没有这份凭证，
客户只能截图或手抄账户，抄错账户/金额会造成打款失败甚至打错账户。

**Independent Test**：用一笔「待收款」对公订单打开订单详情 → 断言入口可见 →
触发导出 → 断言下载文件名包含订单号，且生成内容包含账户、商品、金额与订单信息。

**Acceptance Scenarios**：

1. **Given** 一笔 `offlinePay.waiting = true` 的对公订单，**When** 进入订单详情，
   **Then** 显示「导出对公转账单」入口，且入口在「待收款」区块附近。
2. **Given** 上述订单，**When** 点击导出，**Then** 下载一份 A4 PDF，文件名形如
   `对公转账单_O202611241357331.pdf`。
3. **Given** PDF 已生成，**When** 打开查看，**Then** 包含：收款户名、收款账号、开户行、
   订单号、下单时间、订单状态、实付金额、每个商品的名称/规格/单价/数量/小计。
4. **Given** 后台配置了转账提示语（如「附言写订单号」），**When** 导出，**Then** 提示语出现在 PDF 中。

---

### User Story 2 - 确认收款后导出留档 (Priority: P2)

订单确认收款后，「待收款」区块按 008 的口径消失，但客户仍可在订单详情导出同一份
PDF 作为付款与采购留档。

**Why this priority**：财务对账、报销与内部审计需要凭证；若入口随「待收款」区块消失，
客户事后无法补取。

**Independent Test**：用一笔 `offlinePay.waiting = false` 且已收款的对公订单打开详情 →
入口仍可见 → 导出成功，内容包含账户与商品信息。

**Acceptance Scenarios**：

1. **Given** 一笔已确认收款的对公订单，**When** 进入订单详情，**Then** 导出入口仍可见。
2. **Given** 上述订单，**When** 导出，**Then** PDF 与待收款时结构一致（不因 `waiting=false` 缺少账户）。

---

### Edge Cases

- **非对公订单（`offlinePay = null`）**：不显示导出入口，页面其余行为不变。
- **已取消的对公订单**：不显示导出入口（Q168）—— 取消后后端 `waiting` 仍可能为 `true`
  （它只看「是否确认收款」与「是否已付」），若不排除会导出一份「看起来仍可付款」的凭证。
- **订单状态**：PDF 的订单信息必须写明状态（待收款 / 已付款等），不得让凭证脱离状态被使用。
- **收款账户未配置 / 字段为空**：PDF 如实显示「—」，前端不得编造账户信息（008 既有口径）。
- **商品项很多（如 30 项）**：自动分页，不得截断；不得因超出一页而丢商品或金额。
- **商品名 / 买家留言 / 开票抬头含 `<` `>` `&` 等字符**：按纯文本呈现，不得被当作 HTML 执行，
  也不得影响页面其他内容。
- **重复点击**：生成期间禁用按钮并提示「生成中…」，避免并发生成多份。
- **生成失败（浏览器不支持 / 画布受限）**：给出可读的失败提示，不下载空白或损坏文件。
- **订单项图片**：PDF **不包含商品图片**（跨域图片会污染画布导致导出失败），只保留文字信息。
- **开票信息**：未申请开票时整块不渲染；已申请时展示票种、抬头类型、抬头、税号、金额。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-585**: 订单详情页 MUST 对**未取消的对公转账订单**（`offlinePay` 非空且状态不是「已取消」）
  显示「导出对公转账单」入口；非对公订单与**已取消**订单 MUST NOT 显示该入口。
- **FR-586**: 点击入口 MUST 在浏览器生成并下载一份 **A4 PDF**；文件名 MUST 包含订单号
  （形如 `对公转账单_<订单号>.pdf`）。
- **FR-587**: PDF MUST 包含对公收款账户：**收款户名、收款账号、开户行**（值来自订单详情接口）。
- **FR-588**: PDF MUST 包含**采购商品清单**：每个订单项的名称、规格、单价、数量、小计。
- **FR-589**: PDF MUST 包含订单基本信息：**订单号、下单时间、订单状态、实付金额**
  （状态文案：待收款 / 已付款等，与服务端状态一致）。
- **FR-590**: PDF MUST 包含**收货信息**：收货人、手机号、收货地址。
- **FR-591**: PDF MUST 包含**金额明细**：商品总额、运费、优惠券优惠、积分抵扣、会员优惠、应付金额
  （各项为 0 时如实显示 0，不得隐藏或编造）。
- **FR-592**: 订单**已申请开票且发票未作废**时，PDF MUST 包含开票信息：票种、抬头类型、
  抬头名称、税号、开票金额；未申请或已作废时 MUST NOT 渲染该区块（Q169）。
- **FR-593**: 买家留言**非空**时，PDF MUST 包含该留言；为空时不渲染该区块。
- **FR-594**: PDF 内容超出一页时 MUST 自动分页，MUST NOT 截断商品或金额。
- **FR-595**: 生成过程中 MUST 禁用入口并显示进行中提示；生成失败 MUST 提示失败原因，
  MUST NOT 下载空白或损坏的文件。
- **FR-596**: 订单中的用户可控文本（商品名、规格、留言、抬头等）MUST 以纯文本渲染，
  MUST NOT 作为 HTML 注入。
- **FR-597**: 本特性 MUST NOT 新增或修改后端接口、数据库结构；所有数据 MUST 来自既有订单详情响应。
- **FR-598**: 金额的换算与展示格式 MUST 与订单详情页一致：以「元」为单位、保留两位小数
  （行数不必一致：PDF 需额外列出积分抵扣与会员优惠）。

### Key Entities *(include if feature involves data)*

- **对公转账订单**：`offlinePay` 非空的交易订单；凭证的数据来源是订单详情快照。
- **收款账户**：户名、账号、开户行（后台交易配置，服务端下发）。
- **PDF 凭证**：一次导出的 A4 文档，内容由订单快照与收款账户组成；不落库、不产生新数据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-217**: 待收款对公订单从进入详情到拿到 PDF 不超过 **3 次操作**（进入详情 → 点导出 → 保存），
  且下载文件名包含订单号。
- **SC-218**: 对照订单详情逐项核对，PDF 中 FR-587~FR-593 要求的信息**缺项数为 0**。
- **SC-219**: 随机抽查 10 笔非对公订单，导出入口出现次数为 **0**。
- **SC-220**: 含 **20 个及以上**订单项的订单导出后，商品项与金额**一项不少**（允许分页）。
- **SC-221**: 商品名/留言中含 `<script>` 与 `<>&` 的订单导出后，PDF 如实显示原文，
  页面不执行脚本、不出现 DOM 破坏。
- **SC-222**: 随机抽查 10 笔**已取消**的对公订单，导出入口出现次数为 **0**（Q168）。
- **SC-223**: 普通桌面浏览器下，**20 个商品项**的订单从点击导出到开始下载 **≤ 3 秒**。

## Assumptions

- 允许门面站新增两个运行时依赖（`jsPDF`、`html2canvas`），由本特性说明理由（Q165）；
  不引入 UI 组件库（项目既有硬约束不受影响）。
- 收款账户、金额、商品、订单信息都以**订单详情接口**为准；本特性不提供新的数据口径。
- PDF 采用「先排成 A4 版式的 HTML，再转成图片写入 PDF」的方式；不要求文字可复制/搜索（Q165 已接受）。
- 商品图片不进入 PDF，避免跨域画布污染（E6）。
- 不涉及小程序 / App 端；管理端不需要该凭证（管理端有自己的订单详情与导出）。

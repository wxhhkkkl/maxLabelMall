# 功能规格：代客开票（管理端代客户申请发票）

> 编号续 022：本规格从 **FR-599 / SC-224 / US73** 接着往下排
> （022 排到 FR-598 / SC-223 / US72 / Q169）。

**Feature Branch**: `023-agent-invoice`
**Created**: 2026-11-25
**Status**: Draft
**Input**: User description: "想让运营在代客下单时直接带发票" + 澄清：完整 006 发票字段；后台也可为已有订单补申请；补申请适用所有订单。

---

## 背景与问题

017 代客下单当时的口径是「**不代客申请发票**」（FR-465）—— 客户支付后自己到 C 端补开。
实际运营中，客户常在电话里把发票信息直接给运营，期待下单时一并办好：

| 客户想做的事 | 今天怎么做 | 问题 |
|---|---|---|
| 下单时就把发票开好 | 运营拒绝，让客户自己去订单详情填 | 客户不会操作/嫌麻烦；两通电话来回 |
| 先下单，发票信息后补 | 仍要客户自己登录 C 端补申请 | 运营手里有信息却办不了 |
| 企业客户开专票 | 客户自己填开户行/账号/行号 | 填错率高，财务退回重开 |

本特性放开 017 的限制：**代客下单时可直接带发票**，并且**运营可以在后台为任何已有订单
代客户补申请发票**。发票字段、校验、落库全部复用 006 的既有实现，不新增表/列/权限点。

## 现状与证据（棕地事实）

| # | 现状 | 证据 |

| E9 | 订单管理已有权限点 `trade:order:update`（改价/取消/改地址等都用它）；代客下单另有 `trade:order:agent-create` | `TradeOrderController` |

## Clarifications

### Session 2026-11-25（所有者已拍板）

- Q170：代客下单时的发票字段范围？ → A：**完整 006 一套**（票种/抬头类型/抬头/税号/注册地址/
  注册电话/开户行/银行账户/开户行行号/邮箱），与 C 端结算页一致。
- Q171：发票只能在代客下单时带，还是后台也能补？ → A：**两者都要**：下单时可选开票；
  已有订单也可由运营在后台**补申请**。
- Q172：后台补申请的范围？ → A：**所有订单**（不限于代客下单的订单）。

### 实现约束（所有者确认的口径）

- 权限复用 `trade:order:update`，**不新增权限点**、不新增菜单/按钮数据。
- **不新增表/列，无 SQL 迁移**；发票仍落 `trade_order_invoice`，一单一条。
- 0 元订单不能开票：代客下单时前端禁用开票选项；后台补申请时服务端拒绝。
- 企业授权商品订单必须使用企业抬头（沿用 FR-296）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 代客下单时直接带发票 (Priority: P1)

运营在代客下单表单勾选「开具发票」，填好客户给的票种与抬头信息，提交后订单与发票一起创建；
客户在 C 端订单详情能看到「待开票」，付款后运营再开具/上传。

**Why this priority**：这是本次需求的原点 —— 客户已经口头提供了发票信息，运营却要再让客户
自己登录填写，体验断裂。

**Independent Test**：管理端代客下单勾选开票并填完整字段 → 创建成功 → 订单详情显示「待开票」
且字段与填写一致；不勾选时行为与今天完全一致（无发票）。

**Acceptance Scenarios**：

1. **Given** 运营在代客下单页，**When** 勾选「开具发票」并填写企业普票信息，**Then** 可提交，
   订单创建成功后发票申请同时存在（状态「待开票」）。
2. **Given** 不勾选开票，**When** 提交订单，**Then** 不创建任何发票申请（与既有行为一致）。
3. **Given** 发票信息不合法（如企业抬头缺税号、个人开专票），**When** 提交，**Then** **订单与发票都不创建**，
   返回明确原因。
4. **Given** 订单含企业授权商品，**When** 选择个人抬头，**Then** 被拒绝并提示必须使用企业抬头。
5. **Given** 结算后实付为 0 元，**When** 查看开票选项，**Then** 不能勾选/选择开票。

---

### User Story 2 - 后台为已有订单补申请发票 (Priority: P2)

客户下单时没提发票，后来电话补充。运营在订单详情点「代申请发票」，填好信息提交；
客户在 C 端订单详情立刻看到「待开票」。

**Why this priority**：补申请覆盖「下单后才提」的常见场景；没有它，US1 只能解决一半问题。

**Independent Test**：对一笔已支付、未取消、实付 > 0、尚无发票的普通订单，在后台提交补申请 →
成功；对不满足条件的订单，入口不可用/接口拒绝。

**Acceptance Scenarios**：

1. **Given** 已支付、未取消、实付 > 0、无发票的订单，**When** 运营在详情提交完整发票信息，**Then** 创建成功。
2. **Given** 订单未支付 / 已取消 / 实付为 0 / 已有发票，**When** 查看详情，**Then** 不提供补申请入口；
   直接调接口同样被拒绝。
3. **Given** 客户已自行申请过发票，**When** 运营再补申请，**Then** 被拒绝（一单一条）。
4. **Given** 订单含企业授权商品，**When** 选择个人抬头，**Then** 被拒绝。
5. **Given** 补申请成功，**When** 客户打开 C 端订单详情，**Then** 显示「待开票」，可等待开具后下载。

---

### Edge Cases

- **0 元订单**：代客下单选择开票但实付为 0 → 前端禁用开票；服务端沿用既有「忽略」策略（不建发票）。
  后台补申请则**明确拒绝**（订单已存在，给出可读原因）。
- **对公转账待收款单**：下单时可以带发票（申请为「待开票」）；**确认收款前后台不能开具**
  （既有 E7 规则），与 C 端一致。
- **虚拟商品 / 个人订阅订单 / 企业授权订单**：均可开票；企业授权订单强制企业抬头。
- **已退款/已取消**：补申请入口不显示，接口拒绝。
- **重复提交**：一单一条；并发由唯一约束兜底，报「该订单已申请发票」。
- **发票已作废后**：不能在后台补一条新的（仍是一单一条，作废记录保留）；与 006 的作废口径一致。
- **权限不足**：没有 `trade:order:update` 的账号看不到入口，接口返回 403。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-599**: 代客下单表单 MUST 提供可选的「开具发票」开关，默认**关闭**（不开票）。
- **FR-600**: 开启后 MUST 采集完整 006 字段：票种、抬头类型、抬头名称、税号、注册地址、注册电话、
  开户行、银行账户、开户行行号、邮箱；必填矩阵 MUST 与 `InvoiceValidator` 一致
  （企业+普票/专票要名称+税号；个人+普票只要名称；收据只要名称；个人不能开专票）。
- **FR-601**: 代客下单携带的发票 MUST 与订单**同一事务**落库：任何一项校验失败时，
  订单与发票都 MUST NOT 创建。
- **FR-602**: 含企业授权商品的代客订单，发票抬头 MUST 为企业（沿用 006 / FR-296）。
- **FR-603**: 结算后实付为 0 元的代客订单 MUST NOT 允许开票（前端禁用开票选项）；
  服务端沿用既有「忽略」策略，不创建发票。
- **FR-604**: 管理端 MUST 为**任何已有订单**代客户补申请发票；入口 MUST 仅在满足
  「已支付 + 未取消 + 实付 > 0 + 尚无发票申请」时可用。
- **FR-605**: 补申请 MUST 复用与 C 端补开相同的字段与校验（票种/抬头矩阵、企业抬头规则），
  并 MUST 保持**一单一条**；重复申请 MUST 被拒绝并给出可读原因。
- **FR-606**: 代客下单与后台补申请 MUST 复用权限点 `trade:order:update`；
  MUST NOT 新增权限点、菜单或按钮数据。
- **FR-607**: 系统 MUST 记录代申请的操作人，便于审计（至少能在订单日志或发票记录中追溯到后台操作）。
- **FR-608**: 补申请成功后，客户在 C 端订单详情 MUST 看到「待开票」；
  开具后 MUST 按既有 006 流程看到/下载发票。
- **FR-609**: 补申请 MUST NOT 改变订单金额、支付状态或订单状态。
- **FR-610**: 本特性 MUST NOT 新增数据库表或列，MUST NOT 包含 SQL 迁移脚本。
- **FR-611**: 017 的 FR-465（不代客申请发票）MUST 被本特性修订；017 文档 MUST 注明由 023 承接。
- **FR-612**: 发票字段的校验 MUST 仍由服务端唯一实现（`InvoiceValidator`）裁决，
  前端校验只能作为提前提示，MUST NOT 形成第二套规则。

### Key Entities

- **发票申请（`trade_order_invoice`）**：一单一条，金额取订单实付快照（006 既有口径）；
  本特性只是新增「由运营发起」的创建入口，不改表结构。
- **代客订单**：`agent_user_id` 非空的订单；本特性不新增字段。
- **操作人**：发起代申请的后台账号，用于审计。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-224**: 运营在代客下单时勾选开票并填写完整信息，订单创建后订单详情**立即可见**「待开票」，
  字段与填写内容一致（缺项数 0）。
- **SC-225**: 发票字段非法（缺税号 / 个人开专票）时，**订单与发票均未创建**（抽样 10 次，残留 0 条）。
- **SC-226**: 含企业授权商品的订单选择个人抬头，**100% 被拒绝**且提示必须使用企业抬头。
- **SC-227**: 满足条件的已有订单，运营从打开详情到完成补申请 **≤ 3 次操作**；
  对 10 笔不满足条件的订单，入口误放行次数为 **0**。
- **SC-228**: 同一订单重复补申请（含客户已申请的情况）**100% 被拒绝**，且只存在 1 条发票记录。
- **SC-229**: 后台代申请可追溯到操作人（订单日志或发票记录），抽查记录可查到操作人。

## Assumptions

- 发票字段与校验完全复用 006，不新增票种/字段/状态。
- 代申请不改变 006 的后续流程：运营仍需在订单**已支付**后开具/上传；已开票可重新上传。
- 补申请入口放在**订单详情**（管理端）；列表页不新增入口（运营从详情操作）。
- 权限沿用 `trade:order:update`，不区分「代客下单」与「补申请」两个动作。
- 客户仍保留 C 端自助补开能力；两边共用同一服务校验，先到先得（一单一条）。
